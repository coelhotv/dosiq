# AP-307 — Flag esconde a SUPERFÍCIE mas o GATE continua bloqueando por ela → bloqueio invisível

**Spec:** 044 (dose-only) · **Plataforma:** mobile · **Severidade:** HIGH (beco sem saída em produção; usuário não consegue excluir medicamento)

## O furo

A 044 F3 desligou as superfícies de estoque no modo dose-only. No sheet de bloqueio de
exclusão (`MedicineDeleteBlockedSheet`) isso virou uma condição de render:

```js
{stockTrackingEnabled && stockUnits > 0 ? <CardDeEstoque/> : null}
```

Mas o **pré-check** que decide se o botão fica habilitado (`useMedicineDelete`) continuou
bloqueando por estoque sem consultar a flag:

```js
const hasDependencies = protocols.length > 0 || stockUnits > 0 || titrationSteps.length > 0
```

Usuário dose-only com saldo de estoque congelado (a 044 **congela**, não apaga — ver [[AP-294]])
via: botão `[Apagar]` **desabilitado**, texto *"Desative ou exclua as **dependências abaixo**"*,
e a lista **vazia**. Acusação sem réu — o app afirma uma pendência e se recusa a mostrá-la.
Beco sem saída (Constituição IX). Achado no smoke do PO.

## Por que passou por tudo

- **tsc/lint**: os dois lados compilam; nada relaciona a condição de render com a condição do gate.
- **testes**: `useMedicineDelete` **não tinha nenhum teste** (hook de 90 linhas com regra de
  negócio). O teste do sheet, se existisse, veria a lista vazia como render correto — porque é.
- **RC5/RC6 da F3**: revisaram a F3, onde a mudança do sheet é obviamente certa. A omissão está
  no arquivo **não tocado**.
- **web já estava certa**: `views/Medicines.tsx:39` fez
  `const hasStock = stockTrackingEnabled && stockSummary.some(...)` na própria F3. A paridade
  quebrou só no mobile — mesmo modo de falha do [[AP-296]].

## O que a correção NÃO precisou fazer

A hipótese natural ("na exclusão, zerar o estoque antes de apagar") é **desnecessária**.
Verificado no banco (`pg_constraint.confdeltype`):

| FK | delete |
|---|---|
| `stock_medicine_id_fkey` | `c` = CASCADE |
| `protocols` / `medicine_logs` / `purchases` / `stock_adjustments` / `stock_consumptions` | `c` = CASCADE |
| `titration_steps_medicine_id_fkey` | `a` = NO ACTION |

O banco já zera o estoque no delete. O único FK restritivo é o de `titration_steps` — e aquele
bloqueio (029 F5) segue valendo nos dois modos, junto com o de tratamento. **Consultar o FK antes
de escrever lógica de limpeza manual** evitou código que duplicaria o que o schema já garante
(hierarquia de verdade da [[R-295]] vale também para `ON DELETE`).

## Fix

`useMedicineDelete(medicine, stockTrackingEnabled = true)` — estoque só conta como dependência
com o controle **ligado**. Default `true` = fail-safe [[AP-277]]: ausência de dado nunca desliga o
estoque por omissão. Matrix de cache ([[R-236]]) atualizada: a exclusão passa a invalidar
`@dosiq/stock-snapshot`, porque agora ela pode apagar lotes que estavam no snapshot.

## Farol

- **Toda condição `flag && X` adicionada a um RENDER exige a pergunta: existe um GATE que decide
  por `X`?** Esconder a superfície sem soltar o gate produz bloqueio invisível; soltar o gate sem
  esconder a superfície produz o inverso (superfície fantasma). São **um** fato, em dois arquivos.
- Mensagem de bloqueio que aponta para uma **lista** ("as dependências abaixo") + lista renderizada
  condicionalmente = par que precisa de invariante: `bloqueado ⇒ lista não-vazia`. Se a UI pode
  acusar sem listar, o beco sem saída já existe, só falta o dado.
- Hook com regra de negócio e **zero testes** é o lugar onde flags novas passam despercebidas.
- Feature-flag entregue por fases: a fase que apaga a superfície precisa varrer **quem mais lê o
  mesmo dado** (`grep` do campo, não só dos componentes visíveis).
- Paridade web↔mobile: guard aplicado num lado é checklist do outro ([[AP-296]]).

## Relações

Espelho de [[AP-305]] no lado do BLOQUEIO: lá um canal não **consumia** a capacidade declarada
(feature pronta que não faz nada); aqui um gate não consumia a flag (trava que não deveria existir).
Nos dois, o pipeline valida cada arquivo isolado e nunca pergunta se os dois lados concordam.
Família 044: [[AP-277]] [[AP-294]]. PR #759.
