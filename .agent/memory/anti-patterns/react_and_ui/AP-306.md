# AP-306 — Unidade de medida montada em string solta no call site → N grafias divergentes, e o JSDoc vira ficção

**Detectado:** spec 029 F5, smoke do PO 2026-07-18
**Relaciona:** [[AP-299]] · [[R-267]] · [[R-295]]

## O sintoma

`packages/core/src/utils/doseUnit.ts` produz **três grafias de mililitro**, no mesmo arquivo:

| Origem | Saída |
|---|---|
| `formatLiquidConcentration` (l.53) | `0,5ml` — minúsculo, **sem espaço** |
| `formatConcentrationLabel` (l.222) | `0,5 mL` |
| `formatDose` (l.329) | `2,5 ml` |

Lado a lado numa mesma tela: `Mounjaro 2,5 mg / 0,5ml`.

## O que torna isto um anti-padrão, e não um typo

**O JSDoc do `formatConcentration` promete `'2,5 mg / 0,5 mL'` (l.73 e l.79) — e a implementação
entrega `0,5ml`.** A documentação estava CERTA; a implementação divergiu depois, em silêncio.
Ninguém percebeu porque nenhum teste do arquivo assertava a grafia da unidade — os testes existentes
fixavam o número, não o rótulo. Escrevi um teste novo a partir do JSDoc e ele falhou: a doc virou
ficção sem nunca ter sido "editada errado".

A causa raiz não é a caixa da letra. É que a unidade é **concatenada em string no ponto de uso**:
44 call sites fora do core montam unidade à mão (medido 2026-07-18, web+mobile+bot). Cada call site
novo é um sorteio entre `ml`/`mL`/`0,5ml`. Padronizar a grafia sem centralizar a emissão só reseta
o contador — o próximo componente reintroduz a divergência, e nenhum gate reclama.

## Por que passa por todos os gates

Rótulo de unidade é **string de apresentação**: `tsc` não o conhece, lint não o conhece, e o teste
que renderiza o componente costuma assertar o número (`'2,5'`) ou usar regex frouxa. É a mesma
família do [[AP-305]] — o pipeline valida a FORMA do dado e nunca pergunta como ele é LIDO.

## Regra

**Unidade de medida NUNCA é concatenada no call site. Sai sempre de um formatador do core, e o
formatador tem teste que fixa a grafia — não só o número.**

Ao tocar qualquer texto com unidade:
1. `grep` a grafia no core antes de escrever a sua. Se houver mais de uma, é bug, não estilo.
2. Teste novo asserta a string COMPLETA (`'Mounjaro 2,5 mg / 0,5ml'`), nunca só o valor.
3. Divergência entre JSDoc e implementação: **o JSDoc é a intenção original** — confirmar qual dos
   dois envelheceu antes de "corrigir" o teste para passar.

## 🔴 Armadilha para quem for padronizar

`DOSAGE_UNIT_LABELS` (`packages/core/src/schemas/medicineSchema.ts:15`) mapeia
**valor de enum do banco → rótulo de exibição**:

```ts
'mg/ml': 'mg/ml',   // ← chave = valor com CHECK constraint em medicines.dosage_unit
'ui/ml': 'UI/ml',   // ← só o lado DIREITO é rótulo
```

Trocar a CHAVE quebra o insert com `23514`. Um sweep `sed s/ml/mL/` pega as duas colunas e derruba
o cadastro de líquido em produção — exatamente a classe do [[AP-299]]. Só o lado direito é editável.

## Convenção correta (para a spec)

`mL`. SI aceita `l` e `L`, mas o contexto é farmacêutico: é a grafia da ANVISA nas bulas e a que está
impressa na caneta. O `L` maiúsculo existe para não confundir `l` com o algarismo `1`.

## Farol

Duas grafias da mesma unidade no mesmo arquivo. JSDoc com exemplo que a função não produz.
Unidade aparecendo em template literal fora de `utils/`.

## Escopo do débito (medido 2026-07-18)

44 call sites hardcoded fora do core · 35 arquivos de teste fixando string com `ml` · helpers
espalhados por 9 arquivos de `packages/core/src/utils/`. Tier 2 (cruza web+mobile+bot+core).
Spec de padronização a abrir após o merge do 029 F5.
