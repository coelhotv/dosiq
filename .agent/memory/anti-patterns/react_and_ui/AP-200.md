# [AP-200] Cache de query persistido não invalida em mudança de fonte server-side

**Status:** active · **Layer:** warm · **Domain:** react_and_ui
**Criado:** 2026-05-31 (PR-F4.1 / Fase 4 — smoke b0c9746c)

## Sintoma
Após reescrever a FONTE de uma view/RPC cacheada (ex: `v_daily_adherence`/`v_adherence_heatmap`
de `medicine_logs`→`dose_instances`, G6), o usuário continua vendo os números **antigos**
(adesão pré-migração) — sparkline com dias errados, heatmap com células `0%` que a view nova
não produz. **Hard reload (Cmd+Shift+R) NÃO resolve.**

## Causa
`webQueryCache` persiste em `localStorage['dosiq_query_cache']` (SWR, `staleTime` 30s,
evict em `staleTime*2`=60s). Pontos que prendem o stale:
1. **Hard reload limpa HTTP cache + memória, NÃO localStorage** — o cache persistido sobrevive.
2. **SWR stale-while-revalidate**: entry stale é servido imediatamente; a revalidação em
   background atualiza o cache mas **não o `state` do componente** que já renderizou — fica
   stale até remount/navegação.
3. **Invalidação programática** (`_invalidateAdherenceCache`) só dispara em **mutação de log**
   (create/edit/delete), nunca em **DDL/mudança de fonte server-side**.

## Regra
Toda mudança de **FONTE ou shape** de um dado cacheado server-side DEVE **bumpar o `persistKey`**
do query cache (`dosiq_query_cache` → `_v2` → `_v3`...). Isso abandona o cache persistido antigo
no deploy: todo cliente começa cold para as queries e refetcha a fonte nova no 1º acesso — sem
pedir hard refresh manual (que nem funcionaria).

Verificação instantânea em dev: `localStorage.removeItem('dosiq_query_cache'); location.reload()`.
