## Descrição

O pipeline de notificações multicanal possui **dois enums Zod independentes** que precisam ser atualizados ao adicionar novos kinds:

1. `dispatchInputSchema.kind` em `dispatchNotification.js` — valida entrada do dispatcher
2. `kindSchema` em `server/notifications/payloads/buildNotificationPayload.js` — valida antes de construir o payload

Falhar em atualizar qualquer um resulta em rejeição silenciosa: a exceção é capturada por um `try/catch` no dispatcher e retorna `{ success: false }` sem logar no banco nem enviar push. O usuário pode receber a notificação via caminho legado (Telegram) mas o `notification_log` fica vazio.

## Incidentes

**Incidente 1 — Sprint N1.1/N1.3 (2026-04-26):**
`dispatchInputSchema` não atualizado. Blocos grouped rejeitados silenciosamente antes de chegar aos canais. Descoberto no planning de N1.3 via code review.

**Incidente 2 — Sprint N1.5 (2026-04-26):**
`buildNotificationPayload.kindSchema` não atualizado. R-193 apontava para `api/notify.js` (que chama a função) em vez de `server/notifications/payloads/buildNotificationPayload.js` (onde a função é definida). Implementador checou `api/notify.js`, não encontrou o enum, assumiu que estava correto. Resultado: Telegram e push chegavam via caminho legado mas `notification_log` ficava vazio — inbox da central de avisos vazia por ~24h. Corrigido no PR #504.

## Correção

```js
// server/notifications/payloads/buildNotificationPayload.js
const kindSchema = z.enum([
  'dose_reminder',
  'dose_reminder_by_plan',  // ← adicionar
  'dose_reminder_misc',     // ← adicionar
  'stock_alert',
  'daily_digest',
])

// server/notifications/dispatcher/dispatchNotification.js
kind: z.enum(['dose_reminder', 'dose_reminder_by_plan', 'dose_reminder_misc', 'stock_alert', 'daily_digest']),
```

## Como evitar

Seguir R-193 (checklist completo). Nunca referenciar `api/notify.js` como local do `buildNotificationPayload` — o arquivo de definição é `server/notifications/payloads/buildNotificationPayload.js`.
