# AP-324 — Dep de dev que só se exclui numa plataforma vaza pro release da outra

## Sintoma

O Google Play Console emitiu **dois avisos diferentes** sobre o AAB da v0.30.0 que pareciam ser sobre
o código do dosiq e não eram:

- *"deprecated APIs for edge-to-edge"* citando
  `expo.modules.devlauncher.launcher.configurators.DevLauncherExpoActivityConfigurator.setColor`
- *"resizability and orientation restrictions"* citando
  `com.google.mlkit.vision.codescanner.internal.GmsBarcodeScanningDelegateActivity`
  com `android:screenOrientation="PORTRAIT"`

O dosiq **não tem leitor de código de barras**. A Activity do ML Kit chegou ao binário de produção
porque `expo-dev-launcher` depende de `play-services-code-scanner` + `mlkit:barcode-scanning` para
ler o QR do menu de desenvolvimento.

## Causa

`expo-dev-client` declara `"debugOnly": true` no seu `expo-module.config.json` **apenas no bloco
`apple`**. O bloco `android` não tem o campo — o módulo é autolinkado em **toda** variante.

O gradle plugin do dev-launcher reforça a ilusão de que está tudo certo: ele checa a variante
(`DevLauncherPlugin.kt` → `if (!isDebugVariant(variant, reactExtension)) return`) e **não instrumenta**
classes fora de debug. Mas instrumentar é diferente de linkar: o AAR inteiro continua no APK/AAB.

Custo real no binário publicado: ML Kit, Compose, Koin, Apollo, okhttp, gson, commons-io, e o
manifest anunciando o deep link `exp+dosiq-app`.

## Por que nenhum gate pegou

Não é um bug de código — é **composição de dependências**. `tsc`, `eslint`, os testes e o
`strict-island.sh` operam sobre o JS/TS do projeto; nenhum deles enxerga o grafo do gradle. O
`expo-doctor` valida versões, não conteúdo do artefato. A informação só existe em dois lugares: no
AAB montado e no painel da loja depois do upload.

**A moral não é sobre o dev-client:** é que **o conteúdo do artefato de release é uma superfície sem
gate** neste repo. Toda dependência de desenvolvimento é candidata ao mesmo vazamento.

## Farol

- Pacote de desenvolvimento em `dependencies` (não `devDependencies`) num projeto Expo/RN.
- `expo-module.config.json` de uma dep com `debugOnly` em **um** bloco de plataforma só.
- Aviso da loja apontando classe de um pacote que você não chama.
- Permissão, Activity ou scheme no manifest de produção que ninguém no time reconhece.

## Fix aplicado (2026-07-30)

Config plugin `apps/mobile/withoutDevClientOnRelease.js`: usa `expoAutolinking.exclude`
(propriedade da extensão do settings plugin, vira `--exclude` no comando de autolinking) para tirar
`expo-dev-client`/`-launcher`/`-menu`/`-menu-interface` quando `EAS_BUILD_PROFILE` está definido e é
diferente de `development`. Remove também o scheme `exp+<slug>`, que vem do config plugin do
dev-client e portanto sobrevive à exclusão do autolinking.

Medido: **27 módulos → 23** resolvidos para Android.

**`preview` entra junto de propósito.** Se a exclusão valesse só em `production`, o APK usado no
smoke deixaria de reproduzir o binário publicado — e, como nada disto é verificável por teste, o
smoke é a única verificação que existe. Um smoke que valida um artefato diferente do que vai à loja
não é smoke, é cerimônia.

## Verificação

```bash
cd apps/mobile
npx expo-modules-autolinking resolve -p android --json | \
  node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{const m=JSON.parse(s).modules.map(x=>x.packageName||x.name);console.log(m.length, m.filter(n=>/expo-dev-/.test(n)))})"
```

Sem `EAS_BUILD_PROFILE` deve listar os 4 módulos de dev (é o dev build). Com
`EAS_BUILD_PROFILE=production`, o `settings.gradle` pós-prebuild deve conter a linha
`expoAutolinking.exclude = [...]`.
