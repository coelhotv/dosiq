# AP-324 — Dep de dev que só se exclui numa plataforma vaza pro release da outra

## Sintoma

O Google Play Console emitiu **dois avisos diferentes** sobre o AAB da v0.30.0 que pareciam ser sobre
o código do dosiq e não eram:

- *"deprecated APIs for edge-to-edge"* citando
  `expo.modules.devlauncher.launcher.configurators.DevLauncherExpoActivityConfigurator.setColor`
- *"resizability and orientation restrictions"* citando
  `com.google.mlkit.vision.codescanner.internal.GmsBarcodeScanningDelegateActivity`
  com `android:screenOrientation="PORTRAIT"`

O dosiq **não tem leitor de código de barras**. A Activity do ML Kit chegou ao binário de produção
porque `expo-dev-launcher` depende de `play-services-code-scanner` + `mlkit:barcode-scanning` para
ler o QR do menu de desenvolvimento.

## Causa

`expo-dev-client` declara `"debugOnly": true` no seu `expo-module.config.json` **apenas no bloco
`apple`**. O bloco `android` não tem o campo — o módulo é autolinkado em **toda** variante.

O gradle plugin do dev-launcher reforça a ilusão de que está tudo certo: ele checa a variante
(`DevLauncherPlugin.kt` → `if (!isDebugVariant(variant, reactExtension)) return`) e **não instrumenta**
classes fora de debug. Mas instrumentar é diferente de linkar: o AAR inteiro continua no APK/AAB.

Custo real no binário publicado: ML Kit, Compose, Koin, Apollo, okhttp, gson, commons-io, e o
manifest anunciando o deep link `exp+dosiq-app`.

## Por que nenhum gate pegou

Não é um bug de código — é **composição de dependências**. `tsc`, `eslint`, os testes e o
`strict-island.sh` operam sobre o JS/TS do projeto; nenhum deles enxerga o grafo do gradle. O
`expo-doctor` valida versões, não conteúdo do artefato. A informação só existe em dois lugares: no
AAB montado e no painel da loja depois do upload.

**A moral não é sobre o dev-client:** é que **o conteúdo do artefato de release é uma superfície sem
gate** neste repo. Toda dependência de desenvolvimento é candidata ao mesmo vazamento.

## Farol

- Pacote de desenvolvimento em `dependencies` (não `devDependencies`) num projeto Expo/RN.
- `expo-module.config.json` de uma dep com `debugOnly` em **um** bloco de plataforma só.
- Aviso da loja apontando classe de um pacote que você não chama.
- Permissão, Activity ou scheme no manifest de produção que ninguém no time reconhece.

## 🔴 A primeira tentativa de fix FALHOU — e o motivo é a parte mais útil deste AP

A tentativa inicial usou `expoAutolinking.exclude` no `settings.gradle`, escrito por um config
plugin. O `settings.gradle` gerado continha a linha correta, e o CLI de autolinking respeitava
`--exclude`. **O APK saiu com o dev-launcher dentro assim mesmo** — 260 referências a
`expo/modules/devlauncher` no `classes2.dex`, `GmsBarcodeScanningDelegateActivity` ainda no
manifest, modelos `.tflite` do ML Kit ainda empacotados.

**Causa: bug upstream no plugin gradle do Expo.** Em `AutolinkigCommandBuilder.kt:44-46`:

```kotlin
fun option(key: String, value: List<String>) = apply {
  optionsMap[key] = value.joinToString(" ")   // ← lista vira UMA string
}
```

A flag do CLI é variádica (`--exclude <exclude...>`). Recebendo um argumento único, o autolinking
procura por um módulo literalmente chamado
`"expo-dev-client expo-dev-launcher expo-dev-menu expo-dev-menu-interface"` — que não existe.
Exclui zero, sem erro, sem aviso.

Reprodução lado a lado:

```
--exclude "a b c d"         → 27 módulos, 4 dev   ← o que o gradle faz
--exclude a --exclude b …   → 23 módulos, 0 dev   ← o que foi testado
```

**A lição:** validar um mecanismo pela CLI e presumir que o build o invoca do mesmo jeito. O
`settings.gradle` estava certo, o CLI estava certo, e o produto estava errado — porque a ponte
entre os dois não era o que se supunha. Só a inspeção do artefato pegou ([[R-308]]).

Excluir um módulo só também não resolve: são resolvidos independentemente
(`--exclude expo-dev-client` → 26 módulos, 3 dev restantes).

## Fix que funciona (2026-07-30)

**1. Exclusão dos módulos — `apps/mobile/package.json`:**

```json
"expo": { "autolinking": { "android": { "exclude": [
  "expo-dev-client", "expo-dev-launcher", "expo-dev-menu", "expo-dev-menu-interface"
] } } }
```

O CLI lê o `package.json` diretamente (`parsePackageJsonOptions`), sem passar pelo builder
quebrado. Escopo `android` deliberado: o iOS não é afetado (28 módulos antes e depois) e lá o
`debugOnly` já resolve.

**Custo aceito pelo PO:** é estático — não há env var que condicione autolinking por perfil, então
vale também no dev build Android. `expo run:android` perde o dev launcher e o dev menu do Expo; o
dev menu do próprio React Native (reload, inspector) permanece. Nenhum script do repo usa
`--dev-client`, e o perfil `development` do `eas.json` não seta `developmentClient`.

**2. Scheme de dev — `apps/mobile/withoutDevSchemeOnRelease.js`:** o `exp+<slug>` NÃO vem do
autolinking (é do config plugin do dev-client) e por isso sobrevive à exclusão dos módulos. O
plugin o remove do manifest de release, abortando se o scheme `dosiq` não sobreviver.

## Verificação — use o gradle, não o CLI

A verificação pelo CLI **passa mesmo com o bug** e foi exatamente o que produziu o falso positivo.
A pergunta certa é o que o build monta:

```bash
cd apps/mobile/android && ./gradlew projects | grep -c "expo-dev-"   # tem que ser 0
```

Medido após o fix: 23 → **19 projetos**, nenhum `expo-dev-*`. Confirmação final no artefato:

```bash
unzip -p <apk> classes2.dex | strings | grep -c "expo/modules/devlauncher"   # tem que ser 0
```
