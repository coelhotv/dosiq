# AP-268 — `as any` em options de navigator sem validar o literal no union type do stack

**Domínio**: mobile_and_platform · **Descoberto**: 2026-07-06 (040 F5 lote 7, PR #723) · **Severidade**: média (comportamento de UI silenciosamente errado)

## Sintoma

Migração TS nível B encontra erro de tipo em options de navigator e desativa com cast:

```ts
// Navigation.tsx — JS stack (@react-navigation/stack)
options={{ presentation: 'fullScreenModal' as any }}  // BUG: JS stack não aceita 'fullScreenModal'
```

`'fullScreenModal'` só existe no union de `presentation` do **native-stack**. No JS stack o valor é ignorado/degrada em runtime — a tela não abre como fullscreen modal. O erro de tipo era um **bug real de runtime pré-existente**, e o `as any` o re-enterrou.

## Por que escapou

Stack JS (`@react-navigation/stack`) e native-stack (`@react-navigation/native-stack`) têm union types DIFERENTES para `presentation` (e outras options). Em sessão nível B "cast pra destravar" é o reflexo padrão — mas erro de tipo em **literal de configuração** (não em plumbing genérico) frequentemente é o compilador apontando valor inválido de verdade.

## Regra de prevenção

1. Antes de `as any` em options de navigator: conferir o union do navigator EM USO (JS stack vs native-stack) — hover no tipo ou olhar o `.d.ts`.
2. Se o literal não existe no union: é bug, não fricção de migração. Corrigir pro valor válido equivalente (`'fullScreenModal'` → `'modal'` no JS stack) no mesmo commit, com nota.
3. Classe geral: erro de tipo em **valor literal de config** merece 30s de verificação antes do cast — diferente de erro em generics/plumbing, onde `any` + TODO é aceitável em nível B.
