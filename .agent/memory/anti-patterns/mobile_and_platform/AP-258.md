# AP-258 — Read-modify-write concorrente em AsyncStorage sem serialização → clobber/perda

**Categoria:** mobile_and_platform · **Detectado:** review Gemini #700 (spec 042 Slice B, criticalAuditQueue)

## Sintoma
Fila persistida em AsyncStorage (JSON array). `flush()` lê `[A]`, `await insertOne(A)` (lento);
enquanto isso `enqueue(B)` lê `[A]`, grava `[A,B]`; `flush()` termina e grava os "remaining"
calculados sobre `[A]` (ex.: `[]`) → **B é sobrescrito e perdido**. Race clássica de read-modify-write
não-atômico: AsyncStorage não tem transação, e `async` intercala os passos read→modify→write.

## Por que passa despercebido
- Testes unitários rodam operações em série (sem intercalação) → verdes.
- Só aparece sob concorrência real (enqueue no headless durante flush no foreground, foreground durante
  drain). Um `flushInFlight` que só bloqueia flush REENTRANTE não cobre enqueue↔flush.

## Fix
Serializar TODA operação de RMW com um mutex simples (lock encadeado por promise):
```js
let lockChain = Promise.resolve()
function withLock(op) {
  const run = lockChain.then(op, op)
  lockChain = run.then(() => undefined, () => undefined) // corrente viva, sem propagar valor/erro
  return run
}
// enqueue/flush(read→process→write)/peek/clear TODOS sob withLock.
```
O enqueue concorrente espera o lock e anexa ao estado JÁ drenado. Manter flag de skip separada
(`flushInFlight`) se quiser evitar empilhar flushes (skip imediato antes do lock).

## Guard
- Toda estrutura persistida em AsyncStorage com read-modify-write e >1 produtor/consumidor concorrente
  DEVE serializar (mutex) ou usar operação atômica. Teste de regressão: enfileirar DURANTE um flush
  com insert pendente (deferred) e provar que o item sobrevive.
- Vale para qualquer store sem transação (AsyncStorage, arquivo JSON, localStorage sob workers).
