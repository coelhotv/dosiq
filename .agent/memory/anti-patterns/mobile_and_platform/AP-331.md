# AP-331 — "o app foi trazido pro topo" não é "o app está ativo": `top-sleeping` com a tela apagada

**Status:** active · **Layer:** warm · **Origem:** smoke da spec 067 Slice C (2026-08-19)
**Pack:** mobile_and_platform · **Relacionados:** [[AP-257]] · [[AP-327]] · [[R-309]]

## Sintoma

Trabalho agendado para rodar "quando o app voltar ao foreground" (drenar fila offline, sincronizar,
enviar telemetria) **não roda** depois de um alarme crítico — mesmo com o processo vivo e o app na
frente. A evidência chega distorcida: no dosiq, eventos enfileirados no disparo do alarme só viravam
linha no banco **16 minutos depois**, e como a linha só tinha `created_at`, a métrica de pontualidade
media *"quanto a paciente demorou a olhar o celular"* achando que media *"quanto o alarme atrasou"*.

## Causa

O full-screen intent do alarme **lança a Activity com a tela ainda apagada / o device bloqueado**.
O Android coloca o processo no topo, mas em estado `top-sleeping` — não há interação, a tela não
acordou. O `AppState` do React Native **nunca emite `active`**, então todo listener pendurado nele
fica parado.

Medido com `adb shell dumpsys activity processes`:

```
Proc # 0: fg  b/A/TPSL  -------  t: 0  15219:com.coelhotv.dosiq/u0a210 (top-sleeping)
    oom: max=1001 curRaw=0 setRaw=0 cur=0 set=0
mAwake=false  mScreenOnEarly=false  mScreenOnFully=false     (dumpsys window)
```

`fg` + `oom cur=0` enganam: parecem foreground pleno. O que decide é o sufixo **`(top-sleeping)`**.

## Por que engana o teste manual

O caso feliz esconde o defeito. Se o testador destravar o celular por qualquer motivo antes do
alarme — dar uma soneca, olhar uma notificação —, o processo já está `active` e a drenagem sai em
2-3 segundos. Foi exatamente o que aconteceu na primeira rodada do smoke 067 C (Δ 2s e 3s) e
sustentou a hipótese ERRADA de que o problema só existiria com o app morto pela otimização de
bateria. A condição real é a **mais comum de todas**: silenciar o alarme e voltar a dormir.

## Correção

1. **Não amarre correção de dado à volta ao foreground.** Carimbe o instante **na origem**, onde o
   fato acontece (o handler headless), e trate o momento da gravação como outra coisa —
   coluna separada, nunca o mesmo campo ([[R-299]]: fato datado carrega seus atributos).
2. Se o trabalho **precisa** rodar no foreground, aceite que ele pode demorar horas e projete para
   isso (fila persistente com cap, idempotência, item sai só após confirmação).
3. **Valide no estado certo:** device **bloqueado**, alarme tocando, sem destravar. Destravar para
   "conferir se funcionou" destrói o estado sob teste.

## Detecção

```bash
adb shell dumpsys activity processes | grep -A1 "<pacote>"   # procure por (top-sleeping)
adb shell dumpsys window | grep -E "mAwake|mScreenOnFully"   # false = tela apagada
adb exec-out run-as <pacote> cat databases/RKStorage > /tmp/RK  # inspecionar a fila ANTES do flush
sqlite3 /tmp/RK "select value from catalystLocalStorage where key='<chave da fila>'"
```

Ler a fila enquanto o item ainda está nela é a prova direta de que o dado existe e o transporte é
que está esperando — separa "não capturou" de "não drenou", que a linha no banco sozinha não separa.
