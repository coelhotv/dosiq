# AP-323 — `navigationRef.addListener('state', ...)` anexado fora da árvore nunca dispara se montar antes do `NavigationContainer`

**Achado:** smoke do PR 1.5b (kill switch de versão mínima, spec 051-A), 2026-07-26.

## O que aconteceu

`useAlarmScreenActive` (hook que faz o `VersionGateOverlay` ceder o topo da tela quando o alarme
full-screen está ativo — obrigação clínica > bloqueio de update) usava
`navigationRef.addListener('state', check)`. No smoke, o alarme disparava, a navegação para
`AlarmFullScreen` acontecia de verdade (confirmado por log), mas o overlay nunca soube — ficou
preso por cima do alarme pra sempre.

Causa: `VersionGateOverlay` monta como **sibling** de `NavigationTree` dentro de `Navigation.tsx`,
e `NavigationTree` só monta o `NavigationContainer` de verdade **depois** que `session` resolve
(antes disso retorna um spinner). O `useEffect` do overlay roda ANTES desse ponto — o
`navigationRef` ainda não tem contêiner nenhum para anexar o listener. Quando o container
finalmente monta e navega, não existe listener pendurado nele: o evento não tem para onde ir.

## Por que passou despercebido

Nenhum teste unitário cobre timing de montagem entre dois componentes irmãos independentes —
é exatamente o tipo de acoplamento invisível a `tsc`/lint/jest de componente isolado. Só apareceu
com dispositivo real, e só na 2ª rodada de smoke (usando soneca do notifee pra redisparar o
alerta): a 1ª tentativa (alarme direto com app minimizado) mostrou "não abre a tela cheia", que
por si só já apontava para outro bug pré-existente (retry de `navigationRef.isReady()` ausente em
`AlarmSchedulerBridge`); só depois de corrigir ESSE, a segunda tentativa expôs que o overlay
continuava preso, revelando o bug **introduzido por este próprio fix** (ver R-304 — 2ª tentativa
falha no mesmo sintoma pede busca em memória antes do 3º round; aqui não havia memória prévia,
por isso o AP nasce agora).

## Fix

Trocar `addListener` por **polling** (`setInterval` de 250ms lendo `isReady()`/`getCurrentRoute()`).
Polling não depende de QUANDO o container fica pronto — só lê o estado atual a cada tick, correto
em qualquer ordem de montagem entre os dois componentes irmãos.

```ts
// packages/../useAlarmScreenActive.ts
useEffect(() => {
  function check() {
    const current = navigationRef.isReady() ? navigationRef.getCurrentRoute()?.name : undefined
    setActive(current === ROUTES.ALARM_FULLSCREEN)
  }
  check()
  const interval = setInterval(check, 250)
  return () => clearInterval(interval)
}, [])
```

## Farol (quando desconfiar)

- Qualquer hook/componente que **monta fora da árvore do `NavigationContainer`** (overlay global,
  guard de boot, splash condicional) e usa `navigationRef.addListener(...)` para reagir a navegação.
- Navegação **de fato acontece** (log/estado confirmam) mas um efeito colateral que depende dela
  **nunca reage** — sintoma de listener anexado a um alvo que ainda não existia no momento do anexo.
- Regra geral: **listener de evento assume que o emissor já existe quando o listener é registrado**;
  se o emissor pode nascer depois (montagem condicional/assíncrona), poll o estado atual em vez de
  esperar o evento — funciona independente de ordem.
