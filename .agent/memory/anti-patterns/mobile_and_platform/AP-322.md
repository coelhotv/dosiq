# AP-322 — `?? []` na fronteira hook→tela apaga a distinção null (erro) vs [] (sucesso vazio)

**Domínio:** mobile_and_platform · **Registrado:** 2026-07-26 (spec 055/051-A, smoke do PR 1.5b kill switch)
**Regra derivada:** nenhuma nova ainda (candidato a promoção se recorrer) · **Família:** [[AP-321]] (mesmo smoke, mesma classe de "estado de erro engolido")

## O que aconteceu

Smoke do kill switch (spec 055): em modo avião, num app com tratamentos reais cadastrados, a aba
"Tratamentos" mostrou o **empty state** ("você não tem tratamentos") em vez de qualquer mensagem
de erro/conexão — mesmo com `state.error` corretamente populado pelo hook.

Mecanismo, em `apps/mobile/src/features/treatments/hooks/useTreatments.ts:59`:

```js
groups: transformed.groups ?? [],
```

`_treatmentsTransformer.ts` foi desenhado com cuidado pra preservar a distinção:
`transformTreatments(null)` → `{ groups: null, ... }` (sem dado — veio de erro sem fallback);
`transformTreatments([])` → `{ groups: [], ... }` (sucesso real, zero tratamentos). A tela
(`TreatmentsScreen.tsx:192`) depende exatamente dessa distinção: `if (state.error && !state.groups)`
mostra `ErrorState`; senão cai no conteúdo normal, onde `isEmpty` decide entre lista e `EmptyState`.

O `?? []` no memo do hook (linha 59) coalescia `null` pra `[]` bem na fronteira hook→tela — depois
disso, `!state.groups` é sempre `false` (array vazio é truthy), o branch de erro nunca dispara, e
a UI cai silenciosamente no empty state mesmo com erro real e dado real perdido.

Comparação: `useTodayData.ts` (aba "Hoje") **não** faz esse coalescing equivalente antes da
checagem de erro da tela — por isso "Hoje" mostrava o banner de stale/offline corretamente,
enquanto "Tratamentos", com a MESMA classe de bug de conectividade, mostrava vazio.

## Por que a classe é perigosa

- `[]` e `null` são ambos "falsy-ish" pra quem não presta atenção (`!groups` funciona pra ambos
  em JS puro), mas representam fatos **opostos**: "não sei se você tem dados" vs "você não tem
  dados". Um `??`/`||` colocado no lugar errado apaga essa oposição sem nenhum erro de tipo,
  nenhum teste quebrado (os testes de tela mockavam `useTreatments` diretamente, pulando por cima
  da linha que tinha o bug).
- É silencioso justamente na pior combinação: usuário real com dados reais, sem rede — a tela
  mente que ele nunca cadastrou nada, quando na verdade só não conseguiu carregar.
- Passa despercebido em dev porque cache e rede quase sempre estão disponíveis; só aparece na
  combinação exata (rede fora + sem cache válido) que só se testa em device real, em avião.

## Como pegar / evitar

- **Nunca usar `?? []`/`|| []` pra "normalizar" um valor que alimenta uma checagem de
  null-vs-empty rio abaixo.** Se uma tela distingue `null` (erro) de `[]` (vazio real), TODO
  ponto entre a fonte do dado e a tela tem que preservar essa distinção — não só o transformer,
  também o memo/shape que expõe pro componente.
- **Grep de sinal**: `transformed.<campo> ?? []` (ou `|| []`) logo antes de expor pro
  componente, quando o transformer devolve `null` de propósito em algum caso — é quase sempre bug.
- **Teste de hook, não só de tela**: `TreatmentsScreen.test.tsx` mockava `useTreatments()` inteiro
  e por isso nunca exercitava a linha 59 real — faltava um teste do HOOK em si (`data=null` após
  erro → `result.groups` deve ser `null`, não `[]`). Gap de cobertura registrado, ainda aberto.
- Ao revisar qualquer hook offline-first com padrão `try (rede) → catch (cache) → setError`,
  conferir a cadeia completa até o componente: transformer → shape exposto pelo hook → condição
  de renderização na tela. Uma auditoria que só olha um dos três elos erra.
