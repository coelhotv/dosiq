## Anti-Pattern

Componente que carrega dados async e alimenta um hook com side effect destrutivo
sofre race condition no mount:

1. Estado inicial é `[]` (array vazio) ou equivalente "sem dados"
2. Valor derivado (`hasCriticalProtocol = protocols.some(...)`) é imediatamente `false`
3. Hook com side effect (`useAlarmScheduler({ isAlarmEnabled: false })`) executa **antes** de `load()` completar
4. Side effect destrutivo (`cancelAll()`) dispara com base em dado incorreto
5. `load()` termina e popula o estado correto — mas os alarmes já foram cancelados

**Sintoma real (sprint-010):** ao retornar do background (AppState change → `active`),
o `AlarmSchedulerBridge` montava com `protocols = []` → `hasCriticalProtocol = false`
→ `useAlarmScheduler` chamava `cancelAll()` antes de `load()` devolver os protocolos
reais → alarmes apagados, nunca reagendados.

## Fix

Gate o hook destrutivo em sub-componente renderizado condicionalmente apenas
após o primeiro load bem-sucedido. Ver R-266 para o padrão completo.

```jsx
// ❌ BUG
export default function Bridge() {
  const [protocols, setProtocols] = useState([])
  const hasCritical = protocols.some(p => p.critical_alarm)
  // executa imediatamente com hasCritical=false → cancelAll
  useAlarmScheduler({ isAlarmEnabled: hasCritical, ... })
  return null
}

// ✅ FIX — gate via sub-componente + loaded state
export default function Bridge() {
  const [protocols, setProtocols] = useState([])
  const [loaded, setLoaded] = useState(!userId)  // derived state
  const hasCritical = protocols.some(p => p.critical_alarm)
  // load() chama setLoaded(true) ao terminar
  return loaded ? <Scheduler isAlarmEnabled={hasCritical} ... /> : null
}

function Scheduler({ isAlarmEnabled, ... }) {
  useAlarmScheduler({ isAlarmEnabled, ... })
  return null
}
```

## Diagnóstico

Sintoma visível: console mostra `[alarmService] cancelAll` logo após `load()`
sem nenhum `scheduleAlarm` após ele — alarmes não reagendados.
