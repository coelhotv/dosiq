## Sintoma

Após editar `targets/dose-activity/DoseActivityAttributes.swift` (ex.: adicionar campo
`scheduledTime`) e rodar `npx expo run:ios` (build incremental), a Live Activity **some
por completo** — nem aparece na Dynamic Island / Lock Screen. Build compila e roda sem erro.

## Causa raiz

`DoseActivityAttributes` precisa de **dupla membership** (ActivityKit casa por TIPO — app e
widget têm de compilar a MESMA struct). As duas builds pegam o arquivo de lugares com
**cadências de atualização diferentes**:

- **Widget target** (@bacons/apple-targets): synchronized folder → `targets/dose-activity/`.
  **Sempre fresco** (referência viva à pasta).
- **App target**: uma **CÓPIA** em `ios/DoseActivityRN/`, feita pelo `withDangerousMod` do
  `withDoseActivityBridge.js` — só roda no **prebuild**.

`expo run:ios` incremental **não re-roda o prebuild** → a cópia app-side fica VELHA. Resultado:
widget compila com a struct NOVA (com `scheduledTime`), app com a struct VELHA (sem). O app cria
a Activity com o layout antigo; o widget tenta decodificar esperando o campo novo → **Codable
falha → render vazio → DI some**. (Como `DoseActivityBridge.swift` também é copiado, o app-side
fica internamente consistente na versão velha — por isso compila sem erro e mascara o split-brain.)

## Fix

**Imediato:** regenerar as cópias app-side antes de buildar:
```bash
cd apps/mobile && rm -rf ios && npx expo prebuild -p ios && npx expo run:ios --no-bundler
```
`build-ios.sh` já faz `rm -rf ios` + prebuild — por isso o bug NÃO aparece via script, só no
`expo run:ios` direto.

## Corolário (mudança de SHAPE de ActivityAttributes/ContentState)

`Activity.update()` só troca o ContentState — **NÃO migra os Attributes** (fixos no `.request`).
Uma Activity criada por um build com shape ANTIGO continua viva (persistida pelo SO); quando o
build novo só faz `update()` nela (ex.: transição `later→upcoming` da mesma dose), o widget novo
decodifica os campos novos como vazios → render parcial (só o ícone, que usa `state`+`scheduledAt`
comuns aos dois shapes; nome/dose/botões somem). Não basta clean prebuild: tem que **ENCERRAR e
RECRIAR** as Activities vivas. No simulador: `xcrun simctl uninstall booted <bundleId>` (mata
Activities persistidas) + clean prebuild + reinstalar → no relaunch o bridge faz `start` (shape novo),
não `update`. Detectado smoke 039/F3 (2026-06-29).

## Regra

Qualquer edição em arquivo de **dupla membership** (`targets/dose-activity/*.swift` que também é
copiado p/ o app por `withDoseActivityBridge`, ou `ios-native/*.swift`) → **clean prebuild
obrigatório** antes do build (`rm -rf ios` ou `expo prebuild --clean`). Nunca confiar no
incremental do `expo run:ios` p/ propagar mudança de contrato nativo da Live Activity. Mudança no
SHAPE de ActivityAttributes/ContentState é especialmente perigosa (silenciosa: compila, some em runtime).

**Corolário 2 — App Intents (`Button(intent:)` na ilha/lock) exigem dupla membership PRÓPRIA
(smoke 039/F3, 2026-06-29):** `LiveActivityIntent` roda no **processo do APP** (doc Apple), não no
widget. O tipo do intent (`DoseActivityIntents.swift`) precisa compilar no **app target** também —
não basta estar no `targets/` (widget). Sintoma do esquecimento: o botão renderiza mas o toque é
**no-op total** (app nem abre, `perform()` nunca roda, fila do App Group vazia). O widget tinha
`Metadata.appintents`, o app NÃO → o sistema não despacha o intent in-process. Fix: adicionar
`targets/dose-activity/DoseActivityIntents.swift` ao `APP_SOURCES` do `withDoseActivityBridge.js`
(copiado p/ `ios/DoseActivityRN/` + `addSourceFile` no app target). Diagnóstico decisivo: `find` por
`DoseActivityIntents.o` sob `Dosiq.build` (app) vs só `DoseActivity.build` (widget); e ausência de
`Dosiq.app/Metadata.appintents`. **Armadilha de timing:** editar o plugin SEM novo clean prebuild
deixa o `ios/` no disco velho (sem a cópia) — verificar `ls ios/DoseActivityRN/DoseActivityIntents.swift`
+ `grep -c DoseActivityIntents.swift ios/*.xcodeproj/project.pbxproj` ANTES de buildar.
