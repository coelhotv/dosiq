# [AP-155] Unsafe `Intl` Usage in Module Scope (Legacy Android/Hermes)

## Description
Accessing `Intl` APIs (like `Intl.DateTimeFormat`) at the module scope (top-level) can cause silent crashes or initialization failures on legacy Android devices (API 24/25) using the Hermes engine, especially when system resources are low or regional support is missing.

## Why it's harmful
- **Crash at Load Time**: If `Intl` fails to initialize, the entire module fails to load, often leading to a white screen or silent app death.
- **Hermes Limitations**: The Hermes engine's implementation of `Intl` is more sensitive to environment state than V8.

## Correct Approach
Always wrap `Intl` calls in `try/catch` and provide a fallback (e.g., hardcoded 24h/12h format or simple string manipulation). Move the check inside a hook or a lazy-evaluated constant.

## Example
### ❌ Wrong
```javascript
const IS_24H = new Intl.DateTimeFormat(undefined, { hour: 'numeric' })
  .resolvedOptions().hour12 === false;
```

### ✅ Right
```javascript
let IS_24H = true;
try {
  IS_24H = new Intl.DateTimeFormat(undefined, { hour: 'numeric' })
    .resolvedOptions().hour12 === false;
} catch (e) {
  console.warn('[Intl] Fallback to 24h format');
}
```
