# AP-207 — Listener do expo-notifications captura o press da notif do Notifee → navega errado

**Layer:** warm · **Status:** active · **Pack:** mobile_and_platform / notifications
**Detectado:** Spec 001 (Alarme Nativo), smoke Android, 2026-06-03

## Sintoma

Ao tocar "Tomei" na tela cheia do alarme (ou no corpo da notif), crash:

```
The action 'NAVIGATE' with payload {"name":"Hoje","params":{}} was not handled
by any navigator. Do you have a screen named 'Hoje'?
```

## Causa

No Android, Notifee e expo-notifications compartilham o sistema de notificação do
SO. O `Notifications.addNotificationResponseReceivedListener` (expo) **captura o
press da notificação do Notifee** (alarme). Esse handler chamava
`navigateFromPush(data?.navigation)` → para o alarme, `navigation` é `undefined`
→ o fallback `?? ROUTES.TODAY` forçava `navigationRef.navigate('Hoje')` no **root**.
`'Hoje'` (TODAY) é aninhado em `TABS` → navegar por ele no root **não resolve** →
crash. Payload `{"name":"Hoje","params":{}}` é a assinatura exata.

## Fix

Distinguir o alarme (tem `doseInstanceId` no `data`) e **não navegar** — o press
do alarme é tratado por outro handler (`AlarmSchedulerBridge`):

```js
function navigateFromPush(data) {
  if (!data || data.doseInstanceId) return // alarme Notifee — ignora
  // ... fallback TODAY só p/ push real (sem doseInstanceId)
}
```

Passar o `data` COMPLETO (não só `.navigation`) p/ o guard poder checar
`doseInstanceId`.

## Lição

Dois sistemas de notificação no mesmo SO → os listeners de um podem receber
eventos do outro. Todo handler de press deve **identificar a origem** (campo
discriminante no `data`) antes de agir. Rota aninhada nunca deve ser alvo de
`navigate()` no root sem `{ screen }`.
