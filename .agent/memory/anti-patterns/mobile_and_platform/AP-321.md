# AP-321 — Erro cru (rede/JS, em inglês) vaza pra UI quando o fallback offline não tem info própria

**Domínio:** mobile_and_platform · **Registrado:** 2026-07-26 (spec 055/051-A, smoke do PR 1.5b kill switch)
**Regra derivada:** nenhuma nova (reforça o espírito de [[AP-314]] — precedência de erro, não vazamento) · **Família:** offline-first, mensagens de erro

## O que aconteceu

No smoke do kill switch (spec 055), testando modo avião num app recém-instalado (sem cache salvo
ainda), a aba "Hoje" mostrou brevemente uma mensagem de erro **em inglês** antes de estabilizar.

Mecanismo, em `packages/core/src/utils/loadFailure.ts` (`describeLoadFailure`): o padrão
offline-first do projeto é "tenta rede → falhou, tenta cache → cache ausente/velho → mostra erro".
Quando o hook (`useTodayData.ts`, `useTreatments.ts`, `useStock.ts`) **não tem cache pra tentar**
(1ª abertura do app), ele relançava o **próprio erro original** (`if (!cached) throw originalErr`)
— e em modo avião esse erro é um `TypeError` de fetch nativo do React Native
(`"Network request failed"`), **sempre em inglês**, nunca traduzido. `describeLoadFailure` não
distinguia "fallback com motivo próprio" (`new Error('Cache expirado...')`, PT, intencional) de
"fallback que só relançou o erro original tal-e-qual" — em ambos os casos usava `.message` cru.

Achado secundário no mesmo smoke: `StockScreen.tsx` **ignorava completamente** o `error` real do
hook e mostrava uma string hardcoded (`"Não foi possível carregar seu estoque."`) — ou seja, mesmo
corrigindo a mensagem no hook, a tela nunca a exibiria.

Achado terciário: as mensagens de "cache expirado" usavam jargão técnico ("Cache expirado (> 24h)")
que a persona Dona Maria não entende.

## Por que a classe é perigosa

- O ponto de falha (rede indisponível) é justamente onde o usuário mais precisa de uma mensagem
  clara em português — é o pior momento pra mostrar texto que ele não entende.
- Passa despercebido em CI/teste porque a mensagem em si não quebra nada (não é um erro de tipo,
  não falha asserção nenhuma) — só aparece em device real, sem rede, sem cache prévio. Uma
  combinação de estado (1ª abertura + offline) fácil de nunca reproduzir em ambiente de dev com
  wifi sempre ligado e cache sempre presente de sessões anteriores.
- Uma tela pode calcular a mensagem certa no hook e mesmo assim mostrar outra coisa (hardcoded),
  porque nada garante que o componente realmente RENDERIZA o `error` que o hook expõe.

## Como pegar / evitar

- **Nunca relançar o erro original cru como fallback "sem info"**: se o hook não tem cache pra
  tentar, lance uma mensagem PRÓPRIA, em PT (`useTodayData.ts`/`useTreatments.ts`/`useStock.ts`
  agora lançam: *"Não identificamos conexão com a Internet, nem dados salvos neste aparelho.
  Conecte-se a rede para continuar."*).
- **Defesa em profundidade no util compartilhado**: `describeLoadFailure` só confia na mensagem
  do fallback quando `fallbackErr !== originalErr` (identidade de objeto, não heurística de
  string) — se for o mesmo objeto relançado, não há informação nova, cai sempre no
  `defaultMessage` (parametrizável por chamador, sempre em PT).
- **Grep por mensagem hardcoded que ignora o `error` real do hook**: `<ErrorState message="texto fixo" .../>` quando o componente já desestrutura um `error` do hook é sinal de que a tela não está escutando o estado real — trocar por `message={error}`.
- **Nunca usar jargão técnico** ("cache", "fetch", "parse") em texto voltado ao usuário — a
  persona (Dona Maria) não sabe o que essas palavras significam; descrever o efeito observável
  ("dados desatualizados", "sem conexão"), não o mecanismo interno.
- Teste de regressão em `packages/core/src/utils/__tests__/loadFailure.test.ts` fixa o caso
  `fallbackErr === originalErr` explicitamente — não basta o `TypeError` genérico, precisa ser o
  MESMO objeto pra reproduzir o rethrow puro.
