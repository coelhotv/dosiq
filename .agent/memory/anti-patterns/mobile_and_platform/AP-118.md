# AP-118 — Repository INSERT não espelhando campos do dispatcher/schema após adição tardia

## Problema

`dispatchNotification.js` passou `treatment_plan_id` e `treatment_plan_name` corretamente. O schema Zod (`notificationLogSchema`) aceitava os campos. Mas `notificationLogRepository.js` não os incluía no INSERT — os dados eram silenciosamente descartados no banco.

Resultado: `notification_log.treatment_plan_name` ficava `null` para todos os registros de plano, mesmo após a migration e o dispatcher estarem corretos.

## Por que acontece

O fluxo de dados cruza três arquivos distintos (schema → dispatcher → repository). Ao adicionar um campo novo, é fácil atualizar dois dos três e esquecer o terceiro — especialmente o repository, que é o único com SQL explícito.

## Exemplo problemático

```js
// dispatchNotification.js — correto, passa o campo
{ treatment_plan_id: data.planId, treatment_plan_name: data.planName }

// notificationLogSchema.js — correto, valida o campo
treatment_plan_name: z.string().nullable().optional()

// notificationLogRepository.js — ESQUECIDO, campo não incluído
const { error } = await supabase.from('notification_log').insert({
  user_id:           parsed.data.user_id,
  notification_type: parsed.data.notification_type,
  // treatment_plan_id e treatment_plan_name ausentes!
})
```

## Solução

Ao adicionar qualquer campo novo ao schema de notificação, seguir o checklist de três pontos:
1. Schema Zod (`notificationLogSchema.js`)
2. Dispatcher (`dispatchNotification.js`)
3. **Repository INSERT** (`notificationLogRepository.js`) ← mais esquecido

**Why:** Incident em N1.8: Central de Avisos exibia "Plano de tratamento" genérico em vez do nome real, mesmo após PR #504 que corrigia dispatcher e schema.
**How to apply:** Sempre que adicionar campo ao `notificationLogSchema`, fazer grep por `notificationLogRepository` e verificar que o INSERT inclui o campo novo.
