# AP-288 — Sob edge-to-edge, `KeyboardAvoidingView` sem `behavior` no Android é no-op

**Classe:** plataforma / layout
**Detectado em:** smoke do PO da spec 044 F4b (tela "Estoque inicial" — teclado cobria a lista e o rodapé)

## Sintoma

Teclado sobe e fica POR CIMA dos inputs e do rodapé. A lista não rola para "levantar" os itens de
baixo — eles ficam inalcançáveis enquanto o teclado está aberto.

## Mecanismo

O app roda com `edgeToEdgeEnabled: true` (`app.config.js` / `expo.edgeToEdgeEnabled=true`). Sob
edge-to-edge, **o Android deixa de redimensionar a janela** quando o teclado aparece — o app
desenha atrás das barras do sistema. Consequência: o `android:windowSoftInputMode="adjustResize"`
do `AndroidManifest` **vira letra morta**.

E é justamente nesse resize que um `KeyboardAvoidingView` com `behavior={undefined}` confia. Sem
resize, ele não faz nada: é um componente montado, com aparência de proteção, que não protege.

```jsx
// ARMADILHA — o padrão "só iOS precisa de behavior" nasceu antes do edge-to-edge
behavior={Platform.OS === 'ios' ? 'padding' : undefined}   // ❌ no-op no Android

// CERTO
behavior={Platform.OS === 'ios' ? 'padding' : 'height'}    // ✅
```

## Regras que caem junto

1. **`keyboardVerticalOffset` não é constante mágica.** O `60` visto nos formulários compensa a
   altura de um header de NAVEGAÇÃO. Tela com AppBar próprio (dentro da SafeAreaView) usa `0` —
   copiar o 60 descola o rodapé do teclado.
2. **Rodapé fixo fica DENTRO do KAV**, junto com a lista. Fora dele, o teclado o cobre igual.
3. **`ScrollView` dentro do KAV precisa de `flex: 1` no `style`** (não só `flexGrow` no
   `contentContainerStyle`): sem isso ele cresce com o conteúdo e empurra o rodapé para fora da
   tela — a lista fica ok e os botões somem.
4. **Safe area inferior é condicional ao teclado.** Com o teclado ABERTO essa faixa não existe (o
   teclado ocupa o lugar dela); manter o inset deixa o rodapé boiando. Usar
   `useKeyboardVisible()` (`@shared/hooks`) e aplicar `insets.bottom` só com o teclado fechado —
   e NÃO declarar `edges={['bottom']}` na SafeAreaView, que reservaria a faixa sempre.

## Farol

Qualquer tela nova com input + rodapé fixo. E, ao copiar um padrão de teclado de outra tela,
verificar se a tela-modelo é uma que **realmente** convive com teclado no dia a dia
(`ChatScreen`, `DoseRegisterModal` — ambas usam `'height'`) e não uma que "parece funcionar"
porque o formulário é curto e o campo em foco calha de ficar acima do teclado.

## Dívida conhecida (não corrigida na 044)

Usam `behavior={undefined}` no Android e provavelmente têm o mesmo bug latente:
`ProtocolFormScreen`, `DeleteAccountScreen`, `MedicineAnvisaSheet`, `MedicineSelectorSheet`.
Varrer numa task própria — não foi tocado aqui para não inchar o PR da F4b.

## 2ª incidência (055 PR 1.4, 2026-07-24) — promovida a [[R-303]]

Reintroduzido do zero em 4 telas NOVAS (`MedicineFormScreen`, `FeedbackScreen`,
`ProfileEditScreen`, `ChangePasswordScreen`) antes de achar este AP na memória — o agente
copiou `keyboardVerticalOffset={60}` de tela vizinha sem medir (regra 1 abaixo já avisava) e
levou 3 rounds de screenshot com o PO pra diagnosticar (vão morto iOS por offset chutado →
regressão Android por zerar inset sem `behavior='height'` → fix correto). Custo: ~40min de
ida-e-volta que a busca em memória ANTES de codar teria evitado. Regra dura em [[R-303]] —
checklist obrigatório pra toda tela nova com form+rodapé fixo, farol pra RC5/RC6.
