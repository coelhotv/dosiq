# AP-280 — `getNow()` (relógio deslocado p/ o fuso) em cálculo de DURAÇÃO contra timestamptz

**Classe**: date-time / falso-verde dependente do fuso do runner
**Detectado**: 2026-07-11 (spec 044 F2, T004 — gap de reativação do estoque). Quebrou só no CI.
**Status**: active · layer: warm (pack `date-time`)

## Sintoma

`computeStockPauseGapDays` usava `getNow()` como "agora" e subtraía de `stock_paused_at`
(timestamptz **absoluto**). Um congelamento de exatamente 29 dias virava **28** em runner UTC
e **29** em máquina GMT-3 → suíte verde local, vermelha no CI (`expected 28 to be 29`).

## Mecanismo

`getNow()` NÃO devolve o instante atual: devolve o relógio **deslocado** para o fuso do usuário
(é a ferramenta certa para derivar "que DIA é hoje para o usuário"). Subtrair um instante
absoluto de um relógio deslocado subtrai junto o **offset do fuso** (−3h em GMT-3):
`29d 0h − 3h = 28d 21h → floor = 28`. O erro é silencioso e muda de sinal com o fuso do host.

## Regra

Separar as duas perguntas:
- **Duração física** ("há quanto tempo isso aconteceu", TTL, gap, idade de um registro) →
  instante absoluto (`Date.now()` / `.getTime()`) dos DOIS lados. Fuso é irrelevante.
- **Diferença de calendário** ("quantos dias-calendário do usuário", vira-dia, "hoje") →
  `getNow()`/`parseLocalDate` no fuso do usuário (R-020/ADR-049).

Misturar as duas famílias no mesmo subtraendo é sempre bug. Sintoma-farol: **teste de tempo que
passa local e falha no CI** — rodar `TZ=UTC` antes do push quando o cálculo envolve tempo.

Nota: `new Date()` é proibido pelo lint (R-020) — para o instante absoluto use `Date.now()`.

instante absoluto com relógio local.
