# AP-227 — `CREATE OR REPLACE FUNCTION` com +param cria overload órfão

**Categoria:** data_and_schema
**Detectado:** 012 Fase B4 (smoke, 2026-06-14)
**Relaciona:** AP-221 (drift de assinatura de RPC / PGRST202)

## Sintoma

Após `CREATE OR REPLACE FUNCTION foo(...)` numa migração que **adiciona um parâmetro**
(mesmo com `DEFAULT`), a função antiga continua existindo. Postgres identifica funções
por **nome + tipos dos argumentos** — uma assinatura diferente é uma função **nova**
(overload), não uma substituição. Resultado:

- `PGRST203` (PostgREST não consegue desambiguar a chamada entre as N sobrecargas), ou
- a chamada resolve para a **versão antiga** (sem a lógica nova) silenciosamente.

## Caso real (B4)

`create_purchase_with_stock` ganhou `p_injection_container text DEFAULT NULL`. O
`CREATE OR REPLACE` criou a 9-arg, mas a 8-arg sobreviveu:

```
p_medicine_id, p_quantity, p_unit_price, p_purchase_date, p_expiration_date, p_pharmacy, p_laboratory, p_notes              -- antiga (órfã)
p_medicine_id, ..., p_notes, p_injection_container                                                                          -- nova
```

## Fix

1. **DROP explícito da assinatura antiga ANTES do CREATE:**
   ```sql
   DROP FUNCTION IF EXISTS public.create_purchase_with_stock(
     uuid, numeric, numeric, date, date, text, text, text
   );
   CREATE OR REPLACE FUNCTION public.create_purchase_with_stock(... , p_injection_container text DEFAULT NULL) ...
   ```
2. **Verificar pós-migração** que só resta a assinatura nova:
   ```sql
   SELECT pg_get_function_identity_arguments(p.oid)
   FROM pg_proc p JOIN pg_namespace n ON n.oid=p.pronamespace
   WHERE n.nspname='public' AND p.proname='<fn>';
   ```
3. Incluir o DROP no arquivo de migração versionado (idempotência/replay).

## Prevenção

Sempre que uma migração **muda a aridade** de uma função (add/remove param), tratar como
recriação: DROP da(s) assinatura(s) antiga(s) + CREATE. `CREATE OR REPLACE` só substitui
quando a assinatura é **idêntica**.
