# [AP-159] Delete de entidade pai sem pre-check de dependências FK deixa órfãos no banco

## Sintoma
Tela de detalhe de uma entidade (ex: Medicamento) oferece botão "Apagar" → confirma → executa `DELETE FROM medicines WHERE id = ?`. Se a entidade tem FKs em outras tabelas (`protocols.medicine_id`, `stock.medicine_id`):
- Se o constraint é `ON DELETE CASCADE`: silenciosamente apaga tratamentos e estoque (dados de saúde críticos!).
- Se é `ON DELETE RESTRICT`: PostgreSQL lança FK violation e o usuário vê um erro técnico genérico no Toast.
- Se é `ON DELETE SET NULL`: cria órfãos com `medicine_id = NULL` (dados inconsistentes).

Em nenhum dos 3 casos o usuário entende o impacto antes de confirmar.

## Solução correta (hard block)
Antes de oferecer confirmação de delete, calcular `preCheck`:
```javascript
const preCheck = useMemo(() => {
  const protocols = Array.isArray(medicine?.protocols) ? medicine.protocols : []
  const stock = Array.isArray(medicine?.stock) ? medicine.stock : []
  const stockUnits = stock.reduce((acc, s) => acc + (Number(s?.quantity) || 0), 0)
  const hasDependencies = protocols.length > 0 || stockUnits > 0
  return { canDelete: !hasDependencies, protocols, stockUnits }
}, [medicine])
```

- Se `!canDelete`: abrir bottom sheet `XDeleteBlockedSheet` listando dependências e CTAs para resolver ("Abrir tratamentos", "Zerar estoque") em vez de confirmar delete.
- Se `canDelete`: oferecer confirmação normal.

Pre-check inclui dependências **ativas E inativas** — tratamento pausado (`active=false`) com `medicine_id` referente ainda é dado órfão se medicamento for apagado.

## Quando relaxar
- Soft delete (`deleted_at` timestamp) sem cascade pode ser viável, mas deve marcar dependências também (raramente vale o esforço para v1).
- Permitir delete cascade SÓ se há UX explícita "Isto também apagará: 3 tratamentos, 12 doses registradas. Continuar?" — alto risco de cliques acidentais, recomendado HARD block.

## Por que matérias da saúde são especiais
Diferente de "apagar uma foto", apagar medicamento em sistema de aderência:
- Tratamentos órfãos = perda de histórico de adesão (auditoria zero)
- Estoque órfão = inconsistência de inventário
- Doses logadas órfãs = histórico médico quebrado

UX correta: **bloqueio HARD**, não warning leve.
