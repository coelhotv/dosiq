# AP-311 — Vínculo entre entidades guardado numa linha filha opcional: apagar a linha "sorteada" orfana o conjunto

**Status:** active · **Layer:** hot · **Domain:** data_and_schema
**Criado:** 2026-07-20 (smoke do PO na 029/052) · **trigger_count:** 1

## Sintoma

A relação entre A (tratamento) e B (escada) não vive em A nem em B: vive num campo opcional das
**linhas filhas** de B (`titration_steps.protocol_id`). Só algumas linhas o carregam. A leitura faz:

```js
// acha QUALQUER filha com o vínculo → descobre o pai
const link = await db.from('titration_steps').select('titration_id').eq('protocol_id', id).limit(1).maybeSingle()
if (!link) return []        // ← "não existe escada"
```

Apagar as linhas filhas erradas — sem tocar em A nem em B — **destrói a relação**. O conjunto
continua íntegro no banco e some da tela.

## Por que é pior do que parece

**A falha é silenciosa e se disfarça de estado legítimo.** `[]` é indistinguível de "não há escada":
não há erro, não há log, nenhum gate acusa. Para o usuário, "apaguei duas etapas futuras" produziu
"perdi meu tratamento inteiro" — e, do ponto de vista dele, o app apagou dado clínico.

Medido em prod (2026-07-20): **6 de 15 etapas sem `protocol_id`; 1 das 4 vigentes sem**. A escada do
smoke tinha o vínculo em UMA linha, e ela estava no sufixo editável — a parte que o usuário pode
apagar. Não era caso raro: era a configuração normal.

## Regra

1. **O vínculo mora no nível da relação.** Se a pergunta é "qual escada é deste tratamento", a
   resposta pertence à escada ou ao tratamento — nunca a uma linha filha que o usuário pode apagar.
2. **Vínculo derivado por regra de negócio** (aqui, "run same-med") é vínculo instável: quando a
   regra muda de resultado, o ponteiro muda de lugar — ou desaparece.
3. **Leitura que não encontra o vínculo deve distinguir "não existe" de "não achei".** Devolver a
   lista vazia nos dois casos apaga a diferença entre um tratamento sem escada e uma escada órfã.
4. Antes de construir a correção estrutural, **meça o blast radius**: se a classe morre por
   construção numa entrega já decidida e próxima, a correção certa é uma **Proof Obligation** nessa
   entrega, não um vínculo de transição que será deletado (ver §Decisão).

## ✅ RESOLVIDO — 052 Slice C (PR #764 `2c86b4d1`, 2026-07-20)

O executor único fez **toda** etapa nascer vinculada, e a RPC vincula a escada inteira na
transição. A suposição "o Slice C resolve" NÃO foi aceita de graça: virou **PO-9** com a repro
literal do bug ao lado do fix (baseline sem RPC = 0 vínculos, com RPC = 3) — provado 17/17 no
banco real, e o **smoke do PO em prod** adotou 2 etapas legadas `protocol_id NULL` num
`medicine_switch` de dado real. A classe morreu por construção, como previsto, mas por prova, não
por fé. A disciplina virou [[R-300]].

## Decisão tomada (histórico, pré-Slice C)

Não foi construído fix próprio. O Slice C da spec 052 (executor único) faz **toda** etapa apontar
para o executor desde o cadastro, então não sobra etapa sem vínculo para apagar. Blast radius
medido: **1 usuário — o próprio PO** (33 usuários ativos, nenhum outro com escada).

O risco que sobra não é o bug: é a frase *"o Slice C resolve isso"* virar suposição não verificada —
a mecânica exata do [[AP-254]], que armou um revisor contra código correto. Por isso virou
**PO-9 + T029b** na spec 052, com repro literal do caso, em vez de nota de rodapé.

⚠️ **Reavaliar imediatamente se:** o Slice C escorregar no backlog (outra spec na frente) **ou** a
titulação for exposta a usuários reais antes dele. Nesses cenários o blast radius deixa de ser o PO
e a decisão de não corrigir agora perde a base.

## Conserto operacional (enquanto a classe existir)

Escada órfã volta com um UPDATE de uma linha — vincular a etapa **vigente** ao executor:

```sql
UPDATE public.titration_steps SET protocol_id = '<protocolo>'
WHERE titration_id = '<escada>' AND status = 'current' AND protocol_id IS NULL;
```

Diagnóstico (escadas sem nenhuma etapa vinculada):

```sql
SELECT t.id, count(ts.id) AS steps, count(ts.protocol_id) AS com_vinculo
FROM titrations t LEFT JOIN titration_steps ts ON ts.titration_id = t.id
GROUP BY t.id HAVING count(ts.protocol_id) = 0;
```

Escolher o protocolo por **evidência** (medicamento da etapa vigente + dose do protocolo), nunca
por nome — o dado de teste tem medicamentos homônimos.
