# AP-317 — CSV de export LGPD: BOM não respeitado por viewer + header sem escape quebra parse de fórmula

**Categoria:** data_and_schema
**Status:** active
**Origem:** spec 055 PR 1.2 (migração `expo-file-system` legacy→API nova), smoke em device real Android, 2026-07-23

## O problema

Smoke do export LGPD (spec 008) em device físico Android abrindo o CSV no WPS Office revelou dois
defeitos de conteúdo, **nenhum causado pela migração de `expo-file-system`** (a API nova escreve
bytes idênticos ao que a legada escrevia — verificado no source Kotlin `FileSystemFile.kt:60`,
`content.toByteArray()` é UTF-8 por padrão no Android):

1. **Mojibake no texto acentuado** (`Ã£`, `Ã§Ã£o`, BOM aparecendo como `ï»¿` literal na célula A1):
   bytes UTF-8 corretos (BOM `EF BB BF` + conteúdo) sendo exibidos como se fossem Latin-1/CP1252.
   O BOM (`UTF8_BOM = '﻿'`, `packages/core/src/export/exportFormatters.ts:24`) está sendo
   escrito corretamente — o app (WPS Office Android) não está auto-detectando/respeitando o BOM
   no import de CSV. Não confirmado se Excel/Google Sheets têm o mesmo problema.
2. **Header de seção sem escape quebra fórmula**: `'=== METADADOS ==='`
   (`exportFormatters.ts:686`) é escrito cru — qualquer célula que comece com `=` é interpretada
   como fórmula pelo spreadsheet, gerando `#ERROR!` (erro de análise de fórmula). Falta o escape
   padrão CSV-anti-injection (aspa/apóstrofo líder, ex. `'=== METADADOS ===`).

## Por que passou despercebido

Nenhum teste (mockado) e nenhum gate automatizado (tsc/lint/jest) abre o CSV real num spreadsheet
— só um smoke em device físico prova o conteúdo renderizado. A spec 055 PR 1.2 chamou isso
explicitamente ("Encoding implícito... Provar no smoke, não assumir") e o smoke provou que HÁ um
problema — só não na camada que a PR migrava.

## Decisão (PO, 2026-07-23)

PR 1.2 (migração de API) segue como está — a camada de escrita de arquivo está correta. Os dois
bugs de conteúdo ficam para correção separada (spec 008 / follow-up), não bloqueiam esta PR.

## Regra

Bug de encoding/formatação achado num smoke de migração de infraestrutura (I/O, API do SO) DEVE
ser triado por CAMADA antes de virar escopo da PR: (1) os bytes escritos em disco estão corretos?
(verificar no source nativo, não assumir) (2) o app que os leu segue o padrão (BOM, escape de
`=`/`+`/`-`/`@` em CSV)? Migração de mecanismo de escrita não é dona de bug de conteúdo pré-existente
gerado por outra camada (`@dosiq/core`) — mas TAMBÉM não é motivo para deixar de registrar o achado.
