# AP-301 — Feature "ligada" por um status, mas o relógio que a faz andar só é setado num dos caminhos de escrita → estado zumbi

**Status**: hot · **Domínio**: data_and_schema · **Criado**: 2026-07-16
**Incidente**: titulação N1 do dosiq — **nunca funcionou em produção, em 6 meses**. Descoberto no pivô da 029.
**Ver**: [[AP-298]] · [[R-271]] · [[R-295]] · [[AP-221]]

## O que aconteceu

A titulação N1 tinha dois campos que juntos significam "está titulando":

- `protocols.titration_status = 'titulando'` — o **status**
- `protocols.stage_started_at` — o **relógio** (motor calcula `hoje - stage_started_at >= duration_days`)

Três caminhos de escrita, e **só um** setava o relógio:

| Caminho | seta `titration_status` | seta `stage_started_at` |
|---|---|---|
| `create()` com escada | ✅ | ✅ |
| **`update()` adicionando escada** | ✅ (via form) | ❌ **NUNCA** |
| `advanceTitrationStage()` | ✅ | ✅ — mas **código morto: zero chamadores** |

O fluxo real do usuário (criar tratamento → **depois** editar pra adicionar a escada) caía na linha do
meio: gravava `titulando` + `titration_schedule` e deixava `stage_started_at` **NULL**.

O motor ignora etapa sem data de início (corretamente — não dá pra calcular vencimento sem t₀).
Resultado: **status diz "titulando", o relógio nunca começou, e nada nunca acontece.** Sem erro, sem
log, sem alerta. A UI mostra a escada bonita; ela só não anda.

## Por que ficou 6 meses invisível

- **Nenhum CHECK** proibia a contradição: `titration_status='titulando' AND stage_started_at IS NULL`
  era um estado perfeitamente representável no banco.
- **A dose exibida estava sempre certa** — vinha do gerador puro caminhando o schedule em memória,
  que não depende de `stage_started_at` para a etapa 0. Só o *avanço* dependia.
- Testes cobriam `create()` (que seta) e o motor (com fixture que **tinha** a data). O caminho real
  — `update()` — não tinha teste de que a feature ficava **utilizável** depois.
- Havia um segundo bug empilhado ([[AP-298]]) que teria matado o avanço de qualquer jeito. **Dois
  bugs independentes na mesma feature**, cada um suficiente pra explicar o silêncio — o que fez cada
  investigação isolada parecer "resolvida".

## A regra

**Quando um status booleano/enum declara que algo está ATIVO, e outro campo é o que faz esse algo
ANDAR, os dois são UM ÚNICO fato — e o banco tem que se recusar a representar metade dele.**

1. **CHECK que torne o zumbi irrepresentável**:
   ```sql
   ALTER TABLE t ADD CONSTRAINT t_ativo_exige_relogio_check
     CHECK (status <> 'ativo' OR relogio_iniciado_em IS NOT NULL);
   ```
   Se o CHECK dói de escrever, é porque o modelo está errado — não porque o CHECK está.
2. **Todo caminho de escrita que liga a feature seta o relógio.** Inventariar: `create`, `update`,
   RPCs, migrações, seeds, admin. Um caminho esquecido = a feature nasce morta por lá.
3. **Teste de ATIVAÇÃO pelo caminho do usuário real**, não do mais conveniente. "Criei com a feature"
   é o caminho fácil; "adicionei depois" é o que a pessoa faz. Testar só o primeiro prova o que não
   importa.
4. **Função de domínio sem chamador é dívida ativa, não código inofensivo.** `advanceTitrationStage`
   existia, funcionava, e não estava ligada em lugar nenhum — dava a impressão de que a capacidade
   existia.

## Farol

- Coluna `*_started_at` / `*_activated_at` / `*_since` **nullable** ao lado de um status que diz "on".
- Query `WHERE status='ativo' AND relogio IS NULL` retornando **> 0 linhas em produção**. Rode-a: é
  uma linha de SQL e mede se a feature está viva. Aqui teria devolvido **100% das linhas**.
- Feature que "existe" mas cujo funil não tem nenhum caso de sucesso em prod — a ausência de dado é
  o sintoma, não a causa.

## Consequência de segunda ordem (a mais cara)

A 029 nasceu como **migração** de uma feature que ninguém percebeu estar morta. O F2 gastou um slice
inteiro provando **paridade N1↔N2** ([[R-288]]-style, 52 testes verdes) — paridade **com um cadáver**.
O modelo N2 herdou a mesma forma (`status='current'` + `started_at` nullable, sem CHECK) e teria
reproduzido o zumbi no primeiro slice de UI.

**Antes de migrar/espelhar um comportamento, provar que ele ACONTECE em produção** — não que o
código dele existe. Uma query de contagem no dado real teria custado 30 segundos e poupado 2 slices.
