# AP-342 — `Date` que carrega hora de parede depende do fuso do runtime; `toISOString()` só acerta sob UTC

**Domínio**: data_and_schema · **Descoberto**: 2026-09-01 (C5 do PR #817)
**Relaciona**: [[R-020]] (datas locais), [[AP-270]] (fixture não deriva dia por `toISOString`)

## O que aconteceu

O gate de pre-push ficou **vermelho num commit que só mexia em `.agent/` e `plans/`**. O teste que
falhou era da spec 076, sem relação nenhuma com a mudança:

```
AC-3: expected [ '2026-09-02', … ] to deeply equal [ '2026-09-01', … ]
```

Eram 21h05 em São Paulo — e **00h05 em UTC**.

## O mecanismo

`getSaoPauloTime()` monta a hora de **parede** de SP como string e a reparsa:

```ts
const s = d.toLocaleString('en-CA', { timeZone: 'America/Sao_Paulo', hour12: false })
           .replace(', ', 'T');       // "2026-09-01T21:18:00"
return new Date(s);                   // interpretada no fuso do RUNTIME
```

`getTodayLocal()` então extrai o dia com `date.toISOString().split('T')[0]`.

| Runtime | `new Date("2026-09-01T21:18")` | `toISOString()` | Dia |
|---|---|---|---|
| **UTC** (Vercel) | 21:18Z | `2026-09-01T21:18Z` | `2026-09-01` ✅ |
| **-03** (dev no Brasil) | 21:18-03 = 00:18Z | `2026-09-02T00:18Z` | `2026-09-02` ❌ |

O `toISOString()` **desfaz** o shift que o `getSaoPauloTime` acabou de aplicar. As duas operações se
cancelam apenas quando o offset do runtime é zero.

## Por que passou por dois reviews

Produção roda em UTC, onde o resultado é **correto** — o comentário no próprio helper afirma isso, e
a afirmação é verdadeira sob a premissa não declarada `TZ=UTC`. A janela de erro é de 3 horas por
noite, num fuso específico: qualquer suíte rodada de manhã ou de tarde passa. O teste da 076 usava
`Intl.DateTimeFormat('en-CA', { timeZone: 'America/Sao_Paulo' })`, que é **o jeito certo**, e por
isso divergiu do código — o teste estava certo e o helper errado, o oposto do palpite natural.

## A regra

**Uma `Date` que carrega hora de parede de um fuso não é um instante — é uma string com aparência de
`Date`.** Extrair o dia dela com `toISOString()` reintroduz o fuso do runtime como premissa oculta.

- Para **derivar o dia** de um fuso: `new Intl.DateTimeFormat('en-CA', { timeZone: TZ }).format(d)`.
  Uma operação, sem shift intermediário, correta em qualquer runtime.
- Se o shift-para-parede for inevitável, ler o dia pelos **getters locais**
  (`getFullYear`/`getMonth`/`getDate`), que casam com o frame em que a `Date` foi construída — nunca
  por `toISOString()`.
- **Teste roda no fuso da produção.** `env: { TZ: 'UTC' }` no `vitest.base.config.js` (feito) — teste
  que afirma comportamento de produção tem de reproduzir o ambiente de produção.

## Estado

Fuso da suíte fixado em UTC (`apps/web/vitest.base.config.js`), o que **fecha a janela vermelha mas
não conserta o helper**. A correção de `getTodayLocal` e a validação dos **176 call sites** são a
**spec 077** — é caminho de notificação, não vai por commit direto.
