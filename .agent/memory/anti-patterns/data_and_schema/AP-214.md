## Anti-Pattern

Zod **stripa campos desconhecidos por padrão** em `.parse()` / `.safeParse()`.
`protocolUpdateSchema = protocolSchema.partial()` herda essa propriedade.

Se um campo existe no DB mas está **ausente do `protocolSchema`**, toda chamada
de update que passa por `safeParse()` remove o campo do payload silenciosamente —
**o DB nunca é atualizado**.

Não há erro. Não há warning. O campo simplesmente desaparece.

## Exemplo real (sprint-010)

`critical_alarm` foi adicionado à tabela `protocols` via migration, mas não ao
`protocolSchema` em `packages/core/src/schemas/protocolSchema.js`.

Resultado: toggle ligado na UI → `protocolUpdateSchema.safeParse(data)` →
`critical_alarm` stripped → `supabase.from('protocols').update(parsed.data)` →
campo permanece `false` no DB → ao reabrir o form, toggle volta desligado.

```js
// ❌ BUG: critical_alarm ausente → sempre strippado
const protocolSchema = z.object({
  name: z.string(),
  frequency: z.enum([...]),
  // critical_alarm não existe aqui → Zod remove em safeParse
})
const protocolUpdateSchema = protocolSchema.partial()

// ✅ FIX: adicionar o campo
const protocolSchema = z.object({
  name: z.string(),
  frequency: z.enum([...]),
  critical_alarm: z.boolean().default(false),  // novo campo
})
```

## Regra de prevenção

Ao adicionar coluna a `protocols` (ou qualquer tabela com schema Zod):

1. Adicionar ao schema base em `packages/core/src/schemas/`
2. Verificar se `partial()` / `pick()` / `omit()` derivados precisam incluir o campo
3. Ver também R-267 (checklist completo para campos de protocols)

**Why:** Zod é estrito por design — strip é o comportamento padrão em `z.object`.
Usar `.passthrough()` apenas quando explicitamente necessário (raramente).

## Reincidência — spec 064 (2026-08-21)

`ProtocolSchema` (`packages/core/src/schemas/costAnalysisSchema.ts`) não declarava `start_date` nem
`end_date`. O caminho de custo passa os protocolos por `safeParse` antes de chamar o core — logo a
correção de vigência do 064 **nasceria inerte no custo**: o filtro veria `undefined` nos dois campos
e trataria todo tratamento encerrado como vigente, com **teste verde por cima de bug vivo**.

Pego no C1.5 (analysis F-8, armadilha 3 do playbook) **antes de codar**; virou a primeira task do
PR 1 (#807), com teste de que o objeto pós-`safeParse` conserva os dois campos.

**Generalização:** não é só `partial()` em update. Vale para **todo schema de entrada** cujo objeto
validado alimenta uma decisão adiante — se o campo que o predicado lê não está declarado, `safeParse`
o remove em silêncio e a decisão passa a ser tomada sobre `undefined`.
