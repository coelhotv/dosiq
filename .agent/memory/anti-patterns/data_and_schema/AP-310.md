# AP-310 — Enriquecedor que passa a emitir um campo já presente no payload inverte a precedência pelo spread

**Status:** active · **Layer:** warm · **Criado:** 2026-07-19 (052 Slice B, PR #762)
**Detectado por:** RC5 no próprio diff do autor · **trigger_count:** 1

## Sintoma

Um objeto é montado com campos explícitos **e** um spread de enriquecimento:

```js
payload: {
  medicineId: linkedLog?.medicine_id ?? null,   // regra de precedência
  ...enrich(inst),                              // ← spread DEPOIS
}
```

Enquanto `enrich()` não devolve `medicineId`, tudo funciona. No dia em que o enriquecedor
**ganha esse campo** — que é exatamente o que uma migração de fonte de verdade faz —, o spread
passa a sobrescrever a regra de precedência **em silêncio**. Nada quebra: o tipo é o mesmo, o
campo continua presente e populado. Só o *valor* está errado.

## Por que gate nenhum pega

- `tsc`: o shape final é idêntico, ambos os ramos produzem `string | null`.
- lint: spread depois de propriedade é sintaxe legítima e comum.
- teste: só pega se existir um caso onde as duas fontes **divergem**. O teste típico usa fixture
  em que o log e o snapshot apontam para o mesmo medicamento — passa dos dois jeitos.

É a mesma família do AP-300 (o defeito atravessa a bateria inteira porque nenhuma camada
verifica *valor*, só forma), mas em JS puro, sem o banco no meio.

## Regra

Ao adicionar um campo à saída de um enriquecedor/mapper compartilhado, **audite todo call site
que faz spread dele** e verifique se aquele campo já era escrito explicitamente. Se era, existe
uma regra de precedência escrita — e o spread acabou de virar o dono dela.

Ordem defensiva: **spread primeiro, campos com precedência depois**, com comentário dizendo POR
QUE a ordem importa (senão o próximo "organiza" o objeto e reintroduz o bug):

```js
payload: {
  ...enriched,
  // DEPOIS do spread de propósito: `enriched` também traz `medicineId`, e o log ancorado é o
  // que foi REALMENTE tomado.
  medicineId: linkedLog?.medicine_id ?? enriched.medicineId ?? null,
}
```

E o teste que fixa a regra precisa de fixture **divergente** (log aponta para X, snapshot para
Y): um caso onde as fontes concordam não testa precedência nenhuma.

## Origem

052 Slice B: `makeInstanceEnricher` passou a emitir `medicineId` (identidade congelada) para o
`timelineService`. O payload já escrevia `medicineId` a partir do log ancorado — a verdade mais
forte, o que foi de fato tomado. O spread anulou essa precedência. Achado no RC5, corrigido com
`timelineService.identity.test.ts` (2 casos, um deles com log e snapshot divergentes).
