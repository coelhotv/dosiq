# AP-319 — `REVOKE SELECT (coluna)` é INERTE quando existe `GRANT SELECT` de tabela

**Classe:** data_and_schema · **Severidade:** 🔴 alta (exposição silenciosa de coluna)
**Detectado:** 2026-07-25, spec 051-A PR 1.5a (`app_version_gate`), no BEGIN..ROLLBACK antes do apply
**Relacionados:** [[AP-278]] (camadas independentes) · [[R-295]] · [[R-270]] · ADR-091 D5/S-10

## O que aconteceu

A migração seguia o desenho do ADR-091 D5 ao pé da letra:

```sql
GRANT SELECT ON public.app_version_gate TO anon, authenticated;
-- ...
REVOKE SELECT (updated_by, updated_at) ON public.app_version_gate FROM anon, authenticated;
```

O `REVOKE` **não fez nada**. `has_column_privilege('anon', ..., 'updated_by', 'SELECT')` continuou
`true`, e um `select=*` como `anon` devolveria o uuid interno do admin e o horário da operação.

Motivo: no Postgres, `GRANT SELECT ON <tabela>` concede leitura em **todas** as colunas — presentes
e futuras — como um privilégio de tabela. Não existe subtração de coluna a partir dele: o
`REVOKE ... (coluna)` só remove privilégios que foram concedidos **no nível da coluna**. O comando
não erra, não avisa, e o `psql` responde `REVOKE` com sucesso.

## Por que passa despercebido

1. **A sintaxe existe e é aceita.** Nada no retorno sugere que a operação foi um no-op.
2. **A leitura funciona.** O app lê as colunas que precisa e ninguém percebe que lê mais do que devia.
3. **O teste óbvio é o errado.** Conferir "anon consegue ler as 5 colunas do contrato?" passa. A
   pergunta que pega é a negativa: "anon consegue ler as colunas que NÃO deveria?".
4. É uma proteção que existe **no papel da migração** — quem revisa o SQL lê a linha do `REVOKE` e
   marca como resolvido.

## Fix

Não conceder o privilégio no nível da tabela. Enumerar as colunas no `GRANT`:

```sql
REVOKE ALL ON public.app_version_gate FROM PUBLIC;
REVOKE ALL ON public.app_version_gate FROM anon, authenticated;

GRANT SELECT (platform, min_supported_version, is_active, message, store_url)
  ON public.app_version_gate TO anon, authenticated;
```

Consequência aceita e **documentada no código do cliente**: `select=*` passa a devolver `42501`. Sem
o comentário, a próxima pessoa "conserta" o select para `*` e a leitura para de funcionar — falhando
igual a uma falha de rede, ou seja, abrindo o gate em silêncio.

## Gate

Asserção **negativa** no BEGIN..ROLLBACK da migração, para os dois roles:

```sql
-- leitura permitida é medida com has_ANY_column_privilege; o privilégio de TABELA deve ser FALSE
has_any_column_privilege(role, tabela, 'SELECT')  -- esperado: true
has_table_privilege(role, tabela, 'SELECT')       -- esperado: FALSE (senão o revoke é inerte)
has_column_privilege(role, tabela, 'updated_by', 'SELECT') -- esperado: false
```

E o curl executado contra o PostgREST depois do apply (R-295): `select=*` ⇒ `42501`.

## Farol

- Migração que concede no nível da tabela **e** revoga no nível da coluna: as duas linhas juntas são
  o sintoma. A intenção de restringir coluna implica que o `GRANT` nunca deveria ter sido de tabela.
- Coluna nova numa tabela com leitura pública fica legível **por acidente** se o grant for de tabela.
  Com grant column-scoped, coluna nova é privada por omissão — o default correto.
