# AP-193 — Writer cross-plataforma sem âncora log↔instância → falsos `missed`

**Status:** ✅RESOLVED código (S3.6.2/F3.3, mobile 0.7.0) · reconcile histórico de outros usuários PENDENTE · **Layer:** warm · **Domain:** data_and_schema
**Descoberto:** 2026-05-30 (investigação: streak de um usuário caiu 63→21 sem ele ter perdido doses)

## Sintoma
Streak e adesão (lidos de `dose_instances`) despencam, enquanto o sparkline (lido da
view legada `v_daily_adherence`, baseada em `medicine_logs`) ainda mostra ~100%.
Divergência confusa entre superfícies. Dias inteiros aparecem como `missed` mesmo
tendo `medicine_logs` de tomada para todas as doses.

## Causa
A âncora log↔instância (F2.3: liga o `medicine_log` recém-criado à `dose_instance`
materializada via `markTaken`/snap) foi implementada APENAS no web (`logService.create`)
e no bot Telegram. O **mobile usa `apps/mobile/src/features/dose/services/doseService.js`
próprio** (`registerDose` = FAB, `registerDoseMany` = BulkModal) que **insere o log +
consome estoque e PARA** — sem `findAnchorInstance`/`markTaken`/`dose_instance_id`.

Resultado: todo registro mobile deixa o log avulso (`dose_instance_id=NULL`) → a instância
fica `pending` → o sweep diário (writer #3, F2.5 `markMissedDueInstances`) vira pra `missed`
→ **falso `missed`**. Como adesão = `taken/(taken+missed)` e streak quebra em dia <80%,
o falso `missed` corrompe ambos. A view legada (logs) não enxerga isso → diverge.

**Evidência (conta real):** dia com 14 logs, 0 ancorados / 14 avulsos → 14 instâncias
falso-`missed`. 142 logs avulsos no total no usuário (21 reanchoráveis a `missed` na
tolerância). SQL pontual de 2026-05-30 reverteu os 21 (missed→taken + elo) num usuário.

## Regra
- **Toda superfície que escreve `medicine_logs` é um writer da máquina de estados de
  `dose_instances`** e DEVE ancorar o log à instância (direto por `instanceId` quando o
  registro vem de um slot conhecido, ou snap por tolerância via
  `@dosiq/core` `createDoseInstanceRepository.findAnchorInstance`+`markTaken`). Web, mobile
  e bot precisam de paridade — não basta migrar a LEITURA (R-248) sem migrar a ESCRITA.
- Reusar o repo core, NÃO reimplementar a âncora por plataforma (R-231 factory).
- Best-effort (R-245/R-246): falha de âncora não bloqueia registro/estoque; log fica
  avulso e é reconciliável por backfill — mas o sweep o marcará `missed` no meio-tempo,
  então a âncora no write-path é o que evita o falso `missed`, não o backfill.
- `taken_at` = horário pretendido (não `now()`) para o self-heal `missed→taken` funcionar (S3.6.1).
- Ao migrar leitura pra instâncias numa plataforma, AUDITAR todos os pontos de escrita
  daquela plataforma na mesma fatia.

## Fix planejado
- **S3.6.2 / F3.3:** ancorar `registerDose` + `registerDoseMany` do mobile `doseService`. ✅ feito (mobile 0.7.0).
- **Reconcile one-shot** (fatia própria): re-ancorar logs órfãos históricos de TODOS os
  usuários revertendo falsos `missed→taken` (espelha backfill F2.4; idempotente, dry-run, R-179).

## Mitigação futura — 1ª alavanca se órfãos recorrerem (Gemini, PR #618)
O elo `medicine_logs.dose_instance_id` hoje faz `UPDATE ... .eq('id', logId)` com
`throw` no `error` (paridade web/bot). Se logs órfãos voltarem a surgir no mobile,
**reavaliar PRIMEIRO esta camada**: o PostgREST NÃO sinaliza no-op (0 linhas afetadas)
como erro, e a conectividade mobile pode dar comportamento não-determinístico do driver.
Defesa recomendada: `.select('id')` no UPDATE + checar `data.length > 0` antes de
considerar o elo gravado. Não aplicado agora (logId é recém-inserido → casa sempre 1 linha;
web/bot não fazem → evitar divergência), mas é o ponto de inspeção #1 num futuro incidente.
