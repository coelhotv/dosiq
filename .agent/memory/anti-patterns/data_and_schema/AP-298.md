# AP-298 — Filtro por coluna INEXISTENTE + `error` descartado = varredura morta em silêncio

**Domínio**: data_and_schema · **Detectado**: 2026-07-16 (029 F3 / T012b)
**Origem**: PR #526 (2026-05-06) — sobreviveu à migração TS do 040 e a ~2,5 meses de produção.

## O que aconteceu

O cron de titulação filtrava por uma coluna que NUNCA existiu em `protocols`:

```js
const { data: protocols } = await supabase   // ⚠️ `error` NÃO destruturado
  .from('protocols')
  .select('id, current_stage_index, titration_schedule, ...')
  .eq('user_id', userId)
  .eq('status', 'ativo')        // ❌ protocols tem `active` (boolean), não `status`
  .eq('titration_status', 'titulando');

if (!protocols || protocols.length === 0) continue;   // ← silêncio absoluto
```

O PostgREST responde **`42703 column protocols.status does not exist`** (provado via curl contra
prod). Como só `data` era destruturado, o erro morria ali: `protocols` vinha `undefined`, o guard
`if (!protocols)` fazia `continue`, e a varredura inteira virava **no-op**. Resultado: o
auto-avanço de titulação (012 Fase B, FR-005b) **nunca funcionou em produção** — nenhuma etapa
avançou, nenhum `titration_alert` foi enviado.

## Por que ninguém viu (o mais importante)

1. **O sintoma foi mascarado por um acerto de arquitetura.** O `expected_dose` das instâncias vem
   do gerador PURO (`resolveTitrationStageAt`), que caminha a escada em memória por data. As doses
   saíam CERTAS. O que não acontecia era o avanço da LINHA (`current_stage_index`/`stage_started_at`)
   e o push. Bug que não mente na dose do usuário não gera reclamação — só some.
2. **A suíte testava a função pura, não a query.** `titrationAutoAdvance.test.ts` mocka o client
   inteiro (`supabase: {}`) e exercita `_titrationDueAdvance` isolada: verde sobre caminho morto.
   Família do [[AP-279]] (o mock não reproduz o filtro → o teste mede o mock).
3. **Lint/TS não pegam**: o client era `(supabase as any)` e `.eq()` aceita qualquer string.

## Regra

1. **`error` SEMPRE destruturado e tratado** em query de varredura/cron. `const { data } = await`
   é a assinatura do bug: `if (!data) continue` converte QUALQUER erro (schema, rede, RLS,
   permissão) em "não há trabalho". **Silêncio ≠ vazio.**
2. **Nome de coluna em filtro é contrato com o schema** — vale o preflight do [[R-270]]: conferir
   contra `information_schema`/types gerados, não contra a memória nem a CLAUDE.md. Aqui o nome
   veio por analogia de outro domínio (`dose_instances.status`, esse sim existente).
3. **Varredura que "não achou nada" merece log**, não `continue` mudo — 0 linhas por 2 meses num
   cron diário é sinal, e não havia onde ele aparecer.

## Detecção

```bash
# queries que ignoram o erro
grep -rn "const { data[^}]*} = await supabase" --include=*.ts server/ api/ | grep -v error
# conferir o filtro contra o banco antes de confiar
```

Relaciona: [[AP-279]] · [[AP-215]] (select sem o campo → undefined silencioso) · [[R-270]] ·
[[AP-221]] (o schema andou, o código ficou).

## 🔴 Sítios ABERTOS em prod (achados no 050 PR 4, #812 — 2026-08-25)

Três pontos no caminho de lembretes do bot descartam `error` e tratam falha de query como
"não há dado", sem log:

1. `server/bot/reminders/prescriptionAlerts.ts:~43` — `const { data: protocols } = await ...`
   seguido de `if (!protocols || protocols.length === 0) continue;`. Erro de RLS/schema/rede vira
   "esse usuário não tem tratamento" e o alerta de receita não sai, sem nada no log.
2. `server/bot/reminders/prescriptionAlerts.ts:~47` — mesma classe, na query por usuário.
3. `server/bot/reminders/stockAlerts.ts:~198` — `_fetchStockTrackingUsers` captura o throw da
   paginação em `usersErr`, mas o branch `if (usersErr || !users || users.length === 0)` loga
   `info` "Nenhum usuário encontrado" nos DOIS casos e **descarta o conteúdo do erro**. Queda de
   banco para TODO alerta de estoque (volume e validade) e fica invisível no log.

**Não corrigidos no #812 de propósito** (PR move-only — R-318). Correção: destruturar `error`,
logar em `error` com `correlationId` e distinguir o branch de falha do branch de lista vazia.
