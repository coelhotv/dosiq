# AP-185 — Conditional UPDATE no-op em corrida → elo bidirecional órfão

**Categoria:** data_and_schema
**Severidade:** High (correção)
**Detectado:** 2026-05-29 (Gemini Code Assist, PR #609 / F2.3 âncora de log)
**Status:** corrigido

## Sintoma

Um UPDATE com guard de estado (`.eq('status','pending')`) que serve como "reserva otimista":

```javascript
async markTaken(instanceId, medicineLogId) {
  const { error } = await client.from('dose_instances')
    .update({ status: 'taken', medicine_log_id: medicineLogId })
    .eq('id', instanceId)
    .eq('status', 'pending')   // guard contra dupla-tomada
  if (error) throw error       // ← não distingue "atualizou" de "no-op"
}
```

Em **duas tomadas concorrentes** da mesma instância:
1. Writer A: update casa (`pending` → `taken`), grava `medicine_log_id = logA`.
2. Writer B: update **no-op** (status já não é `pending`) — **0 linhas afetadas, sem erro**.
3. Mas o caller de B assume sucesso e grava `medicine_logs[logB].dose_instance_id = instância`.

Resultado: `instância.medicine_log_id → logA` mas `logB.dose_instance_id → instância`. Elo **unidirecional/órfão** — a instância aponta para um log, outro log aponta para a instância.

## Causa raiz

No PostgREST/Supabase, um UPDATE que casa 0 linhas **não** retorna erro. Sem `.select()`, não há como o caller saber se a reserva pegou. Tratar "sem erro" como "sucesso" é a falha.

## Correção

UPDATE retorna as linhas afetadas via `.select()`; o método devolve boolean; o caller só prossegue com o elo inverso se `true`:

```javascript
async markTaken(instanceId, medicineLogId) {
  const { data, error } = await client.from('dose_instances')
    .update({ status: 'taken', medicine_log_id: medicineLogId })
    .eq('id', instanceId).eq('status', 'pending')
    .select('id')
  if (error) throw error
  return !!(data && data.length > 0)
}
// caller:
const marked = await repo.markTaken(inst.id, log.id)
if (!marked) return null   // reserva não pegou → não grava o elo inverso
```

## Regra geral

Qualquer UPDATE condicional usado como **reserva/transição de estado** (status guard, optimistic lock, claim) DEVE retornar as linhas afetadas (`.select()`) e o caller DEVE checar antes de gravar estado dependente do lado oposto. "Sem erro" ≠ "afetou linha".
