# AP-186 — SELECT Supabase/PostgREST sem paginação trunca em ~1000 linhas (silencioso)

**Categoria:** data_and_schema
**Severidade:** High (correção — dados sub-processados em silêncio)
**Detectado:** 2026-05-29 (canário dry-run do backfill, PR-F2.4)
**Status:** corrigido

## Sintoma

Um `SELECT` que percorre "todas as linhas" de um conjunto retorna **no máximo ~1000** — sem erro. O processamento downstream opera sobre um subconjunto truncado e ninguém percebe.

No backfill: a query de `medicine_logs` a casar reportou `1000` logs para um usuário que tinha `1778` (verificado via `count(*)`). Sem paginar, ~44% dos logs ficariam sem âncora — migração silenciosamente incompleta.

## Causa raiz

PostgREST (camada do Supabase) aplica um teto default de linhas por requisição (~1000). `.select()` sem `.range()`/`.limit()` explícito devolve só a 1ª página. Diferente de um erro, é uma resposta "ok" parcial — o canário/dry-run é o que expõe (contagem retornada < contagem real).

## Correção

Paginar com `.range(from, from + PAGE - 1)` em loop até a página vir incompleta:

```js
const PAGE = 1000
const rows = []
for (let from = 0; ; from += PAGE) {
  const { data: page, error } = await client.from('t').select('...') /* filtros */
    .range(from, from + PAGE - 1)
  if (error) throw error
  if (!page || page.length === 0) break
  rows.push(...page)
  if (page.length < PAGE) break
}
```

Quando o processamento **muta** o critério do filtro (ex.: backfill seta `dose_instance_id`), ler TODAS as páginas para memória **antes** de qualquer escrita — evita drift de offset.

## Regra geral

Qualquer SELECT que pretende cobrir um conjunto completo (varredura, migração, agregação, export) DEVE paginar ou provar que o conjunto é < limite. "Funcionou no teste" com poucos dados mascara — só aparece no usuário/tenant grande. Mesma classe do fix de paginação do `doseInstanceScheduler` (Gemini #603).
