# AP-314 — DDL destrutiva validada contra o REPOSITÓRIO derruba os BINÁRIOS já instalados

**Status**: hot · **Domínio**: data_and_schema · **Criado**: 2026-07-22
**Incidente**: 029 F6 (#765) — outage em prod: aba Hoje e aba Tratamentos mortas em todo aparelho Android/iOS que não atualizou a app. Relatado pelo PO 2026-07-22, ~36h após o merge.
**Relaciona**: [[AP-300]] (o outro 42703, mesma tabela, causa oposta) · [[R-295]] (verificar coluna no banco) · [[R-289]] (types gerados) · [[ADR-084]] (titulação N2) · [[CON-032]]

## O que aconteceu

O F6 dropou as 4 colunas de titulação N1 de `protocols` (`titration_schedule`, `titration_status`,
`current_stage_index`, `stage_started_at`), fechando o épico 029.

O gate do DROP foi **rigoroso** — e é importante registrar isso, porque a lição não é "faltou
cuidado". Ele provou, com evidência executada:

1. `grep` das 4 colunas em `apps/ packages/ server/ api/` → **zero** em código de produção;
2. os 7 `select()` alterados **executados** contra o PostgREST real → todos 200 ([[R-295]]);
3. varredura no banco → zero dependentes em `pg_views`, `pg_matviews`, `pg_proc`, `pg_constraint`,
   `pg_indexes`, defaults/generated e `pg_policies`;
4. `validate:full` (798) · `test:critical` (2104) · mobile (497) · lint 0 · strict-island OK;
5. estado medido antes do DROP: as 68 linhas eram byte-idênticas nas 4 colunas → nada a preservar;
6. guardas automáticas contra reintrodução, em três suítes.

Todas essas afirmações eram verdadeiras e continuam verdadeiras. O DROP rodou.

**36h depois, o app da esposa do PO estava travada.** O mobile **v0.27.0**, publicado na Play Store
e instalado em aparelhos que não atualizaram, nomeia `titration_status` no `select()` de dois
serviços:

- `apps/mobile/src/features/dashboard/services/dashboardService.ts:31`
- `apps/mobile/src/features/treatments/services/treatmentsService.ts:113`

Pós-DROP esses selects viram **`42703` permanente**. Não é intermitente, não passa com retry, não
melhora com wifi: a coluna não existe e o binário não muda de ideia.

## O ponto cego, em uma frase

**O item 1 do gate — o `grep` — mede o repositório. O repositório é o código que vai rodar. O que
QUEBRA é o código que JÁ ESTÁ RODANDO, e esse não está no repositório: está em `HEAD~N`, compilado,
dentro do bolso do usuário.**

Web não sofre e por isso ninguém pensa nisso: o browser baixa o bundle novo no reload, o cliente
antigo deixa de existir em minutos. Bot e cron são server-side, deployam junto. **Mobile instalado é
a única superfície do Dosiq onde código velho continua chamando a API por tempo indeterminado** — e
sem update forçado, "indeterminado" é literal.

O gate do F6 herdou o modelo mental da web e aplicou a um DROP que afeta todos os clientes.

## Por que o diagnóstico demorou (dois mascaramentos)

**1. Só duas abas caíram.** Estoque e Perfil não tocam `protocols` → carregavam normal. Isso empurra
a hipótese para "bug de tela", não "erro de schema", e afasta de "outage".

**2. A tela mentiu a causa.** O sintoma na tela era **"Cache expirado (> 24h)"**, não um erro de
banco. Em `apps/mobile/src/features/dashboard/hooks/useTodayData.ts`, o `catch` do `load()` chama
`handleCacheFallback(err)`, que só re-lança o erro **original** se não houver cache; havendo cache
velho, o que aparece é a expiração do snapshot. O `42703` foi engolido:

```js
} catch (err) {
  try {
    await handleCacheFallback(err)     // ← se há cache >24h, reporta "Cache expirado"
  } catch (fallbackErr) {
    setError(fallbackErr.message)      // ← o 42703 nunca chega aqui
  }
}
```

Erro de schema ficou **indistinguível de offline** num app offline-first. O aparelho ainda estava em
modo avião com wifi ativo, o que reforçou a pista falsa. Corrigido junto (ver Fix).

## Regra

**Antes de qualquer DDL destrutiva (`DROP COLUMN`, `DROP TABLE`, `RENAME`, mudança de tipo ou de
CHECK que aperte), o inventário de leitores tem de incluir as VERSÕES MOBILE AINDA EM CAMPO — não
só `HEAD`.**

O `grep` correto não é um, são dois:

```bash
# ❌ o que o F6 fez — só o código que VAI rodar
git grep -n "coluna_alvo" -- apps/ packages/ server/ api/

# ✅ o que faltou — o código que JÁ ESTÁ rodando, versão a versão em uso
for ref in <tags/commits das versões mobile ainda instaladas>; do
  git grep -n "coluna_alvo" "$ref" -- apps/mobile packages/core
done
```

Se qualquer versão em campo nomeia a coluna, existem exatamente três saídas legítimas:

1. **Adiar o DROP** até a versão sair de circulação (exige política de versão mínima suportada);
2. **Expand/contract**: deixar a coluna inerte com DEFAULT que reproduza o valor lido hoje, e dropar
   num ciclo futuro — foi o hotfix aplicado aqui;
3. **Forçar update** (kill switch de versão mínima no app) **antes** do DROP — só funciona se o
   mecanismo já existir no binário em campo, o que hoje não é o caso.

O que **não** é saída: confiar que "o usuário atualiza". Não atualiza.

## Sinal de alerta específico

- Migração cuja justificativa de segurança se apoia em `grep`/inventário **do repositório** — a
  frase "zero leitores no código" está incompleta enquanto não disser **em qual versão**.
- Qualquer `DROP`/`RENAME` numa tabela que o mobile lê. `protocols`, `medicines`, `dose_instances`,
  `logs`, `stock` são todas superfícies de binário instalado.
- Relato de usuário do tipo "algumas abas não carregam, outras sim" logo após um deploy de schema:
  o recorte das abas mapeia exatamente as tabelas tocadas. É diagnóstico, não coincidência.

## Fix aplicado

`docs/migrations/20260722_restore_protocol_titration_n1_legacy_clients.sql` — recria as 4 colunas
**inertes**, com os DEFAULTs que a migração do DROP mediu em produção (`'estável'` / `'[]'` / `0` /
`NULL`). Como as 68 linhas eram byte-idênticas, o cliente antigo voltou a ler **exatamente** o que
lia antes: restauração fiel, não aproximação.

Detalhe que salvou o resultado: o `EvolutionBadge` da v0.27.0 **já derivava de `titration_steps`**
(N2) via `getEvolutionBadge` — `titration_status` era vestígio no select, valor descartado. Por isso
o cliente antigo voltou correto, não degradado. Foi sorte de timing do repontamento, não desenho.

Verificado em produção: 4 colunas com tipos/defaults corretos · backfill 68/68 nas quatro · select
literal da v0.27.0 contra o PostgREST → **200** (controle com coluna inexistente → 42703, provando
que o teste discrimina).

As guardas anti-reintrodução do F6 seguem valendo: **nenhum código novo pode escrever estas
colunas**. Elas existem só para manter binário legado vivo.

## Débito aberto

Não existe hoje **política de versão mínima suportada** nem telemetria de distribuição de versões
instaladas. Sem isso, a saída (1) acima é inaplicável — não há como saber quando uma versão saiu de
circulação, e todo DROP futuro fica no escuro. Enquanto não existir, a regra operacional é
expand/contract por padrão. Discussão de política aberta pelo PO nesta mesma sessão.
