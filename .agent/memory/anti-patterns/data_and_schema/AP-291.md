# AP-291 — Inventário escrito à mão contra schema que anda sozinho (o export mentia por omissão)

**Domínio:** data_and_schema · **Registrado:** 2026-07-14 (spec 008, PR #743)
**Regra derivada:** [[R-291]] · **Família:** [[R-270]] / [[AP-221]] (o schema andou, o código ficou)

## O que aconteceu

O export LGPD web (em produção havia meses) tinha **três** buracos, todos silenciosos:

1. **Omissão**: `biomarkers_log` — glicemia, peso, pressão arterial, **dado sensível de saúde**,
   em prod desde o épico 012 — **nunca** saiu no bundle. O arquivo era gerado, parecia completo,
   e o dado simplesmente não estava lá. Descumprimento de LGPD (art. 18, II/V) que ninguém via.
2. **Seção inteira ausente**: perfil/configurações (`user_settings`) fora do inventário.
3. **Coluna fantasma**: o inventário pedia `medicines.dosage_mg`, `medicines.pill_count` e
   `protocols.times` — **colunas que não existem no schema**. Em JSON viravam `undefined`
   (dropadas pelo `JSON.stringify`); em CSV, célula vazia. O usuário recebia um CSV com a coluna
   "Dosagem (mg)" **em branco em todas as linhas**.

Nada falhou: nem tsc (o objeto era `any`), nem lint, nem teste (não havia asserção sobre
conteúdo), nem runtime (ler propriedade inexistente é `undefined`, não erro).

## Por que a classe é perigosa

Um inventário de export é uma **lista de colunas escrita à mão** apontando para um schema que
evolui por outro caminho (migrações). Não existe compilador entre os dois. E o modo de falha é
**assimétrico**:

- **omitir** = descumprimento invisível (o titular não sabe o que não recebeu);
- **`select('*')`** = vazamento (levaria `verification_token` — segredo do vínculo Telegram —
  para dentro de um arquivo que o usuário compartilha por WhatsApp);
- **coluna fantasma** = campo vazio que passa por "usuário não preencheu".

Os três se parecem com "está funcionando" na tela.

## Como pegar / evitar

- **Read-path por allowlist explícita**, nunca `*`, em qualquer superfície que EXPORTA dado
  (`getProfileForExport`): a lista tem que doer para ser revisada.
- **Teste de conteúdo, não de execução**: o teste do export tem que afirmar *quais seções e
  quais colunas* estão no bundle (fixture → asserts), não só que a função não estourou.
- **Uma implementação, não duas**: web e mobile consomem o MESMO coletor/formatador do core.
  Duas listas de colunas "iguais" divergem no primeiro épico (a família do R-290).
- **Auditoria periódica contra o `information_schema`** (foi assim que os 3 buracos apareceram):
  toda tabela com `user_id` recebe decisão explícita de export — ver R-291 e
  `plans/specs/008-complete-data-export-lgpd/AUDIT_FR-010.md` (local-only).

## Sintoma-farol

Campo que sai **sempre vazio** no artefato exportado, para todos os usuários. A hipótese
preguiçosa é "ninguém preenche esse campo"; a hipótese certa é "esse campo não existe com esse
nome". Conferir contra o schema antes de aceitar a primeira.
