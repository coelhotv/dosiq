# AP-277 — `SELECT ... INTO` sem linha ATRIBUI NULL (não preserva o init da variável) → flag booleana vira fail-OPEN

**Status**: active · **Layer**: warm (`data_and_schema`) · **Criado**: 2026-07-11 (044 F1, PR feature/044/f1-sql)
**Trigger count**: 1

## Sintoma

Em PL/pgSQL, uma flag de política lida de uma tabela de preferências e inicializada com o valor
seguro:

```sql
DECLARE
  v_stock_tracking BOOLEAN := true;   -- "fail-safe": sem linha → estoque ligado
BEGIN
  SELECT COALESCE(us.stock_tracking_enabled, true) INTO v_stock_tracking
    FROM public.user_settings us WHERE us.user_id = p_user_id;   -- ⚠️ zero linhas

  IF v_stock_tracking THEN ... END IF;   -- NUNCA entra: v_stock_tracking = NULL
```

Quando o `SELECT` **não retorna linha**, o PL/pgSQL **atribui NULL** à variável — ele NÃO
"deixa como estava". O `COALESCE` dentro do `SELECT` só roda sobre linhas que existem; com zero
linhas ele nem é avaliado. Resultado: `NULL` → `IF NULL THEN` é falso → o guard cai para o lado
ERRADO (fail-**open**), silenciosamente.

No 044 F1 isso significava: usuário **sem** linha em `user_settings` teria o controle de estoque
**desligado por omissão** — exatamente o contrário do FR-009 (default = estoque ativo). A dose
registrava com saldo 0 sem lançar "Estoque insuficiente".

## Causa

Confundir a semântica de `SELECT INTO` (atribuição incondicional, NULL quando não há linha) com a
de `IF NOT FOUND` (que preserva). O valor de inicialização da variável dá uma **falsa sensação**
de fail-safe: ele é sobrescrito.

## Fix

`COALESCE` **depois** do SELECT, sobre a variável — ou `IF NOT FOUND THEN v := <default>`:

```sql
SELECT us.stock_tracking_enabled INTO v_stock_tracking
  FROM public.user_settings us WHERE us.user_id = p_user_id;
v_stock_tracking := COALESCE(v_stock_tracking, true);   -- ← cobre "sem linha" E "coluna NULL"
```

## Como foi detectado

Pelo teste `BEGIN..ROLLBACK` do failure mode "linha de user_settings AUSENTE" (R-270), rodado
contra o banco real ANTES do commit. O código **parecia** correto na leitura — e o preflight do
agente documentava a premissa errada ("SELECT INTO não sobrescreve"). Só a execução contra o
banco derrubou a premissa.

## Lição (a que generaliza)

**Um failure mode do preflight R-270 só vale se for EXECUTADO.** O raciocínio do agente sobre a
semântica da linguagem é justamente o que está sob suspeita — não pode ser o próprio juiz. A
tabela de failure modes não é documentação: é a lista de testes a rodar. Um default de segurança
"óbvio na leitura" é o candidato nº 1 a estar invertido.

Aplica-se a toda flag de política/permissão lida de tabela: **prove o caminho "sem linha"**, nunca
o assuma.
