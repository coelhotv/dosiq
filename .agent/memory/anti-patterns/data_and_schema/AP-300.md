# AP-300 — Tipo escrito à mão declara campo que a tabela não tem → o `select()` sai do tipo e quebra em runtime

**Status**: hot · **Domínio**: data_and_schema · **Criado**: 2026-07-16
**Incidente**: 029 F3 (#749) — outage em prod: web + mobile + cron, todo o read-path de `protocols`.
**Relaciona**: [[AP-298]] (coluna fantasma em filtro), [[AP-279]] (mock mede o mock), [[R-289]] (types gerados), [[R-271]] (CHECK ↔ enum), [[CON-032]]

## O que aconteceu

`TitrationStepLike` (interface **escrita à mão**, F2) declarava:

```ts
export interface TitrationStepLike {
  position: number
  dose?: number
  duration_days?: number | null
  status?: string | null
  started_at?: string | null
  description?: string | null   // ← a coluna NUNCA existiu em titration_steps
}
```

`description` era campo do **N1** (stage no jsonb). O F1 corretamente não criou a coluna no N2 — a
spec decidiu que "nota/objetivo por etapa não migra" (Decisões §2). Mas o adapter do F2 mapeou
`stageNote: currentStep.description ?? undefined` e **declarou o campo no tipo** para compilar.

**Em runtime isso era inofensivo e invisível**: lia `undefined`, e `stageNote` some da UI sem erro.
Ficou dormente por um slice inteiro.

No F3, escrevi os `select()` do PostgREST **a partir do tipo** — o tipo é o contrato, certo? — e
`description` entrou em 5 selects, incluindo o `DEFAULT_SELECT` de `protocols`:

```
{"code":"42703","message":"column titration_steps_1.description does not exist"}
```

Todo read-path de `protocols` (web + mobile + cron) morreu no merge.

## Por que NENHUM gate pegou

Esta é a parte que importa — a lista inteira passou:

| Gate | Resultado | Por que não pegou |
|---|---|---|
| `tsc` / strict islands | ✅ 0 erros | O select é uma **string**. TS não sabe que ela referencia colunas. |
| `validate:agent` 2068/2068 | ✅ | Os testes **mockam o client** — o mock devolve a fixture e ignora o select (AP-279). |
| Jest mobile 434 | ✅ | idem |
| lint | ✅ | idem |
| SQL live 21/21 | ✅ | Testava a **RPC**, não os selects do PostgREST. |
| RC5 (self-review) | ✅ | Revisei a lógica, não confrontei a string com o schema. |
| Review externo (Gemini) | ✅ | idem |

**A conclusão desconfortável**: um select do PostgREST é a única coisa no projeto que é
simultaneamente (a) crítica, (b) invisível ao compilador e (c) invisível aos testes, porque o
primitivo que ela ataca está sempre mockado. Não existia gate.

## Regra

**Tipo `*Like` escrito à mão é uma HIPÓTESE sobre o schema, não o schema.** Antes de somar campo
num tipo desses — e antes de escrever qualquer `select()` a partir de um:

1. Conferir contra `packages/shared-data/src/database.types.ts` (**gerado** = verdade) ou
   `information_schema.columns`. O tipo à mão não é fonte.
2. **Executar o select contra o banco real** (curl/PostgREST) antes do commit — mesmo espírito do
   R-270 ("failure mode só vale EXECUTADO") e da R-288 ("não prove com mock o que o mock finge").
   Um select novo/alterado é mudança de contrato com o banco, igual a SQL.
   ⚠️ O supabase-js **remove whitespace** do select antes de enviar; ao reproduzir com curl, fazer
   `tr -d '[:space:]'` — senão o teste falha com `PGRST100` por motivo errado (aconteceu).
3. Se o campo existe no legado e **não** no modelo novo, isso é decisão de produto — anotar no tipo
   por que ele NÃO está lá, senão o próximo slice o reintroduz "pra compilar".

## Sinal de alerta

Campo opcional (`?:`) num tipo à mão que **nunca** aparece preenchido em nenhum teste e em nenhum
dado real. Não é campo opcional — é campo **inexistente** esperando alguém escrever um select.

## Antídoto barato

Fixture de contrato: um teste que dispara cada `select()` de produção contra o banco real
(BEGIN..ROLLBACK, sem dado), só para provar que o PostgREST aceita a string. Custa ~10 linhas por
select e teria pego este bug antes do PR — e pegaria também o AP-298.
