# AP-236 — Metadado de ancoragem lido do objeto validado pelo Zod vira `undefined`

## Sintoma

Em mapeamento de lote (`createBulk` web / `registerDoseMany` mobile), o `instanceId`
(metadado de ancoragem) era lido de `validatedLogs[i].instance_id`. Como `instance_id`
**não é coluna** de `medicine_logs`, ele **não está no `logSchema`** — o Zod o remove no
`safeParse`. Resultado: `instanceId` sempre `null` → **ancoragem em lote quebrada** (toda
dose do lote ficava avulsa). Bateu em **web E mobile** no mesmo PR (#673).

## Causa

`safeParse()` estrita campos fora do schema (mesma mecânica de [[AP-214]]). A diferença:
aqui o campo é metadado **intencionalmente fora do schema** (não é coluna), então a
correção NÃO é "adicionar ao schema" — é **ler do input cru, não do output validado**.

## Fix

Mapear sobre `validatedLogs` (dados coeridos) mas ler o metadado do array **original por
índice** — os arrays têm o mesmo comprimento e ordem:

```js
const coreLogs = validatedLogs.map((log, index) => ({
  ...log,
  instanceId: logsData[index].instance_id ?? logsData[index].instanceId ?? null,
}))
```

## Prevenção

Qualquer campo de orquestração/metadado (anchor id, flags de fluxo) que não seja coluna
da tabela: trafega **fora** do payload validado. Ao mapear pós-Zod, recupere-o do input
cru por índice/chave. Irmão de [[AP-214]] (campo de coluna ausente do schema) — sintoma
parecido, fix oposto (lá: adicionar ao schema; aqui: nunca esperar do schema).
