# AP-287 — Carimbo de estado reusado para gravar uma escolha inicial afirma um fato que nunca existiu

**Classe:** modelagem de estado / semântica de dado
**Detectado em:** smoke do PO da spec 044 F4b (conta nova escolhe dose-only no onboarding → o toggle de Settings não abria o saldo inicial)

## Sintoma

Conta nova, onboarding, escolhe "só lembrar minhas doses" (dose-only). Depois vai em
Configurações e liga o controle de estoque: **a tela de saldo inicial não aparece** — o estoque
simplesmente liga, com saldo zero, e o usuário nunca é perguntado quanto tem.

## Mecanismo

`setStockTracking(false)` carimbava `stock_paused_at = now()` **sempre**, porque foi escrito para
o opt-out (F4a), onde o carimbo significa: *"existe um saldo congelado desde T"*.

O onboarding reusou o mesmo escritor para gravar a **escolha inicial**. Só que ali não existe
saldo nenhum — o carimbo é uma **afirmação falsa**. E o resto do sistema acredita nele:

```
neverHadStock = !enabled && !pausedAt   // ← com o carimbo, dá FALSE
```

Então o toggle classificava a conta recém-criada como "congelada", entrava no fluxo de
**retomada** (gap de minutos → < 30d → silencioso), religava o FIFO sobre zero e limpava o
carimbo. Nenhum erro, nenhum log, nenhum teste vermelho: o fluxo errado executou **com sucesso**.

## A regra

**Um campo que carrega um FATO ("congelou em T", "confirmou em T", "migrou em T") não pode ser
escrito por um caminho onde esse fato não aconteceu.** Reusar o escritor porque "o efeito
colateral é o mesmo" (a flag vai pra false dos dois jeitos) ignora que o segundo campo é uma
**asserção sobre o passado** — e uma asserção falsa se vinga longe da origem, em quem a lê como
verdade.

Dois cheiros que denunciam:
1. O mesmo setter serve "desligar porque o usuário desistiu" e "nasceu desligado". São eventos
   diferentes; um tem passado, o outro não.
2. Um derivado do tipo `nunca teve X = !temX && !carimboDeX` — ele é tão confiável quanto a
   disciplina de quem escreve o carimbo.

## Fix aplicado (044 F4b)

1. **Raiz:** `setStockTracking(enabled, { freeze })` — `freeze: false` desliga **sem** carimbar.
   O onboarding (`chooseStockModeInOnboarding`) usa `freeze: false`; o opt-out real mantém o
   default `true`. O carimbo volta a significar exatamente o que promete.
2. **Cinto de segurança (defesa em profundidade):** `assessResume()` passa a devolver
   `hasFrozenBalance` (existe saldo != 0 por trás do carimbo?). Carimbo **sem** saldo → a UI pede
   o saldo inicial em vez de retomar. Cobre dado legado e o opt-out feito com o estoque já vazio —
   retomar "as-is" um saldo que não existe liga o FIFO sobre zero e gera alerta de "acabando" para
   quem nunca disse quanto tem.

## Por que os gates não pegaram

Todos os testes passavam: cada peça estava correta isoladamente, e os mocks do `assessResume`
descreviam um mundo em que o carimbo **sempre** vinha de um congelamento real — o mesmo mundo que
o autor tinha na cabeça. O bug vivia na fronteira entre dois caminhos que ninguém testou juntos
(onboarding grava → Settings lê). Só o smoke de ponta a ponta cruza essa fronteira.
