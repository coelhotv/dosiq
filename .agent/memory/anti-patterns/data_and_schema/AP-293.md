# AP-293 — Coluna de dono denormalizada em tabela-filha + FK só para `parent(id)` = injeção cross-owner

**Domínio:** data_and_schema
**Detectado:** 029 F1 (PR #746, review Gemini) — `titration_steps`
**Relaciona:** [[AP-272]] (FK de dono), [[AP-278]] (grant/guard camadas independentes), [[R-287]], [[R-271]]

## Sintoma

Tabela-filha denormaliza `user_id` (dono) para permitir RLS direta por linha
(`USING (user_id = auth.uid())`), MAS a FK para a tabela-pai referencia só `parent(id)`.
A RLS de INSERT valida apenas `user_id = auth.uid()` — não valida que o `parent_id` apontado
pertence ao MESMO dono. Um cliente malicioso/anômalo insere uma linha-filha com **seu próprio
`user_id`** (a RLS passa) mas com **`parent_id` de outro usuário** → injeta filha na entidade
alheia. Invisível ao alvo (a RLS de SELECT dele filtra por `user_id`), mas:

- quebra a invariante `filha.user_id == pai.user_id`;
- **explode quando um consumidor bypassa RLS** (cron/motor `service_role`, RPC `SECURITY DEFINER`)
  e faz JOIN `filha → pai` por `parent_id` sem re-checar dono — age sobre dado contaminado.

Caso real: `titration_steps` (user_id denormal + `FK titration_id → titrations(id)`); o motor de
avanço F3 roda como `service_role`. Meu teste de RLS cobriu spoof de `user_id` na PRÓPRIA tabela
(caso 9) mas NÃO o vetor `parent_id` alheio — pego pelo revisor externo.

## Fix

FK **composta** para `parent(id, user_id)`, não só `id`:

```sql
-- na tabela-pai: alvo referenciável
ALTER TABLE parent ADD CONSTRAINT parent_id_user_id_key UNIQUE (id, user_id);
-- na filha: a FK amarra dono + pai
ALTER TABLE child
  ADD CONSTRAINT child_parent_user_fkey
  FOREIGN KEY (parent_id, user_id) REFERENCES parent(id, user_id) ON DELETE CASCADE;
```

Torna IMPOSSÍVEL, no banco, uma filha apontar para um pai de outro dono — defense-in-depth
independente da RLS (que continua valendo). `id` já é PK (único), então a UNIQUE(id,user_id) é
trivial de satisfazer e existe só para ser referenciável.

## Guard / regra

- SEMPRE que uma tabela-filha denormaliza a coluna de dono (`user_id`) para RLS direta, a FK para
  o pai DEVE ser composta `(parent_id, user_id)` — nunca só `parent_id`.
- O teste de RLS/segurança da tabela DEVE incluir o vetor **`parent_id` de outro usuário com
  `user_id` próprio** (não só spoof do `user_id` na própria linha).
- Farol: "denormalizei o dono pra RLS ficar simples" → pare e amarre o pai por FK composta.
