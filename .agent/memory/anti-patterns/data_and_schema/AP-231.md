# AP-231 — Mutar `medicine_logs` sem replay dos efeitos colaterais do registro (estoque + âncora)

**Categoria:** data_and_schema
**Severidade:** Critical (correção / corrupção de inventário + adesão)
**Detectado:** 2026-06-15 (smoke + Gemini Code Assist, PR #668 / spec 030)
**Status:** corrigido

## Sintoma

Registrar uma dose (`INSERT medicine_logs`) dispara **dois efeitos colaterais acoplados**:
1. **Consumo de estoque FIFO** (`consume_stock_fifo` / `stock_consumptions`).
2. **Âncora da `dose_instance`** (`status='taken'` + `medicine_log_id`, elo bidirecional — AP-193).

Qualquer superfície que **muta o log direto** (`UPDATE`/`DELETE` em `medicine_logs`) sem **reverter/reaplicar** esses efeitos corrompe o estado. Dois casos reais no mesmo PR:

**(a) Ghost taken (web `logService.delete`)** — deletava o log mas não revertia a instância. A FK `dose_instances.medicine_log_id → medicine_logs.id` é `ON DELETE SET NULL`: limpa o elo mas **não toca `status`**. Resultado: instância `status='taken'` + `medicine_log_id=null` → dose "fantasma" no histórico, sem ações de edit/delete, contando como tomada na adesão.

```javascript
// ERRADO — FK SET NULL deixa status=taken órfão
await supabase.from('medicine_logs').delete().eq('id', id)
// (instância continua 'taken', sem log)
```

**(b) Furo de estoque (mobile `useHistoryMutation`)** — `updateLog`/`deleteLog` operavam direto via cliente Supabase, ignorando o FIFO. Estoque dessincronizava silenciosamente (furos invisíveis), divergindo de web/bot.

```javascript
// ERRADO — bypassa restore/consume de estoque
await supabase.from('medicine_logs').update(logData).eq('id', logId)
await supabase.from('medicine_logs').delete().eq('id', logId)
```

## Causa raiz

O `medicine_log` é a fonte de verdade da tomada, mas **não é auto-suficiente**: o registro tem efeitos colaterais transacionais (estoque, âncora) que o banco **não desfaz sozinho** num `UPDATE`/`DELETE` cru. FK `ON DELETE SET NULL` resolve só o elo, nunca o `status`. Cada superfície de mutação reimplementou o caminho feliz e esqueceu o reverso.

## Correção

**Toda mutação de log replica/reverte os efeitos do registro**, na camada de serviço (service-first), não no hook/componente:

- **delete:** restaura estoque (`restore_stock_for_log`) **antes** de deletar; reverte instância ancorada (`revertToUnregistered` → `missed`/`pending` por janela de tolerância).
- **update com mudança de `quantity_taken`/`medicine_id`:** restaura estoque antigo → update → reconsome novo (`consume_stock_fifo`); rollback se o reconsumo falhar.

Mobile passou a ter `updateOrphanLog`/`deleteOrphanLog` em `doseService` (espelho de `logService` web + `undoDose`). Hook só orquestra estado.

## Regra geral

`medicine_log` tem **efeitos colaterais acoplados** (estoque FIFO + âncora de instância). Nenhuma superfície muta log direto via cliente: usa o **service** que replica/reverte TODOS os efeitos. Ao deletar uma linha com FK `ON DELETE SET NULL`, lembrar que a FK limpa o elo mas **não** reverte campos de estado dependentes (`status`) — reverter explicitamente. Paridade obrigatória web↔mobile↔bot na lógica de mutação de log.
