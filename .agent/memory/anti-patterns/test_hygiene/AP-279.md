# AP-279 — Mock de query que IGNORA o filtro mede o mock, não o código

**Classe**: test-hygiene / falso-verde
**Detectado**: 2026-07-11 (spec 044 F2, T005 — filtro dose-only nos alertas de estoque)
**Status**: active · layer: warm (pack `test-hygiene`)

## Sintoma

Teste do filtro server-side (`checkStockAlertsViaDispatcher` não pode alertar usuário
dose-only) falhou com 2 usuários no dispatch quando o esperado era 1 — mesmo com o código
CORRETO. O mock do Supabase encadeava `.in('user_id', ids)` como no-op (`mockReturnThis()`)
e o `then` devolvia o array COMPLETO enfileirado, inclusive as linhas do usuário que o
código tinha acabado de excluir do `.in(...)`.

## Por que é perigoso (o lado inverso é o falso-verde)

Aqui deu falso-VERMELHO (barulhento, se corrige). O modo grave é o simétrico: um mock que
devolve dados JÁ filtrados pelo autor do teste faz o assert passar **mesmo que o código não
tenha filtro nenhum** — o teste vira decoração. Um filtro de segurança/privacidade testado
assim (RLS, escopo por usuário, opt-out) fica "coberto" sem nunca ter sido exercido.

## Regra

Mock de client de query DEVE honrar os operadores que o teste está verificando:
- se o assert é sobre **quem é filtrado**, o mock aplica `.in()`/`.eq()` nos dados;
- o que o mock não aplica, o teste NÃO pode afirmar.

Alternativa aceita: não asserta a lista de saída — asserta o ARGUMENTO do filtro
(`expect(_ins[0][1]).toEqual([U_ON])`). Os dois juntos (argumento + saída filtrada) é o
padrão forte, e é o que ficou em `server/bot/__tests__/stockAlertsDoseOnly.test.ts`.

## Família

Irmão de AP-276/R-288 (nunca mockar o primitivo que se está testando — lá, o primitivo de
concorrência; aqui, o predicado da query).
