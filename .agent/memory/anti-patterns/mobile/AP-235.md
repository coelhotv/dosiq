# AP-235 — Alarme Local Não Cancelado ao Resolver Dose por Outra Superfície [HIGH]

## Problema

O alarme local (Notifee) de uma `dose_instance` crítica sobrevivia à resolução da dose quando ela era marcada como tomada **fora dos botões do próprio alarme**. Fluxo do bug:

1. Alarme crítico dispara → usuário toca **Soneca 5 min** (`scheduleSnooze` agenda trigger +5min com `id = doseInstanceId`).
2. Antes do re-disparo, a dose é marcada tomada por **outra superfície** (timeline/FAB do app via `registerDose`/`registerDoseMany`, ou web/bot).
3. Nada cancela o trigger +5min já agendado. `syncAlarms` só re-roda em `AppState→active` / mutação de protocolo, **não** no registro de dose; `snoozed_until` só evita **re-agendar**, não cancela o trigger já posto.
4. O trigger dispara → `AlarmFullScreen` abre numa dose já `taken` e **não revalida status**, forçando Tomei/Soneca/Pular → dupla contagem, re-snooze, ou corrupção `taken→skipped_user`.

## Causa Raiz

Falta de idempotência cross-superfície do alarme: (a) nenhuma resolução fora dos botões do alarme cancelava o trigger; (b) a tela cheia não se auto-dismissava para dose já resolvida.

## Fix

1. **Cancel-on-resolve:** `registerDose`/`registerDoseMany` chamam `cancelAlarm(instanceId)` após sucesso, por instância resolvida — **best-effort** (R-245/246, falha nunca bloqueia registro/estoque). `cancelAlarm` já cobre trigger principal + `:nag:N` + soneca (id reusado).
2. **Auto-dismiss:** `AlarmFullScreen` revalida o status das instâncias no mount (`dose_instances.select('id,status').in('id', ids)`); se **nenhuma** está `pending` → `cancelAlarm` + fecha. Grupo: só fecha quando **todas** saíram de `pending`. Falha de leitura **não** fecha a tela (não esconder alarme legítimo por erro de rede).

## Smoke Obrigatório

- Soneca → marcar tomada no FAB/timeline (mesma sessão) → tela cheia **não** reabre em +5min.
- Tela cheia aberta numa dose já resolvida (forçar via web/DevHub) → **fecha sozinha**, sem ação.
- Registro em lote resolve N doses → nenhum alarme remanescente.
- Sem dupla contagem nem `taken→skipped_user` por alarme obsoleto.

## Família

Relaciona a alarmes/notificações e `dose_instances`. Ver também AP-193 (âncora de log por instanceId), AP-217 (medicine_id em dose_instances), AP-230 (lifecycle de instâncias). A unificação web↔mobile do registro (spec 035) deve absorver o hook de cancel-on-resolve.
