# AP-302 — Caminho de produção real não tem nenhum reprocessamento automático; código morto simula que tem

**Domínio:** notifications · **Origem:** hotfix prod (PR #748, evidência via Supabase MCP) · **Data:** 2026-07-16
**Relacionadas:** [[AP-290]] (gate seletivo que não cobre a árvore que promete proteger — mesma classe: existe algo com o nome certo, mas não é o que roda)

## O furo

Usuário reportou erro 503 (Expo push transitório). Investigação por evidência real (Supabase MCP:
`failed_notification_queue`) achou entradas presas sem nenhum retry automático. `server/services/deadLetterQueue.ts`
tem `getPendingForRetry`/`markForRetry` — parecem o mecanismo de reprocessamento. **São código morto:
zero chamadores.** O caminho de produção real (`api/notify.ts` + `api/admin/_handlers/retry.ts`) usa um
`dlqRepo` inline que só grava e serve retry **manual** via admin — nunca reprocessa sozinho.

Gap pré-existente, não introduzido pela 043 (outbox) nem pela 046 (consentimento) — só ficou visível
quando um 503 transitório real produziu uma entrada presa que ninguém drenou.

## Por que passou despercebido

A presença de uma função com o nome certo (`getPendingForRetry`) e sem chamador não dispara nenhum
gate: compila, não quebra teste, não aparece em lint como "não utilizada" se exportada. O caminho real
de produção divergiu silenciosamente do caminho que o nome da função promete.

## Correção

Novo job `dlq_auto_retry` dentro do cron já existente (`api/notify.ts`, bloco 10h, antes de `dlq_digest`)
— zero função serverless nova (R-090). Fecha o reprocessamento no caminho que efetivamente roda em
produção, não no módulo que parecia ser ele.

## Farol

Uma função de retry/reprocessamento sem CALLER no caminho real de produção é sinal — grep por quem
chama antes de assumir que "existe retry" porque o arquivo existe. Investigar incidentes por evidência
de banco (MCP), não por suposição de onde o mecanismo "deveria" estar.
