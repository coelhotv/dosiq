# AP-255 — Gate de canal crítico que só adiciona, nunca restringe → dose crítica vaza pra canais secundários

- **Domínio:** notifications
- **Detectado:** 2026-06-30 (bug prod — usuário viu alarme iOS + Telegram juntos no snooze)
- **Severidade:** alta (duplica aviso de dose crítica; ruído + privacidade)
- **Relacionado:** R-200/R-220 (gate centralizado no dispatcher), AP-215 (read-path), CON-026

## Sintoma

Ao adiar (soneca) uma dose crítica no full-screen do alarme iOS, o re-disparo mandava **push
timeSensitive + Telegram** juntos. Telegram não deveria acompanhar o alarme — é canal do alarme só.

## Causa-raiz

Dois furos compostos em `server/notifications/`:

1. **`resolveChannelsForUser` só ADICIONAVA:**
   ```js
   if (isCritical && activeExpoDevices.length > 0 && !channels.includes('mobile_push')) {
     channels.push('mobile_push')   // adiciona, mas mantém telegram/web_push
   }
   ```
   Para dose crítica, o usuário com telegram+mobile habilitados recebia em AMBOS.

2. **`critical_alarm` ausente do `data` do dispatch** em um dos paths (`_processUserReminderBlock`)
   → `isCritical = data?.critical_alarm === true` era sempre false → nem o "adiciona" rodava.

## Fix

```js
// crítica = extensão do alarme → SÓ canal de alarme, fallback se sem device
if (isCritical) {
  if (activeExpoDevices.length > 0) return ['mobile_push']
  if (hasTelegram) return ['telegram']   // nunca fica mudo
  return []
}
```
+ garantir `critical_alarm` no `data` de TODOS os paths de dispatch de dose.

## Guard

- Teste: crítica + device → `['mobile_push']` (sem telegram); crítica + sem device → `['telegram']`;
  não-crítica → segue preferências (multi-canal).
- `server/notifications/policies/__tests__/resolveChannelsForUser.test.js`.

## Lição

Gate de prioridade/criticidade é **substituição**, não **acréscimo**. "Furar preferências p/
garantir X" deve também **suprimir** os canais que X torna redundantes — senão duplica em vez de
priorizar.
