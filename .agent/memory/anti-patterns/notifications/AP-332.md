# AP-332 — Claim com predicado único sobre estado que dois caminhos gravam de forma diferente

**Severidade:** 🔴 · **Detectado:** 2026-08-20 (RC5 do PR 3 da spec 050, antes do merge)
**Arquivos:** `server/bot/_reminderHelpers.ts` · `packages/core/src/repositories/createDoseInstanceRepository.ts:517` · `server/bot/callbacks/doseActions.ts:419`

## O padrão

Ao transformar "carimba depois do envio" em **claim antes do envio** (`UPDATE ... WHERE <predicado>
RETURNING id` — [[AP-221]] / [[R-288]]), escolhe-se UM predicado a partir da query que alimenta o
caminho feliz. Mas a fila era alimentada por **duas** queries com filtros diferentes, e o estado que
virou predicado é gravado por **dois** produtores com semânticas divergentes:

| Produtor | Grava | `notified_at` |
|---|---|---|
| Telegram (`doseActions.ts`) | `snoozed_until = T` | **zera** |
| Mobile (`setSnoozedUntil`) | `snoozed_until = T` | **preserva** |

A 2ª query do fetch (doses adiadas) não filtra `notified_at` — de propósito. O claim
`.is('notified_at', null)` casava com a 1ª query e **descartava em silêncio** toda soneca vinda do
mobile: reivindica 0 linhas, o código lê "outro worker levou" e não envia. Zero erro, zero teste
vermelho, lembrete de soneca perdido em produção.

## Antídoto

- O claim precisa de **um predicado por população** que a leitura admite — e cada um tem de se
  auto-negar no mesmo UPDATE para continuar sendo claim. Aqui: `notified_at IS NULL` para a dose no
  horário; `snoozed_until IS NOT NULL` para a adiada (o UPDATE zera a soneca).
- **Release restaura TODOS os campos que o claim tocou.** O claim zerava `snoozed_until`; devolver
  só `notified_at` deixava a dose adiada sem marcador e com `scheduled_for` vencido — invisível para
  as duas queries. Trocar duplo teórico por omissão real é piorar ([[R-288]]).
- **Erro de banco ≠ corrida perdida.** Os dois chegam como "zero reivindicado". Sem distinguir, uma
  instabilidade do Postgres vira lembrete não entregue; com `claimError`, degradar para o
  comportamento antigo (envia, carimba depois) preserva a entrega.

## Farol

Antes de promover uma coluna a predicado de claim: `grep` por **todos** os escritores dela e
listar o que cada um faz com as colunas vizinhas; e conferir se a leitura tem mais de uma query —
se tiver, cada query é uma população e precisa do seu predicado.
