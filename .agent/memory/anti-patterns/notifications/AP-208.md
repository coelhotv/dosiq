# AP-208 — Stale device rows acumulam no version bump (fingerprint inclui appVersion)

**Layer:** warm · **Status:** active · **Pack:** notifications / data_and_schema
**Detectado:** Spec 001 (Alarme Nativo) A2, diagnóstico de duplicata, 2026-06-03

## Sintoma

Ao diagnosticar push duplicado, `notification_devices` tem **múltiplos rows
ativos** (`is_active=true`) pro mesmo usuário/plataforma — alguns com o flag novo
(`native_alarm_enabled=true`), outros stale (`false`, `last_seen` antigo). Confunde
o diagnóstico: parece que o gate não pegou, quando na verdade há rows fantasmas.

## Causa

O `device_fingerprint` inclui o `appVersion`. Ao bumpar a versão (0.6.0→0.9.0), o
fingerprint muda → o upsert (conflito por `provider+push_token`) pode criar um
**novo row** (token rotacionado no rebuild) em vez de atualizar o antigo. O row
velho fica `is_active=true` até o Expo retornar `DeviceNotRegistered` e desativá-lo.

## Lição

- Ao investigar entrega de push, filtrar por `last_seen_at` recente — não assumir
  1 row por device. Rows antigos podem ser de versões/installs anteriores.
- Rows de **devices físicos diferentes** (ex.: iPhone 13 vs 15) são legítimos e
  coexistem — não deduplicar por usuário cegamente.
- A auto-desativação via `DeviceNotRegistered` (`shouldDeactivateDevice`) limpa
  tokens mortos com o tempo, mas há janela de duplicata até lá.
- Diagnóstico confiável = inspecionar `device_name`, `app_version`, `last_seen_at`
  e `native_alarm_enabled` por row, não só contar linhas.
