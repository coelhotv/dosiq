# AP-309 — Finding do RC6 sobre linha FORA do diff não vira thread inline → o achado mais raro é o que mais some

**Classe:** processo de revisão · ergonomia de gate
**Origem:** PR #761 (052 Slice A), 2026-07-19
**Severidade:** média (não corrompe dado; corrói o valor do gate)
**Relacionadas:** [[AP-297]] · [[AP-308]] · [[R-060]]

## O que aconteceu

O RC6 do PR #761 devolveu **5 findings**. O script publicou **3 inline** ("3 inline, 0 orphan") — os
3 que apontavam para linhas dentro do diff. Os outros 2 não viraram thread nenhuma e só existiam no
JSON do stdout:

- `createFullLadder` (**high**) — `titrationService.ts:150`, código **não tocado** pelo PR;
- `_prefix` em destructuring (medium, R-093) — linha fora do range ancorável.

O `createFullLadder` era **o melhor achado da revisão inteira**: um quarto caminho de escrita da
classe [[AP-308]] que o inventário do PO-2 não cobria, e que a própria PR agravava (ao congelar a
identidade, transformava um erro transitório de dose em mentira permanente de medicamento).

## Por que isso é pior do que parece

A justificativa do RC6 existir é ser **independente e com contexto completo** — inclusive o arquivo
inteiro, não só o hunk. O `AI_REVIEW.md` chega a instruir: anexar arquivo COMPLETO quando o diff
muda fluxo/aritmética, porque "diff-only é o blind spot #1 do RC6".

Ou seja: gasta-se contexto e quota justamente para que o revisor enxergue além do hunk — e aí o
**canal de saída descarta em silêncio** o que só ele podia ver. O filtro de ancoragem seleciona
contra a classe de achado mais valiosa do gate. Quem lê só as threads do PR conclui "3 findings
mecânicos, revisor fraco" — a leitura oposta da realidade.

Agravante: `0 orphan` no log **soa como cobertura completa**. Não é contagem de descartados, é
contagem de um outro conceito — então o operador não tem sinal de que perdeu 2 de 5.

## Regra

1. **Nunca julgar o RC6 pelas threads inline.** Ler o JSON do stdout (ou o arquivo de saída do
   background task) e conferir `len(findings)` contra o número de comentários publicados. Diferença
   ⇒ há finding sem thread, e ele é, por construção, sobre código não tocado — a classe mais rara.
2. **Finding sem âncora entra na resposta geral do PR**, com o mesmo rigor de veredicto
   (aceito/declinado + evidência) dos que viraram thread. Sem isso ele desaparece do registro.
3. **`introduced:false` não é sinônimo de "não é deste PR".** Perguntar sempre: *este PR muda a
   severidade do achado?* Se o PR piora um caminho pre-existente (congelar dado, ampliar alcance,
   remover um acidente que protegia), ele deixa de ser dívida alheia e passa a ser escopo — ver
   [[AP-308]] §Reincidência, item 3.

## Farol

- `findings` no JSON > comentários no PR ⇒ investigar o delta ANTES de responder.
- Finding cujo `file:line` não aparece no `git diff` do PR ⇒ é candidato a sumir; tratar à mão.
- Revisão que só produz findings mecânicos (`afterEach`, prefixo, formatação) num PR grande é
  suspeita de truncamento ou de descarte de âncora — a mesma desconfiança que o `AI_REVIEW.md` já
  manda ter com "zero findings em diff gordo".
