## Descrição

A spec de execução listava explicitamente um arquivo para modificar, mas a implementação pulou esse arquivo. A falha não foi detectada na C4 Quality Gate porque o agente não verificou sistematicamente cada item do DoD da spec — e o erro de falha foi silencioso em produção (notificações chegavam via caminho legado mas inbox ficava vazio por ~24h).

## Incidente

Sprint N1 (2026-04-26): `EXEC_SPEC_WAVE_N1_GROUPING.md` linha 66 dizia explicitamente:
> "Adicionar cases `'dose_reminder_by_plan'` e `'dose_reminder_misc'` em `buildNotificationPayload:47–79`."

O caminho no checklist de R-193/AP-115 estava errado (`api/notify.js` em vez de `server/notifications/payloads/buildNotificationPayload.js`). O implementador verificou o arquivo errado, não encontrou o problema, e considerou o item concluído. A C4 não cruzou o DoD da spec item a item — apenas rodou os quality gate commands (lint/tests), que passaram porque o código era sintaticamente correto e os testes mockavam o dispatcher.

**Why:** A falha silenciosa (try/catch que engole o erro) escondeu o problema em produção. O bug só foi descoberto 24h depois via inspeção manual do banco de dados.

**How to apply:** Na C4, para CADA arquivo listado no DoD da spec, abrir o arquivo e verificar que a mudança existe — não assumir que "olhei o arquivo e parecia OK".

## Como evitar

1. Na C4, extrair a lista de arquivos do spec e abrir cada um para confirmar a mudança
2. Se o spec aponta para um arquivo e você não encontra a mudança lá, investigar se o spec tem o caminho errado antes de marcar como concluído
3. Para pipelines com falha silenciosa (try/catch que retorna `{ success: false }`): adicionar logging explícito de erro com stack trace em desenvolvimento, e testes de integração end-to-end que verificam o resultado final (notification_log escrito) não apenas o comportamento do dispatcher
4. Qualquer nova função em arquivo separado deve ser referenciada com o caminho canônico no checklist — nunca usar o arquivo que chama a função
