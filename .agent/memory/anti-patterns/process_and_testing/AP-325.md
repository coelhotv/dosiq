# AP-325 — "Tolerar falha" escondendo ausência total

## Sintoma

O perfil de produção do `eas.json` carregava `"SENTRY_ALLOW_FAILURE": "true"`. A leitura natural
disso é *"o upload de símbolos às vezes falha e não queremos que isso derrube um build de 20
minutos"* — uma decisão defensável.

A medição contou outra história. Via API do Sentry (projeto `dosiq-d4/dosiq-app`, 2026-07-30):

```
GET /projects/dosiq-d4/dosiq-app/files/dsyms/         → []
GET /projects/dosiq-d4/dosiq-app/artifact-bundles/    → (vazio)
releases → com.coelhotv.dosiq@0.30.0+3000 existe, recebeu evento, sem nenhum arquivo
```

**Zero.** Não "às vezes falha": nunca funcionou. O token existia e era válido (autenticou e listou
releases pela CLI) — ele simplesmente nunca chegava ao processo de build, porque o `.easignore`
corta todos os dotfiles (`.env` incluído) e o env que o Expo CLI carrega morre com o processo do
`expo prebuild`.

## Por que a flag é o que torna isto caro

Sem ela, o primeiro build teria falhado e o problema seria resolvido em minutos, meses atrás. Com
ela, o sistema **passou a reportar sucesso para uma operação que nunca ocorreu** — e a descoberta
ficou reservada para o dia em que alguém precisasse ler um stack trace de produção. É o padrão da
Constituição §IX (omissão não é neutra) aplicado a uma superfície interna: quem lê o log do build
acredita que subiu.

Com R8 ligado o custo sobe de "inconveniente" para "crash de produção ilegível".

## Farol

- Flag com nome `ALLOW_FAILURE`, `CONTINUE_ON_ERROR`, `|| true`, `ignoreErrors`, `failOnError:
  false` em cima de uma etapa cujo **produto** ninguém verifica depois.
- A pergunta que desarma: *"se isto nunca tivesse funcionado, como eu saberia?"* Se a resposta for
  "não saberia", a flag está escondendo estado, não amortecendo ruído.
- Especialmente perigoso em observabilidade: a ferramenta que deveria contar a verdade sobre falhas
  é a que está falhando em silêncio.

## Fix aplicado (2026-07-30)

- `SENTRY_ALLOW_FAILURE` removido do perfil de produção — falha de upload volta a derrubar o build.
- `apps/mobile/lib-sentry-token.sh`: carrega o token dos `.env` para o processo do build (usado por
  `build-android.sh` e `build-ios.sh`) e **aborta antes** do build de produção se ele não existir —
  falhar em 2 segundos em vez de 20 minutos.

## ✅ Resolvido — 1º build de produção com o fix (2026-08-02, v0.30.1+3001)

O upload **funcionou**. Evidência no log do build (`RUN_GRADLEW`):

```
Task :app:createBundleReleaseJsAndAssets_SentryUpload_com.coelhotv.dosiq@0.30.1+3001_3001
Check generated source map for Debug ID: 903ddee9-7e60-4743-84c3-5bbace5f1022
> Bundle ID: aca088bc-9349-54e7-9b56-573f91882e41
> Uploaded files to Sentry     > Upload type: artifact bundle
```

Confirmado no servidor: bundle `aca088bc…`, 2 arquivos, associado a
`com.coelhotv.dosiq@0.30.1+3001` / dist `3001`.

## 🔴 A VERIFICAÇÃO QUE ESTE AP PRESCREVIA ESTAVA ERRADA

A versão anterior mandava conferir `files/dsyms/`. **Isso não detecta sourcemap de JS.**
Consultando ali (e em `releases/<rel>/files/`, que é o formato LEGADO), o resultado foi `0` mesmo
com o upload bem-sucedido — e a conclusão foi *"o Sentry continua quebrado"*, oposta ao fato.
São três superfícies distintas no mesmo produto:

| O que você quer saber | Endpoint | Quem alimenta |
|---|---|---|
| sourcemap JS/Hermes | `files/artifact-bundles/` | `@sentry/react-native` (task `SentryUpload` no gradle) |
| símbolo nativo (dSYM/ProGuard) | `files/dsyms/` | Sentry **Android** Gradle Plugin / upload-dif |
| formato legado por release | `releases/<rel>/files/` | uploads antigos; hoje volta vazio mesmo funcionando |

```bash
# a consulta CERTA para sourcemap JS:
curl -s -H "Authorization: Bearer $SENTRY_AUTH_TOKEN" \
  "https://sentry.io/api/0/projects/dosiq-d4/dosiq-app/files/artifact-bundles/"
```

**A lição vale além do Sentry** e é a mesma que o AP original ensina, aplicada contra quem o
escreveu: *"medi o efeito"* só conta se a medição olhar onde o efeito aparece. Endpoint errado
produz um zero tão convincente quanto o do bug real. Quando existir, o **log do build é a evidência
direta** — pedir o log custa menos que inferir do estado final.

## Lacuna que permanece: mapping do R8 não sobe

Nenhuma task de upload de ProGuard mapping aparece no log — só `SentryUpload` (sourcemaps) e
`SentryCollectModules`. O `@sentry/react-native` cobre o JS; mapping nativo exigiria o
`io.sentry.android.gradle`, **não aplicado**. Com R8 ligado desde a v0.30.1: crash de **JS** chega
legível; crash **Java/Kotlin nativo** chega ofuscado.
