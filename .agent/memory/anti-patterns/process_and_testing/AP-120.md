# AP-120 — Refactoring by Purgue (Over-cleaning)

## Problem

Remover grandes blocos de código (1000+ linhas) em orquestradores centrais (ex: `tasks.js`, `notify.js`) sob o pretexto de "limpeza de legado", sem realizar uma análise de impacto 360º. Isso resulta na remoção acidental de fluxos ativos que não possuem cobertura de teste unitário exaustiva ou que dependem de configurações externas (Cron Jobs, Webhooks).

## Evidence

- **Sprint 2026-W18 (Wave N2):** Um agente removeu todo o bloco de orquestração de resumos diários (Digest) e alertas de estoque de `tasks.js` acreditando que a lógica estava 100% no Dispatcher.
- **Impacto:** O cron job da Vercel continuava chamando os endpoints, mas o código que deveria traduzir o trigger em um dispatch havia sido deletado, silenciando os alertas proativos e o digest matinal por 24h.

## How It Happens

1. O agente identifica uma nova arquitetura (ex: ADR-030).
2. O agente assume que o código antigo é 100% redundante.
3. O agente executa um "delete massivo" para "limpar a casa".
4. O agente esquece que o Dispatcher é um *executor*, mas os orquestradores ainda precisam *chamar* o executor com os dados corretos (Trigger -> Orchestrator -> Dispatcher).

## Prevention

1. **Keep-and-Deprecate:** Em refatorações estruturais, prefira comentar ou marcar como `@deprecated` antes de deletar, até que a integração final seja validada em staging/produção.
2. **Contract Checklist:** Antes de deletar código orquestrador, verifique:
   - Quais Cron Jobs chamam este arquivo?
   - Quais Webhooks batem neste arquivo?
   - Há testes de integração que cobrem a ponta inicial do trigger?
3. **Atomic Purgue:** Se for deletar, faça em PRs de limpeza separados após a migração funcional estar provada, nunca no mesmo PR da migração.
