# AP-234 — Commit de docs direto na main durante branch aberta → squash-merge apaga

**Status:** ✅RESOLVED-processo (incidente 033/035, 2026-06-16) · **Layer:** hot · **Domain:** process_and_testing
**Descoberto:** 2026-06-16 (draft spec 035 desapareceu após squash-merge do PR #671)

## Contexto

Workflow oficial do dosiq permite commit de docs (specs, `.agent/memory`) **direto na main**
sem branch/PR ([[feedback_docs_commit_direct_main]]). Em paralelo, features rodam em branches
de longa duração com squash-merge via GitHub.

## O anti-pattern

Com uma feature-branch **aberta**, commitar docs na main (ex.: `plans/specs/035/`) cria um
arquivo que a branch **não conhece** (nasceu de um branch-point anterior). Ao squash-mergear
a branch, o GitHub aplica a **árvore inteira da branch** sobre a main — e remove tudo que
entrou na main depois do branch-point e não existe na branch.

```
main:    A ── 035(B) ─────────── squash-merge #671 (C)   ← C apaga 035!
                \                /
branch:          A ──033 work──/   (nunca teve 035)
```

Incidente real: draft 035 (commit `52b195fe`) + linha no README sumiram no squash `bb54774b`.
Falha silenciosa — nenhum conflito, nenhum aviso. Pior em trocas de contexto / multi-agente,
onde ninguém lembra que a main divergiu da branch.

## Fix / Regra

Ao commitar docs na main **enquanto uma feature-branch está aberta**, escolher UMA:

1. **Rebase a branch na main logo após o commit de docs** (preferido — usuário):
   ```bash
   git checkout <feature-branch> && git rebase main
   ```
   Traz o doc pra dentro da branch; squash-merge não pode mais removê-lo.
2. **Adiar o commit de docs** até o merge da branch.
3. **Verificar `git ls-tree -r <merge-commit> | grep <doc-path>`** no C5 pós-merge (rede de segurança).

**Recuperação:** o arquivo vive no histórico — `git checkout <commit-original> -- <path>` + re-commit.
