# [AP-203] Time-travel de dev vaza para escritas (taken_at no futuro)

**Status:** active · **Layer:** warm · **Domain:** process_and_testing
**Criado:** 2026-06-01 (smoke F4.3e)

## Sintoma
Conta de smoke com doses `taken` cujo `scheduled_for`/`taken_at` estão no FUTURO real
(ex.: dose de "hoje 23:50" marcada tomada às 14h). Travas do produto não barram porque,
do ponto de vista do app, "agora" era o instante deslocado.

## Causa
O override de time-travel de dev (F4.3e — `__setDevNowOffsetMs` deslocando
`getNow`/`getRawNow`/`getTodayLocal`) é lido também pelo **write-path**: `registerDose`
deriva `taken_at` de `getNow()`. Com o offset ativo (ex.: onda pós-meia-noite, +X min),
o `taken_at` gravado cai no futuro real e o snap ancora numa `dose_instance` de horário
futuro → `status='taken'` em ocorrência que ainda não aconteceu. Persiste no DB
(compartilhado) mesmo depois de remover o offset.

## Regra
- Time-travel de smoke: usar **conta descartável** dedicada (raio mínimo).
- Ao fim do smoke, **limpar** os artefatos: `medicine_logs WHERE taken_at > now()` +
  reverter `dose_instances` ancoradas (`status='pending'`, `medicine_log_id=NULL`).
- **NUNCA** mexer no relógio do SO p/ simular: quebra a validação do JWT do Supabase
  (token "expirado" → loop de refresh → **429**; auth/escritas falham, ex.: "Pular tour"
  travado). Usar o offset no app (não toca `Date.now` global) — auth fica intacta.
- O override fica **gated `__DEV__`/`import.meta.env.DEV`** → no-op em produção.

## Detecção
```sql
SELECT count(*) FROM public.dose_instances WHERE status='taken' AND scheduled_for > now();
SELECT count(*) FROM public.medicine_logs WHERE taken_at > now();
```
