# AP-269 — Afirmação de runtime não verificada em comentário de código propaga e envenena o review

**Domínio**: process_and_testing · **Descoberto**: 2026-07-06 (040 F5 gate, PR #725) · **Severidade**: baixa-média (custo de review + risco de "fix" errado)

## Sintoma

Sessão de lote bateu em TS2305/TS2724 com named imports do lucide-react-native e escreveu em comentário: *"CheckCircle2 nem existe em runtime — bug pré-existente preservado"*. A afirmação era **falsa**: `CheckCircle2`/`Edit3` são aliases deprecated que EXISTEM no bundle instalado (`dist/cjs/lucide-react-native.js` → `exports.CheckCircle2 = circleCheck`) — o gap é só no `.d.ts`.

O comentário se replicou por 3 arquivos (copy-paste entre lotes) e o Gemini o leu como fato → 2 sugestões **high** no PR consolidado propondo "fix" de um crash que não existe. Se aplicadas cegas (AP-266), teriam trocado ícones sem necessidade.

## Por que escapou

Erro de TYPES (TS2305) foi interpretado como erro de RUNTIME sem checar. A verificação custa 10s:

```bash
grep -o "exports.CheckCircle2 = .*" node_modules/lucide-react-native/dist/cjs/*.js
```

## Regra de prevenção

1. Comentário de código só afirma comportamento de runtime que foi VERIFICADO (grep no dist instalado, node -e, teste). Senão, escrever o que se sabe: "TS2305 no .d.ts; runtime não verificado".
2. TS2305/TS2724 = símbolo ausente nas DECLARAÇÕES. Não implica ausência no runtime — deprecated aliases e re-exports dinâmicos são invisíveis pro `.d.ts`.
3. Revisor de IA trata comentário de código como fonte de verdade — comentário errado gera review errado em cascata (dual do AP-266: lá o dev confiou no revisor; aqui o revisor confiou no dev).
