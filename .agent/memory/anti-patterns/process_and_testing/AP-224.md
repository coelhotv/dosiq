# AP-224 — `git stash` com sub-agente ativo escrevendo no working tree

**Layer:** hot · **Status:** active · **Created:** 2026-06-10 · **trigger_count:** 1
**Tags:** git, subagents, orchestration, stash, worktree

## O que aconteceu (012 Fase A, 2026-06-10)

Main thread rodou `git stash` para um baseline-check de lint enquanto um sub-agente
(UI mobile) ainda editava arquivos no MESMO working tree. Efeitos em cascata:
1. O stash capturou o trabalho parcial do sub-agente (arquivos "sumiram" sob ele).
2. O sub-agente continuou editando sobre o baseline — re-fez parte do trabalho (v2),
   divergindo da v1 presa no stash.
3. `git stash pop` falhou (conflito com os arquivos re-editados), exigindo
   reconciliação manual seletiva (`git restore --source=stash@{0}` arquivo a arquivo,
   mantendo v2 do agente nos sobrepostos).

Custo: ~10 min de reconciliação + risco real de perda de trabalho.

## Regra

- **NUNCA** `git stash` (ou qualquer operação que mude o working tree: checkout,
  reset, pull) enquanto houver sub-agente ativo escrevendo no mesmo tree.
- Baseline-check de lint/teste contra a main: usar `git worktree` isolado, ou
  rodar ANTES de spawnar, ou comparar via `git diff main -- <files>` (read-only).
- Se inevitável: aguardar todos os agentes concluírem primeiro.

## Recuperação (se acontecer)

1. NÃO popar com agente ainda ativo — esperar concluir.
2. Inventariar: `git diff stash@{0}^..stash@{0} --name-only` × `git status`.
3. `git restore --source=stash@{0} -- <arquivos só-do-stash>`; manter working
   (versão final do agente) nos re-editados; mesclar manualmente interseções.
4. Verificar consistência cross-versão (props/contratos entre arquivos v1×v2) no C4.
