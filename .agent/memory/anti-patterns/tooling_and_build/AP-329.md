# AP-329 — Script de regen com `>` trunca o arquivo VERSIONADO antes de o comando existir

**Categoria**: tooling_and_build · **Severidade**: alta · **Detectado**: 2026-08-17 (spec 067 A2)

## O que aconteceu

`npm run supabase:types` é:

```json
"supabase:types": "npx supabase gen types typescript --project-id <ref> > packages/shared-data/src/database.types.ts"
```

O shell abre o redirecionamento **antes** de executar o comando: `database.types.ts` (2.129 linhas,
versionado, consumido por `apps/web`, `apps/mobile`, `server/` e `api/`) foi **zerado no instante 0**.
Em seguida o `npx supabase` — que não estava instalado e exige login — ficou pendurado baixando o CLI
e esperando autenticação, sem nunca escrever nada. Resultado: arquivo de contrato de tipos com
**0 bytes** e um processo travado. Só apareceu porque eu conferi `wc -c` no arquivo; um `git status`
mostrava apenas ` M` — modificação, indistinguível de um regen bem-sucedido.

## Por que é perigoso além do susto

- O dano é **imediato e silencioso**: qualquer `tsc`/build rodado nessa janela falha por um motivo
  que não tem relação com o que se estava fazendo, e a investigação vai para o lado errado.
- Se a sessão tivesse sido interrompida ali (timeout, `/clear`, máquina), o commit seguinte
  carregaria um `database.types.ts` vazio — o `tsc` do web pegaria, mas só depois de o dev perder
  tempo com erros em cascata em arquivos que ele não tocou.
- O mesmo padrão existe em qualquer script `<gerador> > <arquivo versionado>`: `gen types`,
  `openapi`, `graphql codegen`, dumps de schema.

## Antídoto

Escrever em temporário e mover só no sucesso — o `&&` é o gate:

```json
"supabase:types": "npx supabase gen types typescript --project-id <ref> > /tmp/db.types.ts && mv /tmp/db.types.ts packages/shared-data/src/database.types.ts"
```

Alternativa usada nesta sessão (sem depender do CLI): `mcp__supabase__generate_typescript_types` +
escrita do payload no arquivo. O diff resultante foi de **3 linhas** (Row/Insert/Update da coluna
nova), que é a evidência que a [[R-289]] pede — e um diff pequeno também é o farol de que o regen
saiu certo.

## Farol

- Script de package.json com `>` apontando para caminho **dentro do repo**.
- Gerador que exige rede/login (`npx <cli> gen ...`): a probabilidade de falhar DEPOIS de truncar é alta.
- `git status` mostrando ` M` num arquivo gerado + build quebrando em arquivos não tocados ⇒ conferir
  `wc -c` antes de investigar o build.

## Recuperação

`git checkout -- <arquivo>` (era versionado e limpo). Se já estivesse modificado de propósito antes
do regen, o conteúdo anterior estaria perdido — mais um motivo para o temporário.

Ver [[R-289]] · família [[AP-275]] (default privileges) não; família de **ferramenta que destrói
antes de validar**: irmã de [[AP-318]] (gate que não cobre o artefato real).
