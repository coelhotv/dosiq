# AP-320 — Env de controle de segurança lida em escopo de módulo depende da ORDEM DE IMPORT

**Classe:** infra_and_deploy · **Severidade:** média (aqui falhou fechado; a classe pode falhar aberto)
**Detectado:** 2026-07-25, spec 051-A PR 1.5a, ao executar o PO-SEC-4 (fail-closed do `verifyAdminAccess`)
**Relacionados:** [[AP-278]] (proteção por acidente) · ADR-091 D10 · R-042

## O que aconteceu

`server/utils/auth.ts` e `api/admin.ts` liam a MESMA variável em escopo de módulo:

```ts
const adminUserId = process.env.ADMIN_USER_ID;   // topo do arquivo, nos dois
```

Rodando localmente sem a env, o comportamento foi **incoerente entre os dois arquivos**: o
`verifyAdminAccess` viu `undefined` (e negou, corretamente), enquanto o guard de configuração de
`api/admin.ts` viu o valor preenchido (e deixou passar). Resultado observado: `401` do auth em vez do
`500` de configuração — dois arquivos, duas verdades sobre a mesma env, no mesmo processo.

Causa: `api/admin.ts` importa `../server/services/deadLetterQueue.js`, que carrega **`dotenv`
transitivamente**. A ordem de avaliação ESM roda os módulos importados antes do corpo do importador:

```
auth.ts (import na linha 7)   → lê process.env → undefined
deadLetterQueue (linha 13)    → dotenv injeta o .env → ADMIN_USER_ID passa a existir
api/admin.ts (corpo)          → lê process.env → preenchida
```

Provado com um probe explícito:

```
A antes do loop: undefined
B depois do loop: undefined
C depois de auth.ts: undefined
[dotenv@17] injecting env (1) from .env
D depois de deadLetterQueue: b0c9746c-...
```

## Por que importa mesmo tendo falhado para o lado seguro

Em produção (Vercel) as env vars existem antes do processo subir, então não havia impacto — e a
divergência local negou o acesso, que é a direção segura. Mas "seguro porque o import certo veio
primeiro" é literalmente o [[AP-278]]: proteção por **acidente de ordenação**, não por controle. Um
reorder de imports, um `import` novo que carrega dotenv mais cedo, ou um script que monta o env
manualmente muda o valor que o controle enxerga — sem tocar no controle.

Corolário desagradável: a mesma mecânica poderia fazer um guard ler uma env **preenchida** em um
contexto e vazia em outro, e o modo de falha oposto (liberar) é indistinguível no código.

## Fix

Ler a env **na chamada**, não no escopo do módulo, em qualquer código que decide acesso:

```ts
function readConfig() {
  return {
    supabaseUrl: process.env.VITE_SUPABASE_URL || process.env.SUPABASE_URL,
    supabaseAnonKey: process.env.VITE_SUPABASE_ANON_KEY || process.env.SUPABASE_ANON_KEY,
    adminUserId: process.env.ADMIN_USER_ID,
  };
}

export async function verifyAdminAccess(authHeader) {
  const { supabaseUrl, supabaseAnonKey, adminUserId } = readConfig();
  if (!adminUserId) return { authorized: false, error: DENIED };  // fail-closed
  // ...
}
```

Custo: um objeto por request. Ganho: o valor deixa de depender de quando o módulo foi avaliado.

## Gate

O fail-closed **não é demonstrável num harness local**: `dotenv@17` sobe a árvore de diretórios e
reinjeta o `.env` do repositório, então "rodar sem a env" exigiria renomear o `.env` do
desenvolvedor. Encodar como teste, com a ausência construída de forma determinística:

```ts
vi.stubEnv('ADMIN_USER_ID', '')
expect((await verifyAdminAccess('Bearer token-valido')).authorized).toBe(false)
expect(getUserMock).not.toHaveBeenCalled()   // nega ANTES de qualquer trabalho
```

(`server/utils/__tests__/auth.test.ts`, 18 casos — inclui S-12/mensagem uniforme e AP-216.)

## Farol

- `const X = process.env.ALGO` no topo de arquivo que decide **autorização**, **grant** ou **rota
  privilegiada**.
- Mesma env lida em dois módulos do mesmo processo com resultados diferentes: pare e olhe quem
  carrega `dotenv` no grafo de import.
- Teste de "env ausente" que passa por acidente porque o harness nunca conseguiu remover a env de fato.
