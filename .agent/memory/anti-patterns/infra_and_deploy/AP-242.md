# AP-242 — URL/subdomínio do Supabase hardcoded em repo opensource

**Categoria:** infra_and_deploy · **Detectado:** smoke 037 Slice 2 (2026-06-23)

## Sintoma

O subdomínio do projeto Supabase (`https://<id>.supabase.co/...`) aparecia literal
no código de app e em scripts, num repositório **opensource público**:
- `apps/mobile/src/shared/hooks/useMedicineDatabase.js` — base URL da base ANVISA
- `scripts/analyze-notifications.js` — client Supabase

Isso vaza o id do projeto para qualquer um que leia o repo e acopla o código a um
ambiente específico (não dá pra apontar um fork/staging para outro projeto).

## Causa

Conveniência: copiar a URL pronta em vez de puxar do mecanismo de env já existente
no projeto. O resto do app já lia de env — o hardcode era um ponto fora da curva.

## Fix

Ler sempre de variável de ambiente, seguindo o padrão por plataforma:
- **Mobile (Expo):** `process.env.EXPO_PUBLIC_SUPABASE_URL` via `nativePublicAppConfig.supabaseUrl`
- **Web (Vite):** `import.meta.env.VITE_SUPABASE_URL`
- **Scripts (Node):** `process.env.SUPABASE_URL` (com fallbacks `VITE_*`/`EXPO_PUBLIC_*`)

```js
// ❌ const BASE = 'https://<id>.supabase.co/storage/v1/object/public/...'
// ✅
const BASE = `${nativePublicAppConfig.supabaseUrl}/storage/v1/object/public/...`
```

## Guard

- Antes de commitar em repo público: `git grep -n '\.supabase\.co' -- ':!*.map'`.
  Resultados aceitáveis = só docs/audit-trail (comentários de evidência). **Código = nunca.**
- Novo endpoint que monta URL do backend → derivar do config de env, não literal.
- Vale para qualquer segredo/endpoint de ambiente (chaves, webhooks, buckets).
