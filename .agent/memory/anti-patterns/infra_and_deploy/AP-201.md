# [AP-201] 🔒 CREATE OR REPLACE VIEW reseta security_invoker → bypassa RLS (vazamento cross-usuário)

**Status:** active · **Layer:** hot · **Domain:** infra_and_deploy
**Criado:** 2026-05-31 (PR-F4.1 / Fase 4 S4.2b — smoke b0c9746c)

## Sintoma
Após `CREATE OR REPLACE VIEW` numa view sobre tabela com RLS, o client passa a ver dados
de **outros usuários** misturados — no caso, `v_adherence_heatmap` retornava linhas
duplicadas por `(day_of_week, period_index)` (uma por usuário dos 15). O consumidor
(`grid[dow][period] = row`) sobrescrevia a célula com a última linha (frequentemente de
outro usuário, 0%) → heatmap com células 0% e "pior horário" errado; sparkline idem.

**Enganoso:** parecia cache stale — sobreviveu a Cmd+Shift+R, restart do dev server e
`localStorage.removeItem`. Só a **resposta crua do Network** (linhas duplicadas por chave)
revelou que a própria view retornava multi-usuário.

## Causa
`CREATE OR REPLACE VIEW` **reseta o reloption `security_invoker` para `false`** (Postgres
não preserva reloptions não declarados no replace). View sem `security_invoker` roda com a
permissão do **OWNER** (postgres) → **bypassa a RLS** das tabelas-base
(`dose_instances.dose_instances_owner: user_id = auth.uid()`). Os consumidores web
(`getDailyAdherenceFromView`/`getAdherencePatternFromView`) consultam as views **sem filtro
`user_id`**, confiando na RLS para escopar — que deixou de aplicar.

## Regra
Toda view sobre tabela com RLS DEVE declarar `WITH (security_invoker = true)` — tanto no
CREATE quanto reafirmado após qualquer `CREATE OR REPLACE`. Validar escopo simulando o
papel autenticado:
```sql
SET LOCAL role authenticated;
SELECT set_config('request.jwt.claims', '{"sub":"<uid>","role":"authenticated"}', true);
SELECT count(DISTINCT user_id) FROM public.<view>;  -- deve ser 1
```
