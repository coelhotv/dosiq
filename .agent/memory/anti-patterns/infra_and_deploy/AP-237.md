# AP-237 — Endpoint de LLM sem auth + system prompt montado no cliente

**Domínio:** infra / serverless / segurança
**Detectado:** 2026-06-22 (endurecimento do Chatbot IA, parte A)

## Sintoma

`api/chatbot.js` (Groq) era **público** (sem autenticação) e recebia o `systemPrompt`
**inteiro montado no cliente** (`chatbotService.js` enviava `{ message, history, systemPrompt }`).

Dois vetores:
1. **Abuso de quota**: qualquer um podia `POST /api/chatbot` anonimamente e queimar a quota
   Groq (free tier com RPD/TPD baixos) — custo/DoS.
2. **Bypass de guardrails**: como o cliente controlava o `systemPrompt`, um POST direto podia
   **remover as "REGRAS ABSOLUTAS"** (SaMD, grounding, disclaimer) e fazer o LLM responder
   fora dos limites clínicos. O safety guard e o rate limit também eram **só client-side**.

## Causa

Endpoint de IA tratado como utilitário stateless de proxy ao Groq, confiando no cliente para
montar o prompt e para se autolimitar. Camada de confiança no lugar errado.

## Correção (padrão)

- **Auth obrigatória** no endpoint: Supabase JWT (`Authorization: Bearer` → `supabase.auth.getUser`,
  padrão `share.js` / R-042). Sem token → 401. Atribui requisições a um usuário (habilita rate limit real).
- **System prompt composto NO SERVIDOR**: o cliente envia apenas `patientContext` (dados, sem PII/IDs);
  as regras vêm de uma fonte única sem dependências (`chatbotConfig.buildSystemPrompt`) e são
  **prepended no servidor**. O cliente nunca controla as regras de segurança.
- **Safety guard + rate limit server-side**: revalidar padrões bloqueados e limitar por `userId`
  (Map em memória, padrão `beta-signup`) no próprio endpoint — defesa em profundidade.

## Regra geral

Todo endpoint que chama um LLM (custo + guardrails de segurança) DEVE: exigir auth, montar o
system prompt/instruções de segurança no servidor (nunca confiar no cliente), e aplicar
rate limit + content guard server-side. Validação só no cliente é UX, não segurança.
