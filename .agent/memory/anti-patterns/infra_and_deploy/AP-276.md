# AP-276 — Claim de fila sem transição de status → re-claim concorrente pós-commit (envio duplicado)

**Categoria**: infra_and_deploy
**Severidade**: 🔴 Furo de arquitetura (concorrência)
**Detectado**: 043 Slice A (2026-07-10) — só por revisor externo (Gemini #734 re-review), não pelo raciocínio do agente principal
**Relaciona**: [[R-288]] (trace de interleaving), AP-259 (mock esconde bug no predicado SQL), R-281

## O bug

```sql
-- ERRADO: claim reivindica mas deixa status='pending'
UPDATE notification_outbox SET attempts = attempts + 1
 WHERE id IN (SELECT id FROM notification_outbox WHERE status='pending'
              ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 25)
RETURNING *;
```

`FOR UPDATE SKIP LOCKED` dá exclusão **só dentro da transação do RPC**. Assim que o RPC commita,
o lock solta e a linha continua `status='pending'`. Durante o **dispatch assíncrono** (fora da
txn), um segundo drenador/tick concorrente reivindica a MESMA linha → **efeito duplicado**
(notificação enviada 2×). A UNIQUE `(user_id,kind,period_key)` NÃO protege — não é insert
duplicado, é a mesma linha processada 2×.

SKIP LOCKED resolve **contenção de claim dentro da txn**. NÃO resolve **posse exclusiva através
da janela de processamento**. São coisas diferentes; confundi-las é o furo.

## Por que passou (raciocínio do agente — causa-raiz)

1. **Pattern-match no primitivo**: "drenar fila → SKIP LOCKED" tratado como completo. Escopo de
   proteção errado.
2. **Não tracei lock-lifetime × processing-lifetime**: o bug mora no vão entre commit (lock solta)
   e markSent (fim). Nunca desenhei a linha do tempo de 2 workers.
3. **Gate de failure-modes cobria só inputs degenerados** (null/0/boundary), não **interleaving
   temporal/concorrência**. Faltava a linha "2 instâncias intercaladas".
4. **Mock do primitivo sob prova**: o teste mockou `claim` → a propriedade de concorrência foi
   ASSUMIDA, nunca exercida (o bug vive na semântica SQL que o mock abstrai — família AP-259).
5. **"Deploy neutro" (flag off) baixou a guarda** — corretude não escala com o flag.

## Fix (correto, além do mínimo)

```sql
-- claim marca 'processing' + claimed_at na MESMA txn (posse exclusiva) e RECUPERA stuck
UPDATE notification_outbox SET attempts = attempts + 1, status='processing', claimed_at=now()
 WHERE id IN (SELECT id FROM notification_outbox
              WHERE status='pending'
                 OR (status='processing' AND claimed_at < now() - interval '15 minutes')
              ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 25)
RETURNING *;
```

- `status='processing'` tira a linha do conjunto reivindicável enquanto o envio roda.
- **Recuperação de stuck** (`processing` preso > N min): sem isso, um worker que crasha entre
  claim e finalize deixa a linha em `processing` PARA SEMPRE (nunca re-reivindicada) → troca
  "envio duplicado" por "envio perdido". `processing` sem timeout é um novo bug, não um fix.
- `revertClaim`/`markFailed` voltam a `pending` limpando `claimed_at`.

## Guard

- Todo design de **fila/claim/drenador/estado mutável compartilhado**: aplicar o **trace de
  interleaving** de [[R-288]] ANTES de codar (2 workers, estado da linha a cada passo).
- Claim SEMPRE transiciona status para um estado de posse (`processing`/`in_flight`) na mesma
  txn + recuperação de stuck com timestamp de claim.
- NÃO provar concorrência com mock do claim — precisa de integração contra o DB real ou, no
  mínimo, um artefato de raciocínio explícito sobre a fronteira transacional.
