# AP-256 — Cliente HTTP/2 de saída (APNs) sem timeout em serverless pendura a função até o limite da plataforma

- **Domínio:** infra_and_deploy
- **Detectado:** 2026-07-01 (review Gemini PR #696 — cliente APNs push-to-start, spec 041)
- **Severidade:** alta (função Vercel travada consome execução até timeout, atrasa/derruba o loop de lembretes)
- **Relacionado:** R-088 (fail-closed em env), R-090 (server/ fora do budget), ADR-076, CON-030

## Sintoma

`http2.connect()` + `client.request()` para `api.push.apple.com` sem nenhum timeout. Se a Apple
demora ou a conexão falha silenciosamente, a `Promise` fica pendente **indefinidamente**. Em
serverless (Vercel) a função executa até o teto da plataforma — desperdício e, pior, atrasa o
fluxo principal (o disparo roda dentro do cron de minuto do `checkReminders`).

## Causa-raiz

Confiar nos eventos `error`/`end` do stream como únicos terminadores. Nem toda falha emite um
deles (ex.: conexão TCP estabelecida mas servidor muda). Sem um relógio próprio, nada resolve.

## Fix

```js
const timer = setTimeout(() => {
  try { client?.close() } catch { /* noop */ }
  resolve({ ok: false, status: 0, reason: 'timeout' })  // fail-open: caller degrada
}, APNS_TIMEOUT_MS)               // 5000
const safeResolve = (val) => { clearTimeout(timer); resolve(val) }
// usar safeResolve em TODOS os caminhos (connect_failed/client_error/end/request_error)
```

## Guard

- Todo cliente de rede de saída em `server/`/`api/` (http2/fetch/socket) DEVE ter timeout explícito
  e resolver fail-open quando o caminho não é o canal garantido (aqui: alarme T0 cobre).
- `safeResolve` (clearTimeout + resolve) em cada terminador — nunca `resolve` cru após instalar o timer.

## Lição

Em serverless, "sem timeout" não é "espera um pouco mais" — é "segura um slot de execução até o
teto". Todo I/O de saída precisa de um relógio próprio; o SO/stream não garante terminação.
