# AP-259 — Query de janela temporal como fatia de 1 minuto exata → perde linhas fora do tick

**Categoria:** infra_and_deploy · **Detectado:** debug do trail 042 (dispatchLiveActivityStarts, spec 041)

## Sintoma
Um cron por-minuto seleciona trabalho por uma **fatia de 1 minuto exata** deslocada (`scheduled_for ∈ [now+lead, now+lead+1min)`). Consequência: qualquer alvo cujo instante-gatilho (`T−lead`) já passou **nunca casa** — ex.: uma `dose_instance` crítica criada/editada para tocar em `<lead` minutos (o `T−lead` dela está no passado). Também perde silenciosamente se o cron pular exatamente aquele minuto. No caso: LA push-to-start nunca disparava para doses de curto prazo → `la_push_started_at`/`la_push_state` = 0 em todo o histórico, e o app fechado ficava sem Live Activity (o alarme T0 ainda tocava — degradação, não perda total).

## Por que passa despercebido
- Testes com mock que **ignora o filtro** de `scheduled_for` (retorna a linha independentemente da janela) passam — o bug vive no predicado SQL, não no fluxo.
- Só aparece com dose criada/editada dentro do horizonte, app fechado — cenário de campo, não de smoke.

## Fix
Janela = **intervalo** `[now, now+lead]` (não fatia de 1min): `scheduled_for >= now AND scheduled_for <= now+lead`, com uma **trava de idempotência** (`la_push_started_at IS NULL`) para não re-disparar nos ticks seguintes. Assim o alvo entra assim que cruza o horizonte, no próximo tick, resiliente a minutos pulados.

## Guard
- Cron periódico que seleciona trabalho por tempo: preferir **range aberto até o horizonte** + trava de idempotência, nunca fatia de minuto exato — a menos que o gatilho seja garantidamente pontual E o tick nunca falhe.
- Teste com mock que **captura os limites** (`gte`/`lte`) e filtra por eles, provando que um alvo dentro do horizonte (não no minuto exato) entra.
- Emitir sinal observável (audit/log) quando o push/ação falha, não só no sucesso — senão o "nunca aconteceu" fica invisível (ver push_failed no lifecycle).
