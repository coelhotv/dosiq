# R-314 — Elegibilidade OTA vs build de loja [CRITICAL]

## Rule

O `eas update` empacota **qualquer** JS que compile. Ele não sabe — e não tem como saber — se aquele
JS é uma correção dentro do propósito já revisado ou uma feature nova que a loja nunca viu. Essa
decisão é humana, é de **compliance**, e tem que acontecer **no SQP (R-221 §4c), antes do código
existir** — não no momento do publish, quando já há pressão para entregar.

### §1 — Três destinos, não dois

| Destino | Quando | Efeito em `APP_VERSION` |
|---|---|---|
| **OTA** (`eas update`) | correção de bug JS, ajuste de UI/cópia, iteração **dentro do propósito já revisado** | **NÃO bumpa** — bump = runtime novo = update órfão (ADR-082) |
| **Build de loja** | qualquer nativo/SDK **ou** qualquer feature nova / mudança de propósito | bumpa (R-221 §4) + tag `mobile-v<X.Y.Z>` (R-307) |
| **Kill switch / versão mínima** | o bug já em campo é grave e OTA **não alcança** o parque | nenhum — é operação, não release |

⚠️ **A pergunta não é "cabe no bundle?", é "a loja já revisou este propósito?"** As duas respostas
divergem exatamente no caso perigoso.

### §2 — Obriga build de loja (sem exceção)

1. **Código nativo, SDK do Expo, `ios/`, `android/`, plugin de build, permissão nova, dependência com
   parte nativa.** OTA não substitui binário: JS novo chamando nativo que o binário instalado não tem
   é **crash imediato** no usuário, não erro de build.
2. **Feature nova ou mudança de propósito do app**, ainda que 100% JS. É o que a **Apple Guideline
   3.3.1** proíbe entregar por código interpretado.
3. **Qualquer coisa que mude a superfície declarada na ficha de loja** (categoria, claims de saúde,
   permissões descritas, política de privacidade).

### §3 — PROIBIDO: embarcar inativo para "ligar depois"

Publicar por OTA (ou embutir no build) código de feature nova **desligado por flag**, para ativar
remotamente sem revisão, é o padrão que a 3.3.1 nomeia. Não vira legítimo por estar atrás de flag —
a flag **é** o mecanismo que a diretriz descreve.

Vale para os dois mecanismos que temos à mão: feature flag do PostHog **e** condicional de código no
bundle. O rollout gradual legítimo existe e é outro: **`--rollout-percentage` do EAS**, que gradua
*quem recebe o bundle já elegível*, não *o que o bundle liga*.

🔴 **Escrutínio extra do Google Play para app de saúde:** código interpretado carregado em runtime
não pode habilitar violação de política. Numa categoria de saúde, "descobriram depois" custa a conta,
não um aviso — e desde 2026-08-21 a **liability é da empresa** (CNPJ), não de pessoa física.

### §4 — Tocou nativo ⇒ o runtime muda, e isso é o gate técnico

Sob `runtimeVersion: appVersion` (ADR-082), bumpar `APP_VERSION` cria um runtime novo: OTA publicado
nele **não alcança nenhum binário instalado**. Portanto:

- mudou nativo ⇒ bump ⇒ **só build de loja entrega** aquela mudança. Não existe "OTA por cima";
- inversamente, um "patch" que bumpe a versão sem build de loja nasce **órfão** — publica sem erro,
  não chega em ninguém, e o silêncio parece sucesso.

### §5 — Limite de alcance (não é compliance, é física)

OTA só alcança binário que embute o cliente `expo-updates` — a **v0.30.0** é a primeira. Installs
abaixo dela seguem inalcançáveis por qualquer publish. Fix crítico para essa faixa é **build de loja
+ kill switch**, nunca OTA (GUIA_OTA §8, AP-314/ADR-088).

### §6 — Checklist (aplicável a um PR)

Responder **antes** do commit; a resposta vai na seção de versão do PR:

- [ ] O diff toca `ios/`, `android/`, SDK do Expo, plugin de build, permissão ou dependência nativa?
      → **build de loja**, e para por aqui.
- [ ] É feature nova ou muda o propósito do app perante a loja? → **build de loja** (3.3.1).
- [ ] Existe código embarcado inativo que alguém pretende ligar depois? → **reprovado** (§3),
      independente do canal.
- [ ] Se OTA: `APP_VERSION` fica **intacto** e a entrada de CHANGELOG é `[X.Y.Z+ota.N]` com
      `updateId` + SHA (GUIA_OTA §7).
- [ ] Se OTA de produção: sai da tag `mobile-v<APP_VERSION>` ou de `hotfix/ota-*` cortado dela
      ([[R-307]]) — **nunca** da `main` que já andou.
- [ ] O parque-alvo embute `expo-updates` (≥ 0.30.0)? Se o alvo é abaixo, OTA não é o instrumento (§5).

## Why

O conteúdo já existia no runbook (GUIA_OTA §5 e §8) e **não era consultado no momento que importa**:
o SQP (R-221) perguntava plataforma afetada e classificação SemVer, e **nunca** perguntava por qual
canal a mudança chega ao usuário. Um protocolo que decide o número da versão sem decidir o veículo
decide metade do release.

O modo de falha não é publicar algo proibido de propósito — é chegar ao fim de um PR já pronto,
sob pressão de entregar, e descobrir que a resposta "isso vai por OTA" nunca foi tomada por ninguém.
Decisão de compliance tomada no fim é decisão tomada pelo cronograma.

## Enforcement

- **R-221 §4c** — o SQP obriga declarar o canal de entrega junto da classificação SemVer.
- `docs/standards/CHANGELOG_AND_RELEASES.md` §SQP Release Checklist — passo de roteamento OTA/loja.
- `docs/operations/GUIA_OTA_EAS_UPDATE.md` §5.1 — checklist de elegibilidade (este §6, operacional).
- `apps/mobile/publish-ota.sh` — recusa `production` fora da tag de release ([[R-307]]).
- ⚠️ **Não há gate automático para §2 e §3** — nenhuma ferramenta lê intenção de produto. O gate é a
  pergunta no SQP e a revisão humana do PR. Declarado, não fingido.
