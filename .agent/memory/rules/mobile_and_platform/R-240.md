## Regra

**PROIBIDO** utilizar conexões WebSocket ativas persistentes (Supabase Realtime) no aplicativo mobile para sincronização comum de dados (como planos e estoque). Em vez disso, utilizar o padrão **Throttled Focus-Refresh** (deduplicação por tempo de rede em eventos de foco/navegação).

### Motivação e Restrições de Dispositivos (Brasil 🇧🇷)

1. **Economia de Dados Móveis:** A grande maioria dos usuários brasileiros utiliza planos de dados móveis pré-pagos limitados. Heartbeats de WebSockets (ping/pong a cada 15-30s) e reconexões constantes consomem a franquia de dados silenciosamente.
2. **Dreno de Bateria (Rádio Celular):** Conexões persistentes ativas impedem que o rádio celular do aparelho entre em modo de economia de energia (deep sleep), causando superaquecimento e dreno severo em aparelhos mid/low-end.
3. **Loop de Reconexão:** Em redes móveis oscilantes (3G/4G instáveis), WebSockets entram em loops de reconexão agressivos, gerando gargalo de CPU em aparelhos com menor poder de processamento.

### Padrão Throttled Focus-Refresh

- **No Hook (`useStock.js`):** Implementar um throttle baseado em tempo (`lastFetchedRef` via `useRef`) para ignorar requisições à rede feitas em um intervalo menor que **10 segundos** a partir da última busca bem-sucedida, resolvendo a chamada com os dados em memória.
- **Nas Telas (`StockScreen.jsx`):** Disparar o `refresh()` incondicionalmente no `useFocusEffect` (sem guards complexos ou flags de `isFirstFocus`). O throttling no hook impedirá o double-fetching na montagem/startup inicial, mas garantirá dados 100% atualizados ao alternar entre abas após alterações em outros dispositivos (Web/Telegram).
- **Recalcular Detalhes Dinamicamente (`StockDetailScreen.jsx`):** Nunca expor cálculos táticos estáticos como parâmetros de rota de forma rígida. As telas de detalhe devem re-computar indicadores como `dailyConsumption` e `daysRemaining` de forma reativa a partir dos dados locais/frescos assim que as entidades forem carregadas via rede.
