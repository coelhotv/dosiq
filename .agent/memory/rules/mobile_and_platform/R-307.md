# R-307 — Procedência do binário: a versão vive no git, não só no `app.config.js` [CRITICAL]

## Rule

`APP_VERSION` diz **qual** versão foi publicada. Ele não diz **qual código** virou aquela versão —
e é esse elo que torna operável tudo que vem depois do release.

1. **Build de loja exige árvore limpa.** `git status --porcelain` vazio antes de compilar
   `--profile production`. Binário compilado de árvore suja é irrastreável: não existe commit que
   corresponda ao que está no aparelho do usuário. Pior que o mesmo problema no OTA, porque binário
   de loja não se corrige por OTA.
2. **Todo build de loja recebe tag `mobile-v<APP_VERSION>`** no commit que o gerou, criada **no
   momento do build** e **empurrada para o origin**. Reconstruir esse vínculo depois é adivinhação;
   tag só local some com a máquina.
3. **Uma tag por versão, não por plataforma.** iOS e Android do mesmo commit compartilham a tag
   (criação idempotente). Colisão em commit **diferente** é erro duro: significa que o código mudou
   sem bumpar `APP_VERSION` — bumpe (R-221 §4), **nunca** mova a tag.

3b. **A tag marca o commit COMPILADO. Commits posteriores ficam fora por definição — inclusive os
   que não afetam o binário.** Não existe exceção para "delta comprovadamente fora do bundle"
   (docs, scripts, memória DEVFLOW), e a ausência dela é deliberada:

   - A tag responde **uma** pergunta: *qual código virou este binário?* Um commit de doc feito
     depois do build **não** virou aquele binário. Mover a tag para alcançá-lo faz a tag apontar
     para um commit que nunca foi compilado — ela passa a mentir exatamente sobre a única coisa que
     existe para dizer.
   - A exceção custaria caro na prática: alguém teria de **provar, manualmente, a cada vez** que o
     delta não entra no bundle — julgamento sob pressão, no fim de um release. Erra-se uma vez e a
     rastreabilidade se perde em silêncio, que é o modo de falha que esta regra inteira combate.
   - O incômodo que motiva mover ("a tag ficou para trás dos docs") é imaginário: ninguém precisa
     que a tag marque o estado do repositório naquele dia. O git já guarda isso. A tag não é um
     marco de calendário, é um ponteiro de procedência.

   Consequência operacional: é **normal e correto** que `mobile-v<versão>` fique alguns commits
   atrás do `HEAD` da `main`. Isso não é dívida a corrigir.
4. **OTA de produção só sai da tag de release ou de branch cortado dela.** O `eas update` empacota
   a **working tree**, não um commit: publicar da `main` que já andou entrega features não lançadas
   junto do fix. Fluxo: `git checkout -b hotfix/ota-<versão> mobile-v<versão>` →
   `git cherry-pick <fix>` → publicar. Cada hotfix aplicado ganha `mobile-v<versão>-ota.N`, para
   que o próximo parta do estado corrente e não desfaça o anterior.
5. **Reproduzir um build antigo** = `git checkout mobile-v<versão>` → `npm ci` → `build-*.sh`.
   Funciona porque `package-lock.json` é versionado e os diretórios nativos são regenerados por
   `expo prebuild` a partir do `app.config.js` daquele commit.

## Why

Três capacidades distintas dependem do mesmo elo ausente, e todas falham em silêncio sem ele:

- **Investigar um bug relatado numa versão antiga.** Sem tag, "rebuildar a 0.28.3" vira arqueologia
  de `git log` por data — e datas não identificam commit de build.
- **Publicar hotfix por OTA.** O bundle é fotografia da working tree; para o hotfix conter *só* o
  fix, a árvore precisa voltar a ser a da loja. Sem tag não há para onde voltar. Publicar da `main`
  entrega código não revisado, possivelmente chamando nativo que o binário instalado não tem
  (crash imediato), e viola Apple 3.3.1 (feature nova sem revisão).
- **Auditar o que está em campo.** "O usuário está na 0.30.0" não responde "qual código ele roda"
  quando OTAs existem — só o par tag + `updateId` responde.

O custo de criar a tag é uma linha no script, no instante em que a informação é gratuita e exata.
O custo de não ter é pagar arqueologia em toda emergência futura, quando o tempo é caro.

**Limite honesto:** a tag reproduz o **código**, não o ambiente. Versão de Xcode, SDK do Android e
toolchain nativa não são fixados pelo repositório — um rebuild meses depois pode produzir binário
diferente. Para bug de JS isso não importa; para bug nativo, registre também as versões da
toolchain.

## Enforcement

- `apps/mobile/lib-release-tag.sh` — `assert_taggable_build` (antes de compilar) e
  `create_release_tag` (depois do artefato existir), usadas por `build-android.sh` e `build-ios.sh`.
- `apps/mobile/publish-ota.sh` — recusa `production` quando `HEAD` não descende de
  `mobile-v<APP_VERSION>`, e avisa explicitamente quando a tag sequer existe.
- Runbook: `docs/operations/GUIA_OTA_EAS_UPDATE.md` §6.

## Origem

Spec 051-A / PR 1.6 (2026-07-27). A pergunta do PO — *"como faria para planejar um OTA no meio do
desenvolvimento de N features para um novo build?"* — expôs que não havia resposta possível: 28 tags
no repositório, todas da web, nenhuma marcando build mobile. A dor relatada (*"como refazer o build
2803 para testar algo"*) era o mesmo vão visto pelo outro lado.

**Emenda 2026-07-30 (§3b) — decisão do PO.** Na Onda 1 da spec 055, a tag `mobile-v0.30.0` foi
**reposicionada 3×** para acompanhar commits de doc/tooling feitos após o build. O delta eram 3
arquivos, nenhum de bundle ou nativo, e o argumento era razoável: bumpar `APP_VERSION` por causa de
um README seria absurdo. Ficou pendente decidir se a regra ganhava exceção para "delta fora do
bundle".

**Decidido: não ganha.** A pressão para mover vinha de um mal-entendido sobre o significado da tag,
não de uma lacuna da regra — o §3b torna isso explícito para que a dúvida não volte. O falso dilema
era "mover a tag ou bumpar por um README"; a saída é a terceira opção: **deixar a tag onde está**.
