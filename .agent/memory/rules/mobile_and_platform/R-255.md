# R-255 — Notifee (alarme local) coexiste com expo-notifications sem se cancelarem

**Layer:** warm · **Status:** active · **Pack:** mobile_and_platform / notifications
**Origem:** Spec 001 (Alarme Nativo Persistente), PR feat/alarme-nativo, 2026-06-02

## Regra

O alarme local persistente usa `@notifee/react-native`; o push remoto usa
`expo-notifications`. São **dois sistemas de entrega distintos** que coexistem.
Para não derrubar um ao limpar o outro:

- **Cancelar alarmes** → `notifee.cancelTriggerNotifications()` (ou
  `cancelTriggerNotification(id)` por ocorrência). **NUNCA** `cancelAllNotifications()`
  nem mexer no agendador do Expo — `cancelTriggerNotifications` só apaga os triggers
  do Notifee, preservando o push remoto.
- **Idempotência cross-restart**: `notificationId === doseInstanceId`. O re-sync
  (cancelAll + reagenda) recria a MESMA id → o SO substitui, não duplica.
- **Sons separados por canal**: alarme `alarm_dose.wav` (canal `dose-alarm` HIGH,
  `bypassDnd`); push `push_chime.wav` (canal do Expo). Não compartilhar canal.
- **Handler de background** do Notifee (`onBackgroundEvent`) **deve** ser registrado
  no top-level do entrypoint (`index.js`), antes do app montar — senão ações da
  lock screen com app fechado ("Tomei"/"Pular") não são processadas.
- **Preferência do toggle em AsyncStorage**, não `user_settings` — adicionar coluna
  seria migration (Tier 2). O toggle do alarme é local ao device. Default OFF (opt-in):
  alarme invasivo nunca liga sozinho.

## Por quê

`cancelAllNotifications()` apagaria também as notificações do Expo (e vice-versa),
quebrando silenciosamente o canal não-alvo. A separação por API de cancelamento +
canal + id estável mantém os dois sistemas independentes.

(expo-notifications SDK 53), [[R-253]] (padrão de nudge de feature).
