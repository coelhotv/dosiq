# R-303 — Checklist obrigatório: tela com form + rodapé fixo (KeyboardAvoidingView)

**Promovida de [[AP-288]]** (3ª incidência: spec 044 F4b origem → dívida catalogada em 4 telas
→ spec 055 PR 1.4 reintroduziu o MESMO padrão em 4 telas NOVAS antes de achar o AP existente).
Recorrência cruzando 3 specs confirma: não é lição pontual, é checklist de toda tela nova.

## Regra

Toda tela mobile com `ScrollView` (ou lista) de inputs + rodapé de ação fixo (`FormActions` ou
equivalente) DEVE, ao nascer, sair com os 4 itens abaixo — nenhum é opcional, nenhum se resolve
"olhando se ficou bonito" (o bug só aparece com teclado ABERTO, que ninguém testa por padrão):

1. **`behavior='height'` no Android, nunca `undefined`.** Sob `edgeToEdgeEnabled` (todo o app
   hoje), o Android para de redimensionar a janela com o teclado — `adjustResize` no
   AndroidManifest vira letra morta, e `KeyboardAvoidingView` com `behavior={undefined}` é NO-OP
   (monta, parece proteção, não protege: teclado cobre input e rodapé).
   ```jsx
   behavior={Platform.OS === 'ios' ? 'padding' : 'height'}   // ✅ sempre este par
   ```

2. **`keyboardVerticalOffset` NUNCA é constante mágica copiada de outra tela.** No iOS,
   `KeyboardAvoidingView` mede a própria posição na tela via `onLayout` interno — se o header
   é um irmão ACIMA dele na árvore (AppBar próprio, dentro da mesma `SafeAreaView`), a posição
   já vem correta e o offset é **0/omitido**. Setar um valor chutado (`60` copiado de outra
   tela) desloca o rodapé pra cima do teclado, criando vão morto — sintoma medido na 055 PR 1.4
   (~150-160px de espaço vazio entre botão e teclado no iOS, achado só no smoke visual).
   Só usar offset não-zero quando o header É de navegação nativa (react-navigation) OU há
   medição real via `onLayout` — nunca por analogia com outra tela.

3. **`ScrollView` dentro do `KeyboardAvoidingView` precisa de `style={{flex:1}}`**, não só
   `contentContainerStyle`. Sem isso, o ScrollView cresce com o conteúdo e empurra o rodapé
   pra fora da tela visível — a lista rola normal, os botões somem.

4. **Safe-area inferior é condicional ao teclado.** Com o teclado FECHADO, o rodapé precisa do
   inset de baixo (home indicator iOS / gesture bar Android). Com o teclado ABERTO, essa faixa
   deixa de existir visualmente (o teclado cobre o espaço) — manter o inset cria o MESMO vão
   morto do item 2, agora entre botão e teclado em vez de botão e header. Usar
   `useKeyboardVisible()` (`@shared/hooks/useKeyboardVisible` — hook canônico, não reinventar
   com `Keyboard.addListener` solto) e aplicar `insets.bottom` só com teclado fechado. **Não**
   declarar `edges={['bottom']}` na `SafeAreaView` (reservaria a faixa sempre, rodapé some do
   controle do componente).

## Farol

- `behavior={Platform.OS === 'ios' ? 'padding' : undefined}` em qualquer tela nova — é o
  template errado, nasceu antes do edge-to-edge virar padrão do app inteiro.
- `keyboardVerticalOffset={60}` (ou qualquer número redondo) sem comentário explicando de onde
  veio — hard sign de copy-paste sem medir.
- `ScrollView` com só `contentContainerStyle`, sem `style` — funciona com conteúdo curto,
  quebra assim que a lista cresce.
- PR de tela nova com form sem screenshot com teclado ABERTO no RC5/smoke — o bug só aparece
  nesse estado, e é exatamente o estado que ninguém screenshota por padrão.

## Guard de revisão (RC5/RC6 — Pass 1 item 6 Domain Rule Conformance)

Ao revisar diff que adiciona `KeyboardAvoidingView` + `FormActions`/rodapé fixo: os 4 itens
acima são checklist obrigatório, cite-os por número ao aprovar ou reprovar.

## Dívida conhecida (não migrada — telas com `behavior=undefined`, mesmo bug latente)

`ProtocolFormScreen`, `TitrationFormScreen`, `DeleteAccountScreen`, `MedicineAnvisaSheet`,
`MedicineSelectorSheet`, `StockAdjustmentScreen`, `PurchaseFormScreen`,
`OnboardingTreatmentStep`, `OnboardingMedicineStep`. Migradas na 055 PR 1.4:
`MedicineFormScreen`, `FeedbackScreen`, `ProfileEditScreen`, `ChangePasswordScreen`
(+ `StockInitialBalanceScreen`, já correta desde a 044 — é a referência canônica).
`FormActions` (`@shared/components/form/FormActions`) aplica o item 4 apenas no iOS — Android
fica sempre-on até a dívida acima ser migrada para `behavior='height'` (misturar os dois
regimes no mesmo componente compartilhado quebra as telas ainda não migradas — validado
empiricamente na 055 PR 1.4, reproduzido e revertido no smoke).
