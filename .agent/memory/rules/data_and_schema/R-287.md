# R-287 — Toda tabela com `user_id` declara FK para `auth.users` com regra de delete explícita e consciente

**Categoria:** data_and_schema · **Origem:** 046 §T000 (2026-07-09) · **Layer:** warm

## Regra
Toda coluna `user_id` (dono = titular) em tabela nova **DEVE** ter FK para `auth.users(id)` com a
regra `ON DELETE` **escolhida deliberadamente**, nunca uuid solto:

| Natureza do dado | Regra `ON DELETE` | Racional |
|------------------|-------------------|----------|
| Dado do titular (clínico, preferências, estado) | **CASCADE** | some com a conta (LGPD art. 16 — eliminação) |
| Trilha que deve sobreviver ao titular (consentimento, auditoria legal) | **SET NULL** + coluna de identificação anônima (hash/e-mail) | prova de compliance persiste sem PII vinculado |

## Por quê
Confiar na RPC `delete_user_account()` (lista manual filhos→pais) é frágil: a próxima tabela nova
sempre fica de fora, gerando dado de saúde órfão silencioso ([[AP-272]]). A FK é o mecanismo
declarativo que cobre TODOS os caminhos de exclusão — a RPC e o prune via Admin API `deleteUser`.

## Checklist ao criar tabela com `user_id`
1. FK `user_id → auth.users(id)` declarada na migração (`<tabela>_user_id_fkey`).
2. Regra `ON DELETE` escolhida pela tabela acima e **justificada em comentário** na migração.
3. CASCADE não conflita com append-only (bypassa RLS; sem BEFORE DELETE trigger de bloqueio).
4. Teste `BEGIN..ROLLBACK`: user fake → povoar → `DELETE FROM auth.users` → contar linhas = 0 (CASCADE)
   ou = trilha preservada com `user_id IS NULL` (SET NULL).
5. Grants/RLS do template (CLAUDE.md §Migrações) permanecem obrigatórios.

Relaciona: [[AP-272]], R-270 (preflight de migração), R-271 (CHECK de domínio finito).
