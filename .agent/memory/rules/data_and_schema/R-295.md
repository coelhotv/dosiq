# R-295 — 🔴 Campo de tabela só entra em tipo/select DEPOIS de existir no banco (verificar via MCP)

**Status**: hot · **Domínio**: data_and_schema · **Criado**: 2026-07-16
**Origem**: outage P0 em prod (029 F3, #749 → hotfix #750): agente **alucinou a coluna
`titration_steps.description`**, declarou no tipo, escreveu o select a partir do tipo → `42703`
em todo o read-path de `protocols` (web + mobile + cron). Sem protocols: **sem dose, sem estoque**.
**Ver**: [[AP-300]] · [[AP-298]] · [[AP-279]] · [[R-289]] · [[R-270]]

## A regra

**Nenhum nome de coluna entra em tipo, schema Zod, `select()`, `insert`, `update`, `.eq()`/filtro,
`order`, ou RPC — sem antes ser verificado contra o banco.** Não existe "óbvio". Não existe
"o tipo já dizia". Não existe "o legado tinha".

**Verificação obrigatória** (MCP Supabase, custa 1 chamada):

```sql
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema='public' AND table_name='<tabela>'
ORDER BY ordinal_position;
```

Ou `mcp__supabase__list_tables`. Colar o resultado no transcript — evidência, não memória.

## Hierarquia de verdade (decorar)

```
1. o BANCO (information_schema / pg_get_constraintdef, via MCP)   ← única verdade
2. database.types.ts  (GERADO do banco — verdade se o regen está em dia, R-289)
3. schema Zod         (hipótese sincronizada à mão — pode estar velha)
4. tipo `*Like` à mão (HIPÓTESE. mente sem avisar. NÃO é fonte)   ← foi daqui que o outage saiu
5. CLAUDE.md / docs   (foto do passado — já divergiu 4x em 2026-07)
6. a sua memória      (é onde a alucinação mora)
```

**Escrever `select()` a partir de (3), (4), (5) ou (6) é o bug.** O select é uma **string**: o TS
não valida, o lint não valida, e o teste **mocka o client** — o campo fantasma atravessa todos os
gates e só aparece em produção (AP-300: a lista inteira passou — tsc, 2068 testes, jest, lint,
SQL live 21/21, RC5 e review externo).

## Gate de saída — select novo/alterado é mudança de contrato com o banco

Igual a SQL: **só vale EXECUTADO** (mesmo espírito do R-270 e da R-288 "não prove com mock o que o
mock finge"). Antes do commit, disparar o select real contra o banco:

```bash
curl -s "$SUPABASE_URL/rest/v1/<tabela>?select=<SELECT>&limit=1" \
  -H "apikey: $KEY" -H "Authorization: Bearer $KEY"
```

⚠️ O supabase-js **remove whitespace** do select antes de enviar. Ao reproduzir com curl, aplicar
`tr -d '[:space:]'` — senão falha com `PGRST100` por motivo errado (aconteceu no #750).

Passou = `200`. Falhou = `42703` (coluna), `42501` (grant), `PGRST100` (sintaxe), `PGRST200` (FK
inexistente no embed).

## Campo que existe no legado e não no modelo novo

É **decisão de produto**, não lacuna a preencher. Anotar no tipo **por que** não está lá — senão o
próximo slice o reintroduz "pra compilar". Foi exatamente isso: `description` era do N1, a spec
dizia "não migra" (029 Decisões §2), o F2 declarou no tipo pra compilar `stageNote`, o F3 escreveu
o select a partir do tipo.

## Sinal de alerta

Campo opcional (`?:`) num tipo à mão que **nunca** aparece preenchido em teste nem em dado real.
Não é campo opcional — é **campo inexistente** esperando alguém escrever um select.

## Antídoto estrutural (fazer)

Fixture de contrato: teste que dispara **cada `select()` de produção** contra o banco real
(BEGIN..ROLLBACK, sem dado), provando que o PostgREST aceita a string. ~10 linhas por select;
pegaria o AP-300 **e** o AP-298 antes do PR.
