# R-298 — Backfill de coluna derivada: separe PASSADO de FUTURO antes de aproximar, e prefira apagar a chutar

**Classe:** migração de dados · honestidade do registro
**Origem:** spec 052 T011 (PO-4), 2026-07-19 — pergunta do PO durante a execução
**Relacionadas:** [[R-295]] · [[R-245]] · [[AP-308]] · [[ADR-084]]

## A assimetria

Ao preencher retroativamente uma coluna derivada (snapshot, denormalização, cache materializado),
o mesmo `UPDATE ... FROM <fonte>` tem **duas naturezas diferentes** conforme a linha:

| | Erro na linha | Quem corrige |
|---|---|---|
| **Passado** (ocorrência já vencida) | **permanente** | ninguém — nada regenera o passado |
| **Futuro** (ocorrência ainda agendada) | **transitório** | o próprio write-path, em qualquer wipe+regen |

Uma linha futura errada se cura sozinha porque o gerador a reescreve na próxima invalidação
(editar o item, avançar etapa, mudar fuso). Uma linha passada errada fica — e se o dado tem uso
clínico, contábil ou legal, ela vira registro falso com aparência de fato.

**Consequência prática:** a “aproximação documentada” de um backfill quase nunca vale para todas as
linhas sem fonte de verdade — vale só para as **passadas**. Para as futuras, a fonte atual costuma
ser simplesmente **correta**, não aproximada.

Caso 052: a spec previa 2 lotes (com log / sem log). A pergunta do PO — *“quantas dessas linhas
acontecem no passado vs no futuro?”* — dividiu o segundo lote em dois e mudou o que a spec pode
afirmar: a aproximação vale para **1.905** linhas, não para 3.087. Mesmo resultado no banco,
registro radicalmente mais honesto.

## A regra

1. **Antes de escrever, particione o lote sem fonte de verdade por `passado | futuro`** e conte cada
   parte. Reporte as duas separadamente na evidência do PO — “N linhas inferidas” e “M linhas
   corretas” dizem coisas diferentes a quem for ler.
2. **Só chame de aproximação o que é aproximação.** Rotular tudo de aproximado subestima a qualidade
   do dado; rotular tudo de correto mente. Ambos corroem a confiança no registro.
3. **Onde a fonte da aproximação pode estar ERRADA, apague em vez de chutar.** Se existe um motivo
   conhecido para a fonte divergir naquela linha futura (uma transição agendada dentro da janela, um
   agendamento que muda o valor), preencher congela o valor errado **para sempre** — o backfill
   transforma um dado ausente (visivelmente incompleto) num dado errado (invisivelmente falso).
   Apagar a linha futura devolve o trabalho ao gerador, que é quem sabe a resposta. É o que o
   `wipeFuturePending` já faz de rotina: não é exclusão excepcional.
4. **Nunca apague linha passada** por esse motivo — ali a ausência é o registro honesto de que a
   verdade se perdeu.

## Farol

- Backfill cuja query não menciona tempo (`scheduled_for`, `occurred_at`, `due_date`) num domínio
  que TEM tempo: quase certamente está tratando passado e futuro como a mesma coisa.
- Evidência de PO que reporta um número único de “linhas aproximadas”: pedir a quebra.
- Linha futura preenchida a partir de uma fonte que uma transição agendada vai contradizer: é o
  momento de apagar, não de preencher.
