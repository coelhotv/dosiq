# R-246 — Âncora de log↔instância: snap por protocol_id + tolerância por linha, best-effort

**Categoria:** data_and_schema
**Origem:** Fase 2 PR-F2.3 (S2.6 / ADR-048, ADR-050)
**Status:** active

## Regra

Ao registrar uma tomada (`medicine_logs`), ligar o log à ocorrência materializada (`dose_instances`) via **snap**:

1. **Escopo por `protocol_id`, NUNCA `medicine_id`** — dois protocolos do mesmo medicamento têm slots distintos; escopar por medicine_id faz logs vazarem entre protocolos (AP-A03).
2. **Tolerância por linha** — cada instância carrega seu próprio `tolerance_minutes` (varia por slot: `min(metade do menor intervalo adjacente, 120)` para diário multi-dose; 120 para não-diário/dose-única). O snap filtra `|taken_at − scheduled_for| <= tolerance_minutes` de **cada** linha, não um valor global.
3. **Mais próxima por instante absoluto** — entre as elegíveis, escolher a de menor diferença. Comparação em ms UTC → cross-meia-noite (22:30 de ontem ↔ 00:05 de hoje) funciona naturalmente, sem lógica de data especial.
4. **Só `pending`** é elegível — nunca re-ancora `taken`/`missed`/`skipped`.
5. **Fora de toda janela → `dose_instance_id = null`** (dose avulsa, legítima).

## Best-effort + fonte de verdade

A âncora roda **após** o estoque ser debitado e é **best-effort** (try/catch que não lança): o `medicine_log` é a **fonte de verdade** da tomada; a instância é estado **derivado**. Falha de âncora deixa o log avulso, reconciliável por backfill (S2.7). Nunca falhar/reverter um registro de dose válido por causa de erro na âncora.

## FP-1 (ADR-050)

`markTaken(instanceId, logId)` marca `status='taken'` + `medicine_log_id` e **não** compara `quantity_taken` com `expected_dose` — a dose aplicada pode divergir da planejada (habilita bolus variável futuro). O elo é bidirecional: `medicine_logs.dose_instance_id` ↔ `dose_instances.medicine_log_id`.

## Superfícies de escrita

Toda superfície que cria `medicine_logs` deve ancorar: web `logService.create` (cobre LogForm + FAB + bulk via funnel) e bot `doseActions.createLogAndConsumeStock`. Capturar `taken_at` UMA vez e reusar no insert e no snap (evita drift de timestamp). Superfícies secundárias do bot (plan/bulk, conversational, medicineLogService) ficam como follow-up.
