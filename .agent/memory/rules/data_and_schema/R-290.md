# R-290 — Regra derivada client-side recorta a própria janela; nunca herda a do chamador

**Domínio:** regra de negócio compartilhada (packages/core) consumida por web + mobile
**Origem:** spec 044 F4b (T018 — gatilho do upsell de estoque), pego na revisão do diff dos sub-agentes

## O problema

O gatilho do upsell ("20 doses **ou** 14 dias consecutivos") foi implementado como função pura no
core, recebendo a lista de dias com dose que **cada plataforma já tinha em mãos**:

- web: `logs` do DashboardProvider → janela de ~1 ano (carregada para o cálculo de streak)
- mobile: query própria → janela de 30 dias

A regra era a mesma nas duas. **A pergunta, não.** Na web, "20 doses" virava "20 doses na vida";
no mobile, "20 doses nos últimos 30 dias". O mesmo usuário via o card numa plataforma e não na
outra — sem nenhum bug visível em nenhum dos dois lados isoladamente.

## A regra

**Se a decisão depende de uma janela temporal, a janela é PARTE DA REGRA e mora com ela** — não
no fetch de quem chama. O chamador passa o que tiver; a regra recorta.

```ts
// core: a janela é constante da regra, não do fetch
export const UPSELL_LOOKBACK_DAYS = 30

const days = loggedDays.filter((day) => {
  const age = dayDistance(todayLocal, day)
  return age >= 0 && age < lookbackDays   // ← recorte DENTRO da regra
})
```

Assim, passar 1 ano ou 30 dias dá o **mesmo veredito**. A plataforma decide quanto busca (custo);
a regra decide quanto **enxerga** (semântica).

## Farol

Toda função pura de decisão que recebe uma coleção histórica (logs, eventos, medições) e cujo
resultado muda conforme o tamanho da coleção. Se dois chamadores buscam janelas diferentes — e
eles quase sempre buscam, porque cada tela otimiza o seu fetch — a regra está implicitamente
parametrizada por um detalhe de infraestrutura.

Relacionado: [[R-267]] (read-path completo), [[AP-214]]/[[AP-215]] (o campo que não viaja até o
consumidor). Aqui não é o campo que falta: é o **recorte** que sobra.
