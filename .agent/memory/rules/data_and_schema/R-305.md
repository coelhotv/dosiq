# R-305 — As duas camadas de acesso falham de formas DIFERENTES: privilégio grita, RLS silencia

**Classe:** data_and_schema · **Layer:** hot · **Criada:** 2026-07-25 (spec 051-A PR 1.5a)
**Relacionados:** [[AP-278]] (camadas independentes) · [[AP-319]] · [[R-270]] · [[R-295]] · ADR-091 D5

## Regra

Toda escrita em tabela protegida por RLS **confere a linha devolvida** (`.update(...).select().single()`
ou `RETURNING`) e trata **"0 linhas" como FALHA explícita** — nunca como sucesso.

Motivo, medido em BEGIN..ROLLBACK em 2026-07-25 sobre `app_version_gate`:

| Camada | Como falha | O que o cliente vê |
|---|---|---|
| **1 — privilégio de tabela** (`REVOKE INSERT/UPDATE/DELETE`) | ALTO | `42501 permission denied` — você descobre na hora |
| **2 — RLS sem policy de escrita** | **BAIXO** | `UPDATE` afeta **0 linhas** e **não levanta erro** |

Com o privilégio reconcedido de propósito (`GRANT UPDATE ... TO authenticated`), a RLS segurou
sozinha — corretamente — mas em silêncio: `ROW_COUNT = 0`, zero exceção, e o PostgREST responderia
`200`/`204`. Um cliente que só checa `error` conclui que gravou.

## Consequência prática

```ts
const { data, error } = await supabase.from(tabela).update(patch).eq('id', id).select().single()
if (error) { /* ... */ }
// 🔴 obrigatório: 0 linhas é falha, não sucesso silencioso
if (!data) return res.status(500).json({ error: 'Update did not affect any row' })
```

Sem isso, a UI anuncia "kill switch ativado" (ou "salvo") sobre uma escrita que **não aconteceu**. Em
superfície de emergência isso é pior que um erro: o operador vai embora acreditando que agiu.

## Escopo

Vale para qualquer tabela com RLS ligada — ou seja, praticamente todas neste projeto. Prioridade
máxima em: escrita por `service_role` atrás de painel admin, RPC que faz `UPDATE ... WHERE` de dono, e
qualquer mutação cujo resultado a UI reporta como concluído.

## Gate

1. No BEGIN..ROLLBACK da migração: conceder o privilégio de escrita de propósito e assere que a RLS
   ainda barra (`ROW_COUNT = 0` e estado inalterado). É o único teste que prova que as camadas são
   **independentes** em vez de uma só disfarçada de duas ([[AP-278]]).
2. No teste do handler: caso com `updateResult: { data: null, error: null }` ⇒ resposta `5xx`.

## Farol

- `.update()` / `.insert()` sem `.select()` em código que reporta sucesso ao usuário.
- Código que trata só `error` do supabase-js e nunca olha `data` — o supabase-js **não lança**, e sob
  RLS o "não autorizado" pode chegar como ausência de linha, não como erro.
