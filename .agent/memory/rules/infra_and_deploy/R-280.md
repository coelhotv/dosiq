# R-280 — Ordem das `messages` p/ Groq Prompt Caching (prefix-match)

**Domínio:** infra_and_deploy
**Origem:** spec 015 Onda 3 (cache hit ~0% observado nos stats do Groq)

## Contexto
O Groq Prompt Caching é **prefix-match exato**: cacheia do início do prompt até o **primeiro byte
que muda**; tudo depois é não-cacheado. A posição relativa do conteúdo importa — o mais estável
deve vir primeiro.

## Regra
Montar `messages` do mais estável ao mais dinâmico:

```
1. system ESTÁTICO   → regras/persona idênticas p/ TODOS os usuários → cache GLOBAL entre conversas
2. DADOS DO PACIENTE → estáveis na sessão (mudam poucas vezes/dia) → cache por usuário após o system
3. histórico         → cresce por turno; cacheado em cima do prefixo estável acima
4. pergunta          → 100% dinâmica; único trecho sempre não-cacheado
```

## Anti-padrão que isto corrige
Embutir o contexto do paciente (dinâmico) **dentro** da mensagem `system` torna o bloco inteiro
por-usuário → o `system` deixa de ser cacheável globalmente e quase nunca há hit. Separar em
mensagens distintas (`system` puro + `DADOS DO PACIENTE` à parte) restaura o cache.

## Trade-off
Pôr o paciente ANTES do histórico maximiza o prefixo estável; só perde cache se o paciente mudar no
meio da conversa (raro). Vale para uso conversacional curto.

## Segurança
As regras autoritativas (`system`) são compostas NO SERVIDOR (AP-237) — nunca recebidas do cliente.
Aplicado em `api/chatbot.js` (web/mobile) e `server/bot/services/chatbotServerService.js` (Telegram).
