# R-282 — Imports relativos em server/ e api/ mantêm extensão `.js` (Node ESM puro)

**Domínio**: infra_and_deploy · **Criada**: 2026-07-03 (040 F2, incidente 434144e/AP-260)

## Regra

`server/**` e `api/**` rodam em Node ESM puro (root `package.json` tem `"type": "module"`):

1. Import relativo **DEVE** manter extensão `.js` explícita. Extensionless = `ERR_MODULE_NOT_FOUND` em runtime.
2. Arquivo `.js` de server/api **NUNCA** importa fonte `.ts` de packages/ diretamente (Node não resolve `.ts`) — usar a cópia `.js` local (ex.: `server/utils/dateUtils.js`) ou aguardar o runtime tsx (040 F3.3).
3. Specifiers extensionless valem APENAS em código consumido por bundler (Vite/Metro/esbuild/tsx).
4. **Adendo F6 (2026-07-08, PR #731):** vale TAMBÉM para `.d.ts` e packages que exportam src `.ts` cru. `tsc` NÃO reescreve specifiers no declaration emit — `.d.ts` com import relativo extensionless não resolve sob nodenext (typecheck Vercel) e o barrel vira "vazio" (TS2305 em todo consumer). Fix no core: pós-build `packages/core/scripts/fix-dts-extensions.mjs`; packages src-exportados (shared-data/storage/config/design-tokens): imports relativos com `.js` na própria fonte (aponta pro `.ts` em compile).

## Por quê

Vitest/Vite resolvem extensionless e mascaram a quebra — o erro só aparece em runtime real (bot, cron). Smoke de detecção: `node --input-type=module -e "await import('<entrypoint>')"`.
