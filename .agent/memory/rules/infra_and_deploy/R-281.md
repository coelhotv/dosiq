# R-281 — Side-effects assíncronos independentes em loop → `Promise.all`, não `await` serial

**Status:** hot · **Origem:** promovido após 3º incidente (review Gemini #698 sweep + #699 ×3 sítios de audit emit).

## Regra
Quando um loop faz `await` de N operações assíncronas **independentes entre si** (sem ordem, sem
dependência de dado de uma para a próxima), disparar em paralelo com `Promise.all(list.map(...))`
em vez de `for...of { await }`. O serial soma a latência de todas; o paralelo paga o max.

```js
// ❌ serial: latência = Σ (cada insert espera o anterior)
for (const id of ids) await audit.emit({ doseInstanceId: id, ... })

// ✅ paralelo: latência ≈ max
await Promise.all(ids.map((id) => audit.emit({ doseInstanceId: id, ... })))
```

## Quando NÃO paralelizar
- Há **ordem/dependência** (resultado N alimenta N+1; trava otimista; transação sequencial).
- Contra-exemplo deliberado: **AP-246** serializa ends do ActivityKit de propósito (request concorreria com `.end()`).
- Rate-limit externo que exige serialização (então use pool/`p-limit`, não serial cego).

## Segurança do `Promise.all`
Só é seguro se cada promessa **não rejeita** (ou a rejeição é aceitável abortar o lote). Para
side-effects best-effort/**fail-open** (ex.: `criticalAuditService.emit` retorna `{ok}` e nunca
lança — CON-031), `Promise.all` nunca rejeita → ideal. Se as promessas podem rejeitar e o lote deve
seguir, usar `Promise.allSettled`.

## Por que importa (não é nitpick)
Contexto **headless/background** (Android `onBackgroundEvent`, serverless minuto-a-minuto) tem
orçamento de tempo limitado pelo SO/plataforma. N inserts seriais podem estourar a janela e o
trabalho é morto no meio. Também reduz tempo de resposta em fluxos sensíveis (snooze, resync, lote).

## Guard
Review de PR: loop com `await` de emit/insert/fetch independentes → sinalizar. Preferir `Promise.all`
desde a 1ª escrita (evita ida-e-volta recorrente com o revisor — foi o gatilho desta regra).
