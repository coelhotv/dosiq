# R-293 — Gate de consentimento cobre TODA superfície que trata dado de saúde: servidor E device

**Domínio:** notifications/privacy · **Origem:** spec 046 Slice B, smoke do PO · **Data:** 2026-07-15
**Relacionadas:** [[R-292]] (por-usuário, não global — a mecânica) · [[AP-295]] (o furo que a violou) ·
[[AP-290]] (erro de leitura ≠ estado do domínio)

## Regra

Consentimento é **política de conta**, não estado de uma tela. Quando ele governa o tratamento de dado
sensível de saúde, **todo** caminho que materializa esse dado precisa passar pelo **mesmo** gate — não
só o que é óbvio na UI. Isso inclui, além do request no servidor:

- **superfícies que o aparelho dispara sozinho:** alarme local (trigger nativo agendado), notificação
  contínua/ongoing, Live Activity / Dynamic Island, widget com timer, badge com nome/dose;
- **geração de derivados:** trilha de auditoria, inferência de estado no foreground, sync de token push.

Suprimir só o **push do servidor** é meia-implementação: o trigger **já agendado no device** dispara
sem rede, e a trava da UI **esconde a tela, não desarma o trigger**. A LGPD não distingue "servidor"
de "aparelho" — distingue tratamento **com/sem** base legal (revogar retira a base; art. 11).

## Como aplicar

- Uma **fonte só** de decisão de consentimento (gate compartilhado / decisão pura), consumida por todas
  as superfícies. Se cada superfície lê à sua maneira, são políticas divergentes na prática.
- Superfície montada **acima** do provider do gate (ex.: bridges no root, fora do Navigation) lê a
  trilha por conta própria (`useConsentSuppressed`) e re-checa nos boundaries dela (mount / foreground /
  troca de usuário) **e** num bus que o grant/revoke dispara — grant/revoke **in-app** não passam por
  foreground, e sem o bus o alarme já agendado dispara antes da próxima reavaliação.
- **Desarmar** = cancelar o agendado, não só parar de agendar novos. Reusar o teardown de logout
  (tratar "revogado" como "sem usuário") é o caminho mais seguro — é código já exercitado.
- **Rearmar** no re-consent é o mesmo mecanismo ao contrário: o grant reavalia o gate → o bus dispara →
  as superfícies re-agendam. Self-healing automático enquanto a trava impede editar o domínio no meio.

## Farol

- Achar que suprimir o servidor basta. Pergunte: "que trigger **local** continua armado depois do revoke?"
- Teardown de superfície keyed só em `logout`/`!userId` — a revogação também tem que derrubar.
- Superfície com dado de saúde montada fora do alcance do provider de consentimento.
