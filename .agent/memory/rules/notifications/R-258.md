# R-258 — Gate de push por-device via flag em `notification_devices` (lido ao vivo)

**Layer:** warm · **Status:** active · **Pack:** notifications
**Origem:** Spec 001 (Alarme Nativo) A2, PR feat/alarme-nativo, 2026-06-03

## Regra

Para suprimir **um** canal de notificação sem matar os outros (ex.: alarme nativo
local cobre a dose → não mandar o push remoto de dose pra aquele device), usar um
**flag booleano por-device** em `notification_devices`, lido **ao vivo no canal de
envio** (não cacheado):

- Coluna `native_alarm_enabled` (default false) + param no RPC de upsert do device.
- O client grava o flag ao ligar o toggle (re-sync do device).
- O canal de envio (`expoPushChannel`) filtra **type-aware** por `metadata.kind`:

```js
const DOSE_KINDS = new Set(['dose_reminder','dose_reminder_by_plan','dose_reminder_misc'])
const isDose = DOSE_KINDS.has(payload?.metadata?.kind)
const devices = isDose ? all.filter(d => !d.native_alarm_enabled) : all
```

## Princípios

- **Por-device, não por-usuário**: web/telegram/outros devices do mesmo user
  seguem recebendo. Granularidade no token, não na preferência global.
- **Type-aware**: só o `kind` coberto pela alternativa é suprimido; estoque/outros
  tipos passam normais pro mesmo device.
- **Lido ao vivo** (`listActiveByUser` direto da tabela) → zero defasagem; o
  próximo disparo já respeita o flag. Sem TTL/cache.
- O flag só grava se houver **token de push** (permissão concedida). Sem token →
  sem push a deduplicar → no-op aceitável.

⚠️ O gate é **server-side**: a dedup on-device só vale **pós-deploy** do canal
(o push nasce da prod). Ver [[AP-206]]. Cuidado com stale device rows: [[AP-208]].
