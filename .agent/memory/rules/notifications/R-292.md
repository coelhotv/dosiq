# R-292 — Estado por-usuário não vira dependência global do pipeline clínico

**Domínio:** notifications · **Origem:** spec 046 Slice B (T014), review do PO · **Data:** 2026-07-14
**Relacionadas:** [[AP-290]] (erro de leitura tratado como estado do domínio) · [[AP-277]] (ausência de
dado nunca desliga o estoque por omissão) · [[R-283]] · [[AP-292]]

## Regra

Uma condição que só se aplica a **alguns usuários** (consentimento revogado, plano suspenso, opt-out,
bloqueio administrativo) **NÃO pode ser resolvida por uma leitura global no caminho crítico** de um
pipeline que serve **todos** os usuários.

Materialize o estado **na linha do próprio usuário**, na tabela que o pipeline **já lê por usuário**,
e escreva esse flag **na mesma transação** do fato que o origina. A decisão passa a ser tomada com o
dado que já está em mãos: **zero query nova, zero ponto de falha novo, zero raio global**.

Consequência que é o ponto inteiro da regra: **falha de leitura vira problema DO usuário afetado.**
Fail-closed continua valendo — "não sei se ele revogou" nunca é "pode enviar" (AP-290) —, mas o custo
recai sobre aquele usuário, jamais sobre a necessidade clínica dos outros pacientes.

## O caso que a gerou

A 1ª versão do T014 lia `consent_log` **uma vez por run do cron** e montava um `Set` de revogados em
memória. Formalmente parecia o padrão do 044 (`stock_tracking_enabled` no mesmo fetch de settings) —
mas não era: o 044 lê a preferência **no fetch que já existia**, e esta versão **introduzia uma query
nova, global, no caminho de todos**.

O fail-closed daquele desenho (trilha ilegível ⇒ aborta o run) estava *logicamente* certo e
*clinicamente* errado: um `SELECT` falhando fazia **ninguém** receber lembrete de dose naquele
minuto. A situação de um titular que revogou podia suprimir a medicação de toda a base. O PO
recusou, com razão: **"a situação de 1 usuário não pode afetar a necessidade clínica de outros
pacientes."**

Correção: coluna `user_settings.consent_revoked_at`, escrita pela mesma txn da RPC que grava a
trilha, lida no `getSettingsByUserId` que o dispatcher já chamava.

## Farol (como reconhecer a violação no code review)

- Um `await` de leitura **antes** do loop de usuários, ou na inicialização do run, cujo erro derruba
  o run inteiro — para decidir algo que vale por usuário.
- Um `Set`/`Map` de "usuários especiais" construído no topo do pipeline.
- A pergunta que expõe: *"se essa query falhar, quem para de receber?"* Se a resposta for **"todos"**
  para um estado que é de **poucos**, a regra foi violada.

## Não confundir

- Isto **não** afrouxa o fail-closed. Continua valendo: estado ilegível ⇒ não envia **àquele**
  usuário (marca `_read_failed`, e o dispatcher trata "não sei" como "não").
- O flag materializado **não** é uma segunda fonte de verdade. A prova continua na trilha
  append-only; o flag é índice operacional derivado, com **um único escritor** e escrito na **mesma
  transação** — não há janela de drift.
- Direção do default: flag ausente/NULL ⇒ **envia**. Espelho invertido do AP-277 — ausência de dado
  nunca cala um alerta clínico. Quem protege o revogado é o flag dele **sempre existir**, não o
  default.
