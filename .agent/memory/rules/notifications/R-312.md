# R-312 — Freio de segurança precisa falhar para o lado seguro quando a CONFIGURAÇÃO dele é lixo

**Categoria:** notifications (aplica-se a qualquer job com teto) · **Layer:** warm
**Origem:** RC5 do 046 Slice C, 2026-08-20

## Regra

Todo teto/limite lido de ambiente passa por um resolvedor que **recusa valor inválido** e cai no
default. Nunca `Number(env.X ?? DEFAULT)` direto num comparador.

```ts
export function resolveCap(raw: string | undefined, fallback: number): number {
  const n = Number(raw)
  return Number.isFinite(n) && n >= 0 ? n : fallback
}
```

## Por que

`Number('abc')` é `NaN`, e **toda comparação com `NaN` é `false`**:

```ts
const cap = Number(process.env.CONSENT_PRUNE_CAP ?? 5)  // 'cinco' => NaN
if (candidatos.length > cap) abortar()                   // NUNCA dispara
```

O freio não some do código — some do **comportamento**. Ele continua lá, legível, revisado, com
teste verde (o teste passa `cap` como número), e simplesmente não age. E não age exatamente no
cenário para o qual foi escrito: população acima do esperado.

Um typo numa variável de ambiente — o tipo de erro mais banal que existe, sem review e sem deploy —
desarma a proteção de um ato irreversível.

## Como aplicar

- Resolvedor único para todo limite vindo de env; teste com `'abc'`, `undefined`, `'-1'`, `''`.
- Cuidado com o zero: `Number('') === 0`, e teto zero é **fail-safe** (aborta sempre), não lixo —
  distinguir "vazio" de "inválido" importa.
- A mesma disciplina vale para timeouts, batch sizes e retries: `NaN` em comparador é sempre um
  freio inerte, nunca um erro visível.

## Farol

- `Number(process.env.X)` alimentando `>`, `<`, `>=` num caminho de proteção.
- Limite configurável cujo teste só exercita valores numéricos válidos.
- Env que, se digitado errado, torna o sistema **mais permissivo** em vez de quebrar.
