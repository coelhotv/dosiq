# R-275 — Status de spec: README índice canônico + atualização obrigatória no C5

**Layer:** hot · **Status:** active · **Created:** 2026-06-10
**Tags:** process, specs, lifecycle, devflow

## Regra

1. `plans/specs/README.md` é a **fonte de verdade** do status de cada spec (vocabulário fechado:
   `draft → specified → planned → in-progress → delivered → superseded`).
2. O header `**Status**` de cada spec.md DEVE espelhar o README usando esse vocabulário —
   proibido vocabulário livre ("Shipped", "IMPLEMENTED", "Dev Ready", "APPROVED", "Migrated Draft").
3. **Todo C5 pós-merge** que entrega (total ou parcialmente) uma spec DEVE atualizar: (a) a linha
   do README com PR# como evidência; (b) o header da spec. Entrega parcial → `in-progress` + fases
   entregues anotadas.
4. Distill (D5) reconcilia README × headers × PRs; linhas `⚠️ auditar` são resolvidas na primeira
   sessão que tocar a spec.
5. Agentes/consultores **NÃO** inferem status pelo header isolado nem pela presença do diretório.

## Por quê

Auditoria CPTO 2026-06-10 encontrou drift sistêmico: 001 "Dev Ready" porém entregue desde 03/06;
022 "Shipped — aguardando merge" porém mergeada; 8 vocabulários distintos em 28 specs. Agentes e
consultores tomavam decisões de roadmap sobre status errado (ex.: assumir LGPD/PDF entregues).

## Como aplicar

- Ao entregar: editar `plans/specs/README.md` + header da spec no MESMO commit do C5.
- Ao consultar: ler o README primeiro; em `⚠️ auditar`, verificar PRs antes de decidir.
