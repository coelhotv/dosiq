# R-221 — SQP (Standard Quality Protocol) [CRITICAL]

## Rule
Any agent performing code-changing work must follow the Standard Quality Protocol before commit, push, or PR creation.

1. **DEVFLOW Bootstrap**: Load `.agent/state.json`, `R-221`, and relevant hot/warm memory before touching files.
2. **Release Impact Classification**: Identify affected platform(s): Web/PWA, Mobile, Shared/Core, Backend/Infra.
3. **SemVer Decision**: Classify impact as `patch`, `minor`, `major`, or `no-user-impact` with a short justification.
4. **Version Source Update**: Update affected version source(s) when impact is not `no-user-impact`:
   - Web/PWA: `apps/web/package.json`
   - Mobile: `apps/mobile/app.config.js` `APP_VERSION`
4b. **Build Provenance (R-307)**: bumping the number is not the whole job — the commit that became
   that number must be recoverable. Every store build runs from a clean tree and is tagged
   `mobile-v<APP_VERSION>` at build time, pushed to origin. A tag collision on a different commit
   means code changed without a bump: bump it, never move the tag. OTA releases to production may
   only be published from that tag (or a `hotfix/ota-*` branch cut from it) — see R-307.
4c. **Delivery Channel Routing (R-314)**: for any Mobile-affecting change, declare the channel
   **before writing code**: OTA (`eas update`), store build, or kill switch. Native code, Expo SDK,
   `ios/`, `android/`, build plugins, new permissions and new features / purpose changes always
   require a store build (Apple 3.3.1); shipping inactive code behind a flag to "enable later" is
   forbidden on either channel. OTA releases must NOT bump `APP_VERSION` (bump = new runtime = orphan
   update, ADR-082) and are logged as `[X.Y.Z+ota.N]`. See R-314 for the PR checklist.
5. **Changelog Logging**: Add a Portuguese entry under `CHANGELOG.md` `[Unreleased]` before PR creation.
6. **Store Note Readiness**: For mobile changes, ensure App Store / Play Store notes can be derived from the changelog entry.
7. **Zero Lint Regression**: No new lint warnings or errors are allowed. Any regression must be fixed before proceeding.
8. **CI Validation**: `npm run validate:agent` must be executed and pass before PR submission unless the human explicitly scopes validation differently.
9. **PR Version Section**: Fill the PR version section from the actual version files and changelog entry.
10. **DEVFLOW C5 Record**: Record platform(s), bump type, new version(s), changelog entry, and store-note relevance in journal/events.

## Gate-Based Extension
Complex projects divided into explicit "Gates" must also apply these stricter steps:

1. **Branch Naming**: All gate work must occur in branches named `feat/gate-{id}-{slug}`.
2. **Hard Stop**: Agents must STOP and request explicit human validation/approval BEFORE any commit or push.
3. **Approval Cycle**:
   - Work starts -> Implementation -> **Hard Stop (Human Review)**.
   - Human approves -> Commit -> Push -> Create PR.
   - PR Review Fixes -> Approval -> Merge -> Finalize Gate.

## Why
Prevents architectural drift, release-note gaps, version drift between platforms, untraceable binaries (R-307), and undocumented store submissions while preserving strict gates for high-risk multi-step work.
