# R-318 — Arquivo que excede sozinho o budget de chunk do revisor deixa de ser revisável

**Status**: active · **Layer**: warm · **Pack**: process_and_testing
**Criada em**: 2026-08-25 (spec 050, PR 4 — #812)
**Aplica-se a**: qualquer arquivo de código que entre em PR revisado por IA com orçamento de contexto

## A regra

Quando **um único arquivo** excede sozinho o orçamento de chunk do revisor, o pass daquele
chunk vira **ADVISORY** — o revisor amostra em silêncio e o `clean` que ele devolve não é
prova de nada. A partir daí, **fatiar o arquivo é requisito de PROCESSO, não estética**: o
custo não é legibilidade, é ficar sem gate de revisão em todo PR que tocar aquele caminho.

Gatilho objetivo (não é julgamento de gosto): **2 PRs seguidos com pass advisory pelo MESMO
arquivo** ⇒ o fatiamento entra na fila como entregável, com o número medido no PR.

## Como fatiar sem virar outro problema

1. **Move-only**, em PR próprio. Zero rename, zero assinatura nova, zero "melhoria de passagem".
   Um diff move+edit de 1.500 linhas não é revisável — é exatamente onde a edição silenciosa
   passa. Bug visto durante o move se **anota e reporta**, não se corrige ali.
2. **Sem barrel** (`index.ts` re-exportando tudo): o hub falso continua no grafo e o revisor
   volta a montar o mesmo payload gigante. Cada consumidor importa do arquivo do domínio.
3. **A prova de move-only não é o `git diff -M`.** Quando 1 arquivo vira N, a heurística de
   rename/cópia do git **não casa** (medido: `-M -C --find-copies-harder` → `renames=0`). A prova
   que vale é comparar cada faixa do arquivo original com o corpo do arquivo novo, byte a byte,
   ignorando só o header de imports/logger — e colar o resultado no PR.

## O que a medição do #812 mostrou depois do corte

Fatiar resolve **a metade do problema que é sua**. No 050 PR 4 o maior arquivo caiu de 74.779B
para 24.687B e 3 de 4 chunks deixaram de ser advisory — mas o **preâmbulo** (índices de regras/APs
injetados) sozinho ocupava **104.086B** contra um chunk budget de **37.914B**. Depois de fatiar,
quem estoura o orçamento passa a ser a MEMÓRIA injetada, não o código: a alavanca vira o teto do
índice (`RC6_IDX_LINE_MAX`), e ela é **manutenção recorrente** — os índices crescem a cada C5.

## Efeito colateral a declarar no SQP

Fatiar por domínio troca o logger único por um por arquivo ⇒ **muda o prefixo dos logs em prod**.
Vai no CHANGELOG: filtro ou alerta preso ao nome antigo para de casar.

## Armadilha de revisão que o fatiamento CRIA

Arquivo original deletado + N arquivos *file-added* ⇒ o revisor lê código movido como código novo
e marca dívida antiga como `introduced: true` — que é exatamente o campo em que o gate de merge
chaveia. Triar com `git show <base>:<arquivo>` e refutar por número de linha antes de pedir
aprovação. Ver [[AP-186]] · [[AP-298]] · [[R-282]]
