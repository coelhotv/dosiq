# R-301 — Fallback de cache não pode engolir o erro que causou a queda

**Camada**: hot · **Status**: active · **Criada**: 2026-07-22 (PR #766, pós-outage [[AP-314]])
**Pack**: `react_and_ui` · **Aplica-se a**: todo hook offline-first (mobile e web) que tenta rede → cai em cache

## Regra

Quando o fetch falha e o fallback de cache **também** falha, a mensagem exibida ao usuário deve ser
a do **erro de servidor**, não a do fallback. Erro que carrega `code` (resposta do PostgREST) tem
precedência sobre "Cache expirado" — e o código vai **visível** na mensagem.

Fonte única: `describeLoadFailure` / `isServerError` (`@dosiq/core`). Não reimplementar por hook.

```js
// ❌ o motivo real morre aqui — schema quebrado vira "app offline"
} catch (err) {
  try { await handleCacheFallback(err) }
  catch (fallbackErr) { setError(fallbackErr.message ?? 'Erro ao carregar dados.') }
}

// ✅ servidor respondeu ⇒ o problema não é conectividade ⇒ mostra o código
} catch (err) {
  try { await handleCacheFallback(err) }
  catch (fallbackErr) { setError(describeLoadFailure(err, fallbackErr, 'Erro ao carregar dados.')) }
}
```

## Por que

O discriminador é o campo `code`: só resposta do banco o carrega (`42703` coluna, `42501` grant,
`23514` CHECK, `PGRST200` FK). Se o servidor **respondeu**, o problema não é rede — e **nenhuma ação
do usuário** (esperar, trocar de rede, reabrir, "Tentar novamente") vai resolver. Reportar isso como
falha de cache é mentir sobre a natureza do problema.

Num app offline-first o custo é duplo:

1. **Para o usuário:** "Cache expirado (> 24h)" com wifi funcionando pede uma ação que não existe.
2. **Para o diagnóstico:** quebra de schema fica **indistinguível de estar offline**. No outage de
   2026-07-22 isso custou horas, e o sintoma ainda apontava para a direção errada (parecia problema
   de conectividade do aparelho).

O código exposto na UI é deliberado: é o que o usuário consegue reportar num print, e o que torna o
diagnóstico imediato para quem recebe esse print.

## Escopo

Vale para os três hooks que já seguem o padrão — `useTodayData`, `useTreatments`, `useStock` — e para
**qualquer hook novo** com a forma "tenta rede → cai em cache". A lógica mora no core justamente
porque três cópias divergem (família [[R-290]]).

## Farol

- `catch (fallbackErr)` cujo `setError` usa **só** o erro do fallback.
- `catch { }` sem binding logo após um `throw new Error('Cache expirado')` — o erro original está no
  escopo e não está sendo usado.
- Mensagem de erro de carga que não distingue "servidor recusou" de "você está offline".

## Teste que trava

`packages/core/src/utils/__tests__/loadFailure.test.ts` — fixa a PRECEDÊNCIA (erro de servidor vence
"Cache expirado") com o `42703` literal capturado em produção, e garante que a função **nunca**
devolve vazio sob nenhuma combinação de entrada.
