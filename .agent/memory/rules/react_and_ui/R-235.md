# R-235 — Hook canônico antes de inline (use*Delete / use*Mutation patterns)

**Regra**: ao adicionar lógica de delete/mutation/fetch em screen ou componente, **primeiro grep por hook canônico existente** (`use*Delete`, `use*Mutation`, `use*Stats`) e adotar via DI/composição. Implementação inline é aceita apenas se nenhum hook cobrir o caso E o hook seria sobre-engineered pra um único call site.

**Why**: durante Fase 2, `ProtocolDetailScreen` reinventou delete inline (state `isDeleting` + `protocolService.delete` direto + toast + navigation + haptic) quando `useProtocolDelete(protocol)` já existia desde T2.10 com cache invalidation AsyncStorage + haptics + toast + navigation encapsulados. Gemini PR #568 pegou (HIGH).

**How to apply**:
1. Antes de implementar lógica de delete/mutation: `grep -rn "use<Entity>Delete\|use<Entity>Mutation" apps/mobile/src apps/web/src`
2. Se existe: importar e adotar. Confirm que API do hook atende (props, return shape).
3. Se NÃO existe + 2+ telas precisam da mesma lógica: criar o hook PRIMEIRO, então adopt.
4. Se NÃO existe + 1 tela única: inline OK, mas adicionar TODO comment se previsível replicação futura.

**Indicadores de oportunidade de hook**:
- Mesma estrutura `try/catch → service.X → toast/haptic → navigation.goBack` aparece em N telas
- Cache invalidation manual repetida (AsyncStorage.removeItem + invalidateKeys)
- Estado `isLoading/isDeleting` duplicado

**Hooks canônicos atuais no Dosiq**:
- `useMedicineDelete`, `useMedicineMutation` (Fase 1)
- `useProtocolDelete`, `useProtocolMutation`, `useProtocolStats` (Fase 2)
- `useFormState`, `useMutation` (shared)
