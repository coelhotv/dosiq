# R-247 — Uso Obrigatório de `maxLength` em Inputs e Textareas [CRITICAL]

## Regra
Qualquer campo de entrada de texto (`<input type="text">`, `<textarea>` e componentes nativos equivalentes como `<TextInput>` do React Native) criado ou modificado em formulários do Dosiq **DEVE** declarar explicitamente o atributo `maxLength` com um limite numérico adequado.

Limites recomendados padrão do projeto:
* **Campos Curtos (Nomes, Títulos de Medicamentos/Tratamentos):** `maxLength={100}` ou `maxLength={150}`
* **Campos Médios (E-mails, Descrições de Medicamentos, Tags):** `maxLength={255}`
* **Campos Longos (Observações de Log, Notas Clínicas):** `maxLength={1000}`
* **Emojis Isolados:** `maxLength={10}` (ver seção de observação sobre emojis)

---

## Por que Importa

A omissão de limites de caracteres em formulários de entrada gera vulnerabilidades severas que foram recorrentemente apontadas pelo Gemini Code Assist (**36 incidentes auditados na base histórica**):

### 1. Quebra de Integridade no Banco de Dados (Postgres Error `22001`)
Colunas em tabelas de produção (como `medicine_logs`, `protocols`, `user_settings`) possuem limites físicos de armazenamento de caracteres ou restrições de rest do PostgreSQL. A tentativa de inserir ou atualizar registros com strings de tamanho infinito resulta em exceções catastróficas em tempo de execução:
> `Error: string or binary data would be truncated (Postgres SQLSTATE 22001)`

Isso causa falhas silenciosas de mutação e impede que o paciente grave seus dados.

### 2. clipping e Overlap Visual de Layout na UI (Mobile & Web)
Sem `maxLength`, usuários de má-fé ou ações de colar acidentais podem introduzir strings gigantes que quebram o fluxo de renderização (flexbox/grid layout), transbordando e sobrepondo outros elementos de tela, degradando severamente a experiência de visualização.

### 3. Vulnerabilidades locais de Segurança (DoS)
O processamento de strings excessivamente longas na manipulação do estado React, renderização de tabelas e processamento de buscas consome recursos pesados da CPU e thread principal, provocando lentidão perceptível (jank) e crash em dispositivos mobile low-end.

---

## Casos de Uso Especiais

### 1. Campos de Emoji Isolados
Ao implementar seletores de emoji baseados em texto puro, nunca use limites excessivamente restritivos como `maxLength={1}` ou `maxLength={4}`. Emojis modernos utilizam sequências complexas de múltiplos caracteres Unicode combinados com *Zero Width Joiners* (ZWJ). 
* **Regra:** Para emojis, configure `maxLength={10}` e implemente a validação semântica de "apenas um caractere visual" via lógica de negócio ou schema Zod (`z.string().emoji()`).

### 2. Validação Dupla com Zod
O `maxLength` na UI atua como a primeira linha de defesa contra erros acidentais e mantém a experiência do usuário fluida (impedindo a digitação espúria). No entanto, toda mutation **DEVE** continuar sendo validada nos Services usando o schema Zod canônico:
```javascript
const medicineSchema = z.object({
  name: z.string().min(1).max(100, "O nome deve ter no máximo 100 caracteres")
});
```

## Exemplos de Código

### ❌ Incorreto (Web PWA)
```jsx
// Permite colar strings infinitas que estouram o layout e quebram o INSERT
<input
  type="text"
  value={treatmentName}
  onChange={(e) => setTreatmentName(e.target.value)}
  placeholder="Ex: Anti-inflamatório"
/>
```

### ✅ Correto (Web PWA)
```jsx
<input
  type="text"
  value={treatmentName}
  onChange={(e) => setTreatmentName(e.target.value)}
  maxLength={100}
  placeholder="Ex: Anti-inflamatório"
/>
```

### ❌ Incorreto (React Native Mobile)
```jsx
<TextInput
  value={observations}
  onChangeText={setObservations}
  placeholder="Adicione observações sobre a tomada..."
  multiline
/>
```

### ✅ Correto (React Native Mobile)
```jsx
<TextInput
  value={observations}
  onChangeText={setObservations}
  maxLength={1000}
  placeholder="Adicione observações sobre a tomada..."
  multiline
/>
```
