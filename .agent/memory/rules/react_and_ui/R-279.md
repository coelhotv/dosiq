# [R-279] Lógica de domínio não nasce em `views/` — desce para feature/core

## Context
`apps/web/src/views/` é a camada de **composição/orquestração**: monta hooks, services e componentes de feature numa tela. Não é onde regra de negócio deve viver. Funções de domínio (status clínico, cálculo de dose/custo, derivações de estoque) escritas inline numa view ficam: (a) não testáveis isoladamente, (b) invisíveis para mobile (`@dosiq/core` é o ponto de paridade web↔mobile), (c) sujeitas a drift quando duplicadas.

Decisão 038 (A + carve-out, RC3): `views/` segue como camada legítima de composição — **não** se baixa lógica em massa (risco em lógica clínica testada, strangler-fig). Mas vazamentos pontuais de domínio devem descer.

## Rule
Função **pura de domínio** definida dentro de um arquivo `views/*.jsx` é um cheiro. Extrair para:
- `@dosiq/core` (`packages/core/src/utils/`) quando há (ou pode haver) paridade web↔mobile, com teste unitário; **ou**
- `features/<feature>/` (hook/service/util) quando é específica da feature web.

A view passa a **importar** e apenas orquestrar. Não confundir com JSX/handlers/estado de UI — esses pertencem à view.

## Example
### ❌ Incorrect
```jsx
// views/Stock.jsx
function deriveProtocolStatus(protocol, now = getNow()) {
  if (!protocol.end_date) return 'ativa'
  // ...regra de vigência inline, sem teste, invisível p/ mobile
}
```

### ✅ Correct
```jsx
// views/Stock.jsx
import { derivePrescriptionStatus } from '@dosiq/core'
// core: packages/core/src/utils/prescriptionStatus.js + __tests__/prescriptionStatus.test.js
```
