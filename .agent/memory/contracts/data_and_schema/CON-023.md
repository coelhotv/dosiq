# [CON-023] Timeline read service + adapter (FP-3)

**Status:** active · **Layer:** warm · **Domain:** data_and_schema
**Criado:** 2026-05-31 (PR-F4.1 / Fase 4 S4.1+S4.2)

## Interface

`packages/core/src/utils/timeline.js` (builder PURO):
- `buildTimeline(events, { tz='America/Sao_Paulo', order='desc' }) → TimelineEvent[]`
  ordena por instante absoluto (`occurred_at`), anexa `localDay` derivado no `tz`.
- `groupByLocalDay(events) → [{ localDay, events }]` (derivação de exibição; não reordena).
- `deriveLocalDay(occurredAt, tz) → 'YYYY-MM-DD'|null`.
- `TimelineEvent = { id, type, occurred_at, payload, localDay? }`; `type` é **string aberta**
  (`'dose'` hoje; `'biomarker'`/`'note'` depois — FP-3/ADR-050).

`packages/core/src/services/timelineService.js`:
- `doseInstancesToEvents(instances, logs, { protocolsById }) → TimelineEvent[]` — adapter PURO.
  Dedupe: instância ancorada + seu log = 1 evento; log avulso coberto por slot
  representado (tolerância) suprimido (AP-193); skipped_* ocultos; taken usa `taken_at`
  real como `occurred_at`, demais usam `scheduled_for`.
- `createTimelineService({ client }).getTimeline({ userId, fromTs, toTs, tz, order, protocolsById })`
  → busca `repo.getWindow` + logs paginados (AP-186) → adapter → builder.

## Invariantes
- Builder e adapter são PUROS (sem I/O); só o service toca o client.
- Limites de janela em UTC real (AP-194) — `tz` só governa derivação de dia local.
- Novo `event.type` entra por adapter + renderizador, sem tocar builder nem UI.
