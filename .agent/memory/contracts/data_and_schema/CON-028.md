# CON-028 — Interface do fetcher + builder de contexto do chatbot (@dosiq/core/chatbot)

**Status:** proposed · **Categoria:** data_and_schema · **Spec:** 015 · **ADR:** ADR-074

## Interface

```js
// @dosiq/core/chatbot
fetchChatbotContextData({ supabase, getUserId }) : Promise<ChatbotContextData>
buildPatientContext(data: ChatbotContextData) : string
```

### ChatbotContextData (saída do fetcher == entrada do builder; Zod-validado)
```
{
  medicines:      Medicine[],        // id, name, active_ingredient, therapeutic_class, dosage_per_pill, dosage_unit, ...
  protocols:      Protocol[],        // + JOIN treatment_plan(id, name, emoji, color)  ← chave do grouping
  logs:           MedicineLog[],     // protocol_id, taken_at, quantity_taken
  stockSummary:   StockSummary[],    // { medicine, total, daysRemaining, dailyIntake, isLow, isZero }
  stats:          { adherence, ... },
  doseInstances:  DoseInstance[],    // p/ doses pendentes/atrasadas (hoje server NÃO passa — passa a passar)
  treatmentPlans: TreatmentPlan[]    // { id, name } — fallback/listagem (grouping primário lê protocol.treatment_plan)
}
```

## Invariantes
- **Fonte única:** os selects vivem SÓ no fetcher do core. Nenhuma superfície define selects de contexto
  própria (web/mobile/bot chamam `fetchChatbotContextData`).
- **Builder puro:** sem Supabase, sem `new Date()` (R-020 — usar dateUtils do core), sem dep de plataforma.
- **Compat:** contexto sem plano nomeado → grupo "Sem plano"; formato legado preservado p/ quem não agrupa.
- **Não-breaking p/ `api/chatbot.js`:** continua recebendo `patientContext` string; só muda quem o monta.
- **Paridade:** mesma `ChatbotContextData` → mesma string nas 3 superfícies (teste FR-011).

## Consumidores
- web `chatbotService.js` · mobile `chatbotService` (novo) · Telegram `chatbotServerService.js`.
