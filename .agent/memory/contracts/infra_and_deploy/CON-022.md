# CON-022: `getUserTime` + dateUtils tz-aware API

**File:** `packages/core/src/utils/dateUtils.js`

## Assinaturas

```js
// Primitiva nova — generaliza getSaoPauloTime por fuso
getUserTime(date = new Date(), tz = 'America/Sao_Paulo') -> Date

// Wrapper retrocompatível (delega a getUserTime com SP)
getSaoPauloTime(date = new Date()) -> Date

// Param tz opcional adicionado (default 'America/Sao_Paulo')
getNow(tz = 'America/Sao_Paulo') -> Date
getTodayLocal(tz = 'America/Sao_Paulo') -> string 'YYYY-MM-DD'
getYesterdayLocal(tz = 'America/Sao_Paulo') -> string 'YYYY-MM-DD'
getStartOfDayISO(dateStr, tz = 'America/Sao_Paulo') -> string ISO UTC
getEndOfDayISO(dateStr, tz = 'America/Sao_Paulo') -> string ISO UTC
```

Exportadas via barrel `packages/core/src/utils/index.js` e `@dosiq/core`.

## Contrato

- O `Date` retornado por `getUserTime`/`getSaoPauloTime` carrega os valores wall-clock do fuso pedido (`getHours()`/`getDate()` refletem o relógio local daquele tz). Truque `new Date(isoStr)` preservado — CI-safe (AP-W14/AP-W16).
- **`tz` é sempre opcional com default `'America/Sao_Paulo'`** → os ~250 callers existentes não mudam de comportamento (non-breaking, ADR-049).
- Core **não lê DB**; o caller injeta `tz` a partir de `user_settings.timezone`.

## Breaking changes (exigem ADR)

- Mudar o default de qualquer param tz (quebraria os 250 callers).
- Alterar a lógica de normalização wall-clock (`new Date(isoStr)`).
- Remover/renomear `getSaoPauloTime` (wrapper de compat).

## Migração de callers (futuro — Fase 3)

Callers passam a injetar `tz` do usuário gradualmente (adesão/streak primeiro). Enquanto não migrados, operam em SP por default — comportamento idêntico ao pré-ADR-049.
