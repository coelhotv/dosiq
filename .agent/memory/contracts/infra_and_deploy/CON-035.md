# CON-035 — `ContentBuilder` da notification_outbox (argumento de assunto)

**Status**: accepted
**Criado**: 2026-08-19 (spec 050, PR 1a)
**Arquivo**: `server/notifications/outbox/drainOutbox.ts`
**Relacionado**: ADR-078 (outbox), CON-032

## Interface

```ts
export type ContentBuilder = (args: {
  userId: string;
  periodKey: string;
  subjectId: string | null;   // ADITIVO — spec 050
  settings: UserSettings | undefined;
}) => Promise<Record<string, unknown> | null>;
```

## Semântica

- O builder é chamado **no envio**, não no enfileiramento: a fila guarda só referências (SEC-1 do
  ADR-078) e o conteúdo nasce de dados frescos. Devolver `null` = "deixou de ser elegível agora"
  → o drain marca `sent` sem disparar nada.
- `subjectId` identifica **de qual item** a linha fala quando o kind faz fan-out
  (`medicine_id`, `stock.id`...). É `null` para os kinds cuja notificação cobre o
  usuário/período inteiro — os 4 originais (`daily_adherence`, `weekly_adherence`,
  `monthly_report`, `daily_digest`).
- O drain repassa `row.subject_id ?? null`; um builder que ignora o campo continua correto.

## Compatibilidade

**Mudança aditiva, não-breaking.** O argumento é um campo novo no objeto de argumento: builders
existentes desestruturam só o que usam e seguem funcionando sem edição. Foi exatamente o caso dos
4 builders de `api/notify.ts` no PR 1a — nenhum precisou mudar.

## Chave de idempotência associada

`notification_outbox` UNIQUE `(user_id, kind, period_key, subject_id)` **NULLS NOT DISTINCT** —
ver ADR-078. A cláusula é o que permite `subject_id` NULL preservar a semântica antiga: duas
linhas NULL ainda colidem. Sem ela, os 4 kinds perderiam a idempotência em silêncio.
