# CON-033 — Kill switch de versão mínima (resolver puro + superfície de config)

**Status:** `accepted` — C5 do PR 1.5b, 2026-07-26 (código em `packages/core/src/utils/versionGate.ts` + `apps/mobile/src/platform/versionGate/`)
**ADR:** ADR-091 · **Spec:** 051 fatia 051-A · **Tier:** 2
**Registro no índice:** `.agent/memory/CONTRACTS_INDEX.md` (C5 do PR 1.5b). ⚠️ **Realocado em
2026-08-15**: o arquivo vivia em `plans/specs/051-expo-updates/contracts/`, que é **gitignored** —
o contrato existia só na máquina do PO e não viajava no repo. Contrato é memória DEVFLOW versionada.

> **Por que é contrato (Princípio V):** interface **nova e cross-package** — nasce em `@dosiq/core` e
> é consumida pelo mobile (decisão de boot) e pela web (painel admin, via o mesmo schema Zod). Uma
> mudança na assinatura ou na semântica do resolver muda o comportamento de **bloqueio de boot** de
> toda a base instalada.

---

## 1. Resolver puro — `@dosiq/core`

```
resolveVersionGate(installedVersion, gateRow) → VersionGateDecision
```

- **PURO**: sem I/O, sem relógio, sem acesso a rede ou storage. Recebe tudo, decide, devolve.
- `installedVersion`: `string | null | undefined` — a versão do binário (`Constants.expoConfig?.version`).
- `gateRow`: a linha de `app_version_gate` para a plataforma, **ou `null`** (ausente / erro de leitura
  / offline). O chamador **não** interpreta o erro — converte para `null` e deixa o resolver decidir.
- Retorno: união discriminada. Estreitar com `=== false` / `=== true`, **nunca** com `!decision.blocked`
  (**R-286** — `!` não discrimina sob consumidor `strict:false`; mobile e api herdam da base).

### Tabela-verdade — NORMATIVA

Esta tabela **é** o contrato. Cada linha vira uma asserção no teste unitário. Alterá-la exige emenda
ao ADR-091.

| Condição | Decisão |
|---|---|
| `gateRow == null` (rede, timeout, offline, `error` do PostgREST, linha ausente) | **ABRE** |
| `gateRow.is_active === false` | **ABRE** |
| `compareSemver(installedVersion, gateRow.min_supported_version) === null` | **ABRE** |
| `compareSemver(installedVersion, gateRow.min_supported_version) === -1` | **BLOQUEIA** |
| qualquer outro caso | **ABRE** |

**Invariantes:**

1. 🔴 **`satisfiesSemver` é PROIBIDA neste caminho.** É fail-closed por design
   (`packages/core/src/utils/semver.ts:45`) porque nasceu para filtrar nudges. No boot inverteria a
   semântica: config corrompida ⇒ bloqueio universal. Usar **`compareSemver`**, cujo `null` é
   exatamente o "indeterminado" que o AP-303 manda deixar passar.
2. 🔴 **Fail-open é total.** Não existe caminho de retorno "bloqueia" que não seja a linha `-1` acima.
   Na dúvida, abre.
3. 🔴 **Nenhum default de versão instalada.** Sem fallback `'0.15.0'` (`useNudges.ts:11`) — default
   desatualizado converte indeterminação em bloqueio falso.
4. 🔴 **A UI obedece.** Nenhum consumidor reintroduz condição própria sobre bloquear/abrir. Antídoto
   direto do AP-303 (*"guard de UI que contradiz a decisão pura que consome"*).
5. **Sem cache.** O chamador não persiste a decisão. Cachear um bloqueio ativo bricka o usuário
   offline para sempre.

### O que a decisão carrega quando bloqueia

`message` (ou `null` ⇒ o consumidor usa copy compilada) e `storeUrl` (ou `null` ⇒ constante compilada).
**Ambos são conteúdo remoto não-confiável** — as validações do §3 correm no consumidor, não no resolver.

## 2. Tabela `public.app_version_gate`

| Coluna | Tipo | Contrato |
|---|---|---|
| `platform` | `text` PK | CHECK `('ios','android')` — sincronizado com o enum do core (**R-271**) |
| `min_supported_version` | `text` nullable | `X.Y.Z` imposto pelo **Zod da escrita**; leitura é tolerante (inválido ⇒ abre) |
| `is_active` | `boolean NOT NULL DEFAULT false` | nasce desligado |
| `message` | `text` nullable | cap de tamanho no Zod; renderizado como texto puro |
| `store_url` | `text` nullable | allowlist no Zod **e** no cliente |
| `updated_at` | `timestamptz NOT NULL DEFAULT now()` | **não legível** por `anon`/`authenticated` |
| `updated_by` | `uuid` | FK→`auth.users(id)` `ON DELETE SET NULL` (**R-287**); **não legível** por `anon`/`authenticated` |

**Modelo de acesso — duas camadas independentes (AP-278). Nenhuma pode ser a única:**

1. `REVOKE INSERT, UPDATE, DELETE, TRUNCATE ON public.app_version_gate FROM anon, authenticated;`
   ⚠️ `REVOKE ... FROM PUBLIC` sozinho **não** basta neste projeto — os privilégios vêm de
   `ALTER DEFAULT PRIVILEGES` nomeando os roles.
2. RLS **ON** · **uma** policy de `SELECT` para **`anon` E `authenticated`** com `USING (true)` ·
   **zero** policies de escrita.
3. Column-level: `REVOKE SELECT (updated_by, updated_at) FROM anon, authenticated`.

⚠️ **Não copiar a policy dos nudges** (restrita a `authenticated`): o bloqueio ocorre antes de haver
sessão — `anon` precisa ler, senão o gate fica mudo justamente para quem abre o app pela primeira vez
depois de o servidor mudar.

**Select autorizado do cliente (5 colunas, exatamente):**
`platform, min_supported_version, is_active, message, store_url`
Pedir `*` devolve erro de permissão — comportamento desejado; documentar no código para que ninguém
"conserte".

## 3. Consumidor mobile — obrigações

- Ler como **`anon`**, com timeout curto, **em paralelo** ao render. Nunca segurar a árvore esperando.
- **Reavaliar no foreground, não só no mount.** Boa parte da base deixa o app minimizado por dias/
  semanas — um gate ativado nesse meio-tempo só seria visto por quem reabrisse o processo do zero.
  `AppState.addEventListener('change', ...)` reexecuta a checagem em toda transição pra `active`
  (achado no smoke do PO, 2026-07-26).
- **Inspecionar `error` explicitamente**: `supabase-js` não lança — devolve `{ data: null, error }`.
  Qualquer `error` ⇒ tratar como `gateRow = null` (abre). O `useNudges` atual não inspeciona e por isso
  sobrescreve o cache bom com `[]` (`useNudges.ts:74-86`) — não repetir.
- **Allowlist de `store_url`**: aceitar apenas `https://apps.apple.com/…` e `https://play.google.com/…`.
  Fora dela ⇒ tratar como ausente e cair para constante compilada.
- **`message` como texto puro**, com cap; sem markdown, HTML ou link tocável.
- 🔴 **Saída para a web é constante COMPILADA** (`https://dosiq.app`). Nunca vem da linha do gate — do
  contrário a config que aplica o bloqueio também poderia apagar a saída de emergência.
- **Alarmes de dose não são suprimidos**: `registerAlarmBackgroundHandler()` roda em
  `apps/mobile/index.ts` antes do `AppRegistry.registerComponent`, fora da árvore React. Afirmar no
  código e provar no smoke.
- 🔴 **O overlay CEDE visualmente ao alarme full-screen** — obrigação clínica > bloqueio de update.
  `useAlarmScreenActive` detecta rota atual == `AlarmFullScreen` e o `VersionGateOverlay` renderiza
  `null` nesse caso (a decisão pura `blocked` não muda; só a UI escolhe não desenhar por cima). Fix
  exige **polling**, não `navigationRef.addListener('state', ...)`: o hook monta fora da árvore do
  `NavigationContainer` (sibling de `NavigationTree`, que só cria o container depois de `session`
  resolver) e um listener anexado nesse momento nunca dispara depois, mesmo com navegação real
  acontecendo (achado no smoke do PO, 2026-07-26 — [[AP-323]]).
- `Linking.openURL(...)` (CTA de loja e link `dosiq.app`) sempre com `.catch(() => {})` — promise
  não tratada é finding padrão de revisor (AP-138), sem efeito funcional aqui mas gate de qualidade.

## 4. Endpoint admin — `PATCH /api/admin?resource=versionGate`

Handler em `api/admin/_handlers/versionGate.ts`, dentro do router existente (**R-090** — sem função
serverless nova; **R-091** — helper em diretório `_`-prefixado).

**Autorização:** `verifyAdminAccess` com `uid == ADMIN_USER_ID` (ADR-091 D10). Env ausente ⇒ **negar**.
`getUser()` sempre (validação server-side) — nunca decode local de JWT. 401/403 uniforme para fora.

**Guarda de raio de impacto — SERVER-SIDE:**
- Ativar (`is_active: false → true`) exige `acknowledge_affected_devices: <contagem exata>` no corpo.
  O servidor computa a sua própria contagem (união `notification_devices ∪ device_activity`, janela
  30d, dedupe por `(user_id, platform)` — mesma lógica de `scripts/fleet-versions.sh`) e **recusa**
  quando não bate, nomeando a contagem correta na resposta.
- **Limiar = zero**: toda ativação exige o acknowledge (decisão de Planning — ver `plan.md`
  §Clarifications).
- **Desativar (`is_active: true → false`) NÃO exige acknowledge.** Destravar tem de ser imediato.
- A UI **apenas exibe** — não é ela que autoriza. Controle que só existe na tela é sugestão (S-7).

`updated_by` é preenchido com o uid do admin autenticado; `updated_at` por `now()`.

## 5. Invariante de recuperação (ADR-091 D9)

**O kill switch nunca gateia a superfície usada para desativá-lo.** Hoje o gate é mobile-only e o
painel é web — satisfeito por construção. Se o web entrar no escopo do gate (NC6), o painel admin sai
do escopo **por construção**, não por configuração.
