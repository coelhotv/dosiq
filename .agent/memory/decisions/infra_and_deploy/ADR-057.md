# ADR-057 — Fonte do reminder = `dose_instances` + idempotência `notified_at` + cutover flag

**Status:** accepted · **Date:** 2026-06-03 · **Spec:** 011-notifications-from-instances
**Pack:** infra_and_deploy / notifications · **Relaciona:** ADR-048 (dose_instances fonte única),
ADR-051 (geração), ADR-029/030 (dispatcher + flag), R-200/R-220 (3-layer), R-191/AP-112
(1 push/bloco), AP-186 (PostgREST trunca 1000), AP-194 (tz instante absoluto). **Pré-req de:** ADR-056 (010).

## Contexto

O refactor `dose_instances` (ADR-048) migrou adesão/timeline/"hoje" do modelo inferido para a
fonte única materializada. **O reminder de dose ficou de fora** — última ilha do modelo inferido:

- `server/bot/_reminderHelpers.js:17-28` lê `from('protocols')` e re-expande `time_schedule` via
  `partitionDoses` — não toca `dose_instances`.
- `dose_instances.notified_at` (DOSE_INSTANCES.md:57, desenhada p/ idempotência) está **100%
  ociosa** — zero leitura/escrita no repo.
- Dedup é **heurística/temporal** (`notificationDeduplicator.js:4`, janela 5 min em
  `notification_log`), não por-ocorrência. `dose_reminder` individual nem passa por dedup.

Consequências: inconsistência arquitetural (lembrete pode divergir do "hoje"/adesão);
idempotência frágil (overlap de cron/retry pode duplicar); sem herança de tz/cross-meia-noite que
`dose_instances` já resolve; **bloqueia a 010** (alarme crítico v2 precisa de roteamento per-dose;
sobre o stack atual vira hack de duas fontes — ADR-056).

## Decisão

**1. Trocar a fonte do reminder** de `protocols`+schedule para **`dose_instances`** (ocorrências
devidas). Query server-side (supabase raw, o reminder não usa o core repo): `status='pending'` +
`scheduled_for` na janela do minuto corrente (instante absoluto UTC, clamp ao presente) +
`notified_at IS NULL` + (`snoozed_until IS NULL OR <= now`), JOIN `protocols`→`medicines`/
`treatment_plans`. Mapear cada linha para o **mesmo shape de `dose`** que `partitionDoses` já
consome (+ `instanceId` interno). **Agrupamento/kinds/dispatcher (CON-019) inalterados** — troca só
o input.

**2. Idempotência por `notified_at`** — após `dispatcher.dispatch` retornar sucesso em **≥1 canal
configurado**, gravar `notified_at = now()` nas instâncias do bloco. Por-ocorrência (não por-canal).
Falha total → não marca, re-tenta no próximo tick (**at-least-once** aceito; base friends/family).
Canais parciais que falharam → **DLQ existente** (Gate 3.5, `dispatchNotification.js:110`), sem
re-disparar o bloco.

**3. Aposentar a dedup heurística** (`shouldSendGroupedNotification` 5 min) **só para os kinds de
dose** — `notified_at` é estritamente melhor (preciso por-ocorrência). `notificationDeduplicator`
permanece para tipos sem ocorrência (`daily_digest`, stock); `notification_log` (auditoria/inbox
L3) intacto.

**4. Rollout = cutover + feature flag de rollback** — env `REMINDER_SOURCE`
(`'instances'`|`'protocols'`, default `'protocols'` até cutover). Rollback = trocar env, **sem
deploy** de código. Sem shadow/paralelo runtime (paridade vira **teste**, SC-001). Após estabilizar,
via legada vira código morto (limpeza futura).

## Opções consideradas

- **(escolhida) Cutover + flag.** Simples, rollback barato, base pequena. Risco: paridade no
  cutover → mitigado por teste de paridade obrigatório (SC-001).
- **Shadow/dual-run com comparação runtime.** Mais seguro mas overhead alto p/ friends/family;
  paridade já cobre via teste. Rejeitado (over-engineering).
- **Manter dedup heurística + só ler dose_instances.** Mantém dois mecanismos de idempotência
  divergentes. Rejeitado — `notified_at` substitui com precisão.

## Consequências

- ✅ Reminder alinha com "hoje"/adesão (fonte única); herda tz/cross-meia-noite (AP-194).
- ✅ Idempotência precisa por-ocorrência; `dose_reminder` individual ganha idempotência (não tinha).
- ✅ **Destrava a 010**: gate crítico per-dose passa a ler `dose_instances.critical_alarm` **direto**
  → ADR-056 re-escopo (some o hack `protocols.critical_alarm` de duas fontes).
- ⚠️ At-least-once (crash pós-envio re-notifica) — aceito p/ base pequena; preferível a perder dose.
- ⚠️ Dependência de ordem: instâncias materializadas (cron 03:00 + JIT, ADR-051) antes da leitura.
- ⚠️ **Sem migração de schema** — `notified_at`/`snoozed_until` já existem; backfill nulo seguro.

## Escopo (NÃO inclui)

`critical_alarm` + roteamento crítico per-dose → **spec 010** (esta é a fundação). Mudança de
canais/preferências (`resolveChannelsForUser`) inalterada. Geração de `dose_instances` (ADR-051)
inalterada — só consumimos.
