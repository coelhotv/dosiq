# [ADR-039] Switch unico de kinds em buildNotificationPayload.js ate 15 kinds

## Status
Accepted (2026-04-30)

## Context
A camada de presentation L2 (`server/notifications/payloads/buildNotificationPayload.js`) usa um `switch` statement para rotear cada `kind` (`daily_digest`, `dose_reminder_by_plan`, etc) para sua logica de formatacao. Apos a wave de consolidacao, o arquivo tera ~10 kinds suportados.

A discussao arquitetural (`notifications_architecture_vision.md`) identificou que o switch e adequado para 10 kinds mas vira inferno em 30+. Alternativas escalaveis:
1. **Per-kind builder modules**: `payloads/builders/dailyDigestBuilder.js`, com registry (`register('daily_digest', builder)`).
2. **Templating engine**: Mustache/Handlebars com templates declarativos por kind. Habilita i18n trivial.
3. **Builder factory pattern**: classe abstrata `NotificationBuilder` com subclasses por kind.

## Decision
Mantemos o switch unico em `buildNotificationPayload.js` ate o **15o kind**. Nesse momento, executar refactor cosmetico para **per-kind builder modules** (alternativa 1). Templating engine (alternativa 2) so entra quando i18n/white-label aparecer no roadmap.

## Consequences
- **Pro**: Para 10 kinds atuais, switch e o mais legivel — toda logica de presentation visivel em um arquivo, facil grep/diff.
- **Pro**: Refactor para modules e mecanico (extrair cada `case` para arquivo + adicionar `register()`); pode ser feito por agente em <1h quando trigger atingir.
- **Con**: Arquivo cresce ~50-80 linhas por kind. Em 15 kinds, ~1000 linhas — proximo do limite de cognitive load.
- **Con**: Adicionar kind requer editar arquivo central — risco de merge conflict em equipe (irrelevante hoje, dev solo).
- **Mitigacao**: Ao ultrapassar **12 kinds**, abrir issue de tracking para split. Nao deixar passar de 15.
- **Trigger de revisao**: Contagem de kinds em `kindSchema.options.length` >= 15.

## Alternatives Considered
1. **Split agora (10 kinds)** — descartado: prematuro; switch ainda e mais legivel.
2. **Templating engine (Mustache/Handlebars)** — descartado: i18n nao e prioridade; templates declarativos perdem capacidade de logica condicional rica (ex: `if percentage >= 90`); ganho de complexidade nao compensa.
3. **Class-based builder (factory pattern)** — descartado: JS funcional + Zod schemas ja entregam o mesmo isolamento sem ceremonia OO.
