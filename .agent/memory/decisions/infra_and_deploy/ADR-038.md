# [ADR-038] Manutencao de scheduler-pull; domain events adiados ate caso real-time

## Status
Accepted (2026-04-30)

## Context
A arquitetura atual de notificacoes do Dosiq e **scheduler-pull**: cron (`api/notify.js`) dispara `tasks.js` que calcula elegibilidade e envia ao dispatcher. Nao ha bus de eventos de dominio nem subscribers — o "evento" e implicito no firing do cron + condicao de elegibilidade.

A discussao arquitetural (`notifications_architecture_vision.md`) identificou que sistemas event-based canonicos (Knock, Courier, SendGrid Notify) operam com:
1. Dominio emite eventos (`DoseScheduled`, `StockLow`, `StreakAchieved`).
2. Bus de eventos roteia para subscribers.
3. Subscribers traduzem em `{ kind, data }` e enviam ao mesmo pipeline L2/L3.

Casos onde o modelo atual e limitante:
- Notificacao real-time disparada por acao do usuario (ex: app registra dose → alerta para cuidador).
- Fan-out (1 evento → N notificacoes para diferentes audiencias).
- Compliance auditavel (evento como source-of-truth, notificacao como side-effect).

## Decision
Mantemos o modelo scheduler-pull. Bus de eventos de dominio **so sera introduzido quando emergir o primeiro caso de uso real-time concreto** (ex: feature de cuidador, integracao com wearable, registro reativo).

## Consequences
- **Pro**: Sistema atual funciona bem para use cases existentes (digests, reminders, reports — todos cron-driven).
- **Pro**: Evita complexidade de bus + replay + ordering antes de necessidade real.
- **Pro**: Arquitetura 3-camadas atual **nao impede** evolucao — bus entra **acima** de L1 sem tocar L2/L3.
- **Con**: Quando caso real-time entrar, primeira implementacao tera que escolher: (a) hack tatico (chamar dispatcher direto do handler) — divida tecnica; (b) introduzir bus na hora — atraso da feature.
- **Mitigacao**: Manter L1 (`tasks.js`) como **unico produtor** atual de `{ kind, data }`. Quando bus entrar, sera so adicionar **outro produtor** (subscriber) consumindo o mesmo dispatcher.
- **Trigger de revisao**: Primeira PRD de feature real-time. Abrir wave dedicada para introducao de event bus (candidatos: in-process EventEmitter, Supabase Realtime, ou external — Vercel Queues, Inngest).

## Alternatives Considered
1. **Introduzir event bus agora** — descartado: nenhum consumidor real existe; abstrair sem use case = overengineering.
2. **Migrar tudo para event-driven** — descartado: cron-driven e perfeitamente adequado para digests/reports recorrentes; modelo hibrido (cron + events) e o padrao da industria.
3. **Wrapper no cron emitindo "pseudo-eventos"** — descartado: ganho zero; complexidade extra sem subscribers reais.
