# [ADR-037] Adiamento de content-tree + format adapters em notificacoes

## Status
Accepted (2026-04-30)

## Context
Apos a consolidacao da arquitetura de 3 camadas para notificacoes (`notifications_architecture_consolidation_plan.md`), L2 (`buildNotificationPayload.js`) emite payload com strings paralelas: `body` (MarkdownV2 rich, consumido por Telegram + persistido no Inbox) e `pushBody` (plain, consumido por Expo Push). Inbox renderer aprende a exibir Markdown em GATE 6.5.

A discussao arquitetural (registrada em `notifications_architecture_vision.md`) identificou que o modelo dual-string nao escala para 4+ canais com formatos divergentes (Email HTML, SMS plano, WhatsApp template). O caminho ideal de longo prazo e um **content tree** semantico (`[{ type: 'heading' }, { type: 'list' }, ...]`) com **format adapters** (`toMarkdownV2`, `toPlainText`, `toHTML`, `toSMS`) — modelo usado por Slack Block Kit, MS Teams Adaptive Cards, MJML.

## Decision
Adiamos a migracao para content-tree + format adapters **ate o 4o canal real materializar**. Mantemos o modelo dual-string atual (`body` + `pushBody`) ate la.

## Consequences
- **Pro**: Evita custo de refactor (~3-5 dias) sem ROI imediato. YAGNI consciente — 2 canais ativos (Telegram + Push) + Inbox como leitor passivo nao justificam abstracao.
- **Pro**: Mantem footprint cognitivo baixo. Adicionar kind hoje requer apenas case no switch de L2.
- **Con**: Quando 3o canal real (SMS/Email/WhatsApp) entrar, refactor sera obrigatorio antes de implementar — bloqueio temporal.
- **Con**: `body` armazenado no Inbox e MarkdownV2 escapado (formato Telegram), nao um IR neutro. Migracao futura precisara de regravacao ou shim de leitura.
- **Mitigacao**: GATE 6.5 fecha o sintoma visual imediato (Inbox renderiza Markdown). Nao acumulamos divida visivel ao usuario.
- **Trigger de revisao**: Quando primeiro canal nao-Markdown entrar no roadmap, abrir refactor wave dedicada com este ADR como ponto de partida.

## Alternatives Considered
1. **Fazer refactor agora** — descartado: custo > beneficio com 2 canais.
2. **Tres campos paralelos (`body`, `pushBody`, `inboxBody`)** — descartado: continua acoplado por canal; apenas posterga o problema.
3. **Content tree + adapters imediato** — descartado por YAGNI; registrado como caminho futuro.
