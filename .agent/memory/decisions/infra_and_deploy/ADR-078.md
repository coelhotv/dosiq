# ADR-078 — Outbox em Postgres como mecanismo de batch de notificações

**Status**: accepted (043 Slice A implementado, 2026-07-10 — migração `20260707_notification_outbox.sql` + `server/notifications/outbox/{periodKey,outboxRepository,drainOutbox,enqueueReports,runOutboxCycle}.ts` + wiring `api/notify.ts` atrás de `OUTBOX_KINDS`. Kinds migrados: daily_adherence/weekly_adherence/monthly_report; daily_digest/stock_alert = cutover futuro no mesmo mecanismo. Reversível por env.)
**Contexto**: spec 043 — `api/notify.ts` processa relatórios (daily/weekly/monthly/digest/stock) sequencialmente na mesma invocação dos dose reminders. Log prod 2026-07-04: 33 usuários, 12.4s serial; teto `maxDuration 60s` estoura a ~150 usuários. Sem checkpoint: crash no usuário K de N = K notificados, N−K perdidos, re-execução cega. Gatilho semanal em fatia de minuto exata (família AP-259).

## Decisão

Relatórios em lote passam pelo padrão **outbox**: tabela `notification_outbox` com **apenas referências** (`user_id + kind + period_key` — SEM payload, decisão SEC-1/LGPD) e `UNIQUE (user_id, kind, period_key)`.

- **Enfileirar**: tick elegível INSERTa com `ON CONFLICT DO NOTHING` — idempotência é constraint, não lógica; elegibilidade por RANGE de horário (nunca minuto exato).
- **Drenar**: ticks seguintes fazem `SELECT ... WHERE status='pending' FOR UPDATE SKIP LOCKED LIMIT 25` — invocações concorrentes nunca duplicam; retomada = drenar o que sobrou; conteúdo do relatório construído NO ENVIO (dado fresco, zero cópia de PII na fila).
- **Semântica**: flip `pending→sent` APÓS envio (at-least-once para relatórios). Dose reminders FICAM FORA — caminho por-minuto com `notified_at` (at-most-once, ADR-057) intacto.
- **Fronteira com DLQ**: falha de canal → `failed_notification_queue` (fluxo existente); falha de construção → `attempts+1`, cap 3 → `status='failed'`.
- **Segurança**: RLS + zero grants authenticated/anon (server-internal); `channel_results` sem push tokens; prune 90d pg_cron (precedente ADR-077).
- **Reversibilidade**: cutover kind-a-kind atrás de env `OUTBOX_KINDS` (precedente ADR-057 `REMINDER_SOURCE`); kind ausente = caminho legado; rollback sem deploy.

## Alternativas rejeitadas

- **(a) Paralelismo inline + marcador de idempotência na aplicação**: menor diff, mas idempotência/retomada viram lógica frágil de app; timeout continua sendo risco estrutural.
- **(c) Função serverless separada com cron próprio**: consome 1 dos 2 slots do budget Vercel Hobby (R-090); precedente ADR-051 existe, mas outbox resolve isolamento sem gastar slot.
- **Vercel Queues (beta)**: infra nova gerenciada; outbox em Postgres é auditável, testável e é o mesmo padrão da DLQ já em produção.

## Consequências

- + Timeout, duplicata e retomada resolvidos por UM mecanismo; auditoria de entrega (FR-009) de graça na linha.
- + Escala por drenagem incremental (1000 usuários = ~50 ticks) sem mudar arquitetura.
- − Latência de entrega de relatório vira "até o próximo tick × lotes" (minutos) — aceitável para relatórios, inaceitável para reminders (por isso ficam fora).
- − Segunda tabela-fila para operar (junto da DLQ) — mitigado por serem o mesmo padrão mental.

## TODO (aberto — spec 050, planning 2026-08-02)

**Consolidar a redundância `channel_results` × `notification_log` na ordem certa: correlacionar
ANTES de dropar.** Hoje `notification_outbox.channel_results` é **write-only** — verificado: só
`outboxRepository.markSent/markFailed` escrevem; nenhuma UI lê (web/mobile leem `notification_log`
via `useNotificationLog`/`useUnreadBadgeCount`), o retry decide por `attempts` e o dedupe
(`notificationDeduplicator`) lê `notification_log`. Com o prune de 90d, nem histórico durável é.

Dropar direto (opção "consolidar") perderia o único vínculo **linha-da-fila → resultado**:
`notification_log` não tem `outbox_id`, e correlacionar por `(user_id, kind, janela)` é justamente
a chave imprecisa que produziu DOIS falsos positivos na medição do PO-5 da spec 050 — e que piora
com o fan-out (`subject_id`), onde um usuário passa a ter N linhas por kind/dia.

Sequência decidida: **(1)** `notification_log` ganha `outbox_id uuid null` (aditivo, sem migração
de dados) · **(2)** só então `channel_results` é dropada, junto de `ChannelResult`/`toChannelResults`
(este último existe apenas para filtrar token bruto — SEC-3; sumindo ele, some a chance de um campo
novo do dispatcher vazar token para a fila).

Fora do escopo da 050 (é integridade de OBSERVABILIDADE, não de entrega). Spec própria quando
priorizado.
