# [ADR-040] Estratégia de Linting Monorepo e Eficiência de CI

## Status
Accepted (2026-05-01)

## Contexto
Com o crescimento do projeto Dosiq, o sistema de linting legado tornou-se lento e ineficiente. Além disso, a modernização das regras de engenharia (R-020, R-204, R-041) expôs uma dívida técnica de ~1300 erros, o que bloqueava qualquer PR de passar no CI remoto. Outro fator crítico é o limite de minutos do GitHub Actions no plano gratuito, consumido excessivamente por execuções de lint redundantes em arquivos não alterados.

## Decisão
Migrar a arquitetura de linting para o **ESLint Flat Config (v9)** e implementar um **Gate de Lint Progressivo/Incremental** no CI.

### Componentes da Decisão:
1. **Flat Config:** Centralização no root e isolamento de domínios (web/mobile/server) para evitar vazamento de dependências e garantir performance de análise.
2. **Lint Incremental (CI):** Em Pull Requests, o ESLint valida apenas o delta de arquivos alterados. O linter global só é executado em branches protegidas (`main`/`develop`).
3. **Paths Ignore:** Workflows de teste ignoram mudanças puramente de documentação ou memória de agentes.
4. **Concurrency:** Cancelamento automático de builds obsoletos na mesma branch/PR para economia de recursos.

## Consequências
- **Positivas:**
  - Redução drástica no consumo de minutos do GitHub Actions.
  - Pull Requests mais rápidas e focadas na qualidade do código novo.
  - Blindagem automática contra regressões de IA em arquivos staged via `lint-staged`.
- **Negativas:**
  - A dívida técnica legada em arquivos não tocados permanece existindo (porém visível no linter global).
  - Exige manutenção de glob patterns específicos no workflow do CI.
