# ADR-067 — Modelo de estoque dose-primário (dose = métrica fundamental; dia = projeção derivada)

**Status:** accepted
**Data:** 2026-06-13
**Contexto:** 012 Fase B4 / FR-026, FR-027, FR-028, FR-029 (falha conceitual exposta no smoke B2)
**Relaciona:** ADR-058 (líquidos), ADR-065 (units_per_ml fallback), ADR-061 (frequencyDailyFactor)

## Contexto

O modelo de estoque atual conta **dias corridos**: `daysRemaining = estoque ÷ consumo_médio_dia`
([`packages/core/src/utils/stock.js:56`](../../../../packages/core/src/utils/stock.js#L56)). Funde
dois conceitos distintos num número só. Para frequência ≠ diário:

- (a) **engana o display**: "28 dias" para 4 canetas semanais — o paciente pensa em aplicações, não
  em dias corridos;
- (b) **quebra o custo**: o detalhe de estoque exibe "consumo/dia 0,071428…" ilegível e calcula
  custo/dose R$60,71 quando o real é R$425 (R$1700 ÷ 4 doses).

A dose (aplicação/comprimido) é a unidade em que o paciente raciocina; o dia corrido é uma projeção
útil só para a recompra (lead time cronológico).

## Decisão

**A dose é a métrica primária; o dia corrido é derivado.** O core (`stock.js`) calcula três
quantidades, considerando tomadas por dia de tomada:

- `tomadasPorDia = time_schedule.length` (quantas tomadas num dia ativo — pode ser >1 mesmo em
  frequências espaçadas);
- `diasDeTomadaRestantes = estoque ÷ (dosePorTomada × tomadasPorDia)` — **o número exibido**
  (líquido: `doseMl` via `doseToMl` da B2/B3; sólido: unidades). Frequency-agnostic;
- `runwayDias = diasDeTomadaRestantes ÷ frequencyDailyFactor(p)` — dias corridos, **derivado**
  (reusa `frequencyDailyFactor` de `adherenceLogic.js:287`).

**Diário:** `diasDeTomadaRestantes == runwayDias` → zero regressão visual no público atual.

**Display em doses, cor em runway** (FR-028): chip/badge exibem "N doses" (injetável: "N aplicações"
via `INJECTION_CONTAINER_SINGULAR`); a **cor/status** (CRITICAL<7 / LOW<14 / NORMAL<30) continua
medindo `runwayDias` — recompra é cronológica (lead time independe da frequência). Freq diário
mantém "N dias".

**Custo por dose** (FR-027): `custoPorDose = precoUnidade ÷ dosesPorUnidade` como número primário;
`custoPorDia` vira derivado opcional (`custoPorDose × dosesPorDia`) e **formatado** (limite de 3 casas
decimais — fim do `0,071428…`). `costAnalysisSchema` ganha `custoPorDose`.

**Propagação** (FR-029): `refillPredictionService` (data de recompra = hoje + `runwayDias`),
PDF/consultation, Telegram `/estoque` exibem doses como número-base e runway como contexto. Sem
mudança de schema de dados — só camada de cálculo/apresentação. Serverless: `dosesPorDia` reusa
`frequencyDailyFactor` do core.

## Regressões absorvidas (decisão PO 2026-06-13 — fix-while-we're-here)

A raiz das duas regressões abaixo é a **mesma** que motiva ADR-067 (modelo errado de dias para
freq ≠ diário / unidade não convertida). Como B4 reescreve o cálculo de estoque, ambas entram aqui
em vez de carregar dívida até a Fase D:

1. **Cron de alerta de estoque (FR-013c, puxado da Fase D → B4)** —
   [`server/bot/_reminderHelpers.js:511`](../../../../server/bot/_reminderHelpers.js#L511)
   `_processUserStockAlert`: `dailyConsumption` soma `dosage_per_intake` na **unidade de tomada**
   (UI/gotas) sem converter, enquanto `stock.qty` é **ml** → `daysRemaining = floor(ml ÷ UI)`.
   Lantus 5,3 ml com 10 UI/dia → `floor(5,3/10)=0` → alerta crítico **falso** (real: 10 UI = 0,10 ml/dia
   → 53 dias). Pior: o payload (`stock_alert`) exibe `remaining: stock.qty` (5,3 ml) rotulado **"5,3
   doses"**. Correção: (a) cron usa o mesmo cálculo dose-primário do core (converte intake→ml via
   `doseToMl`, aplica `frequencyDailyFactor`); (b) só dispara quando `runwayDias` real < limiar;
   (c) payload exibe doses + unidade correta (R-272). Cobertura jest em `server/` (gotas/UI/ml/sólido).

2. **Card de tratamento (web) diverge do card de estoque** —
   [`refillPredictionService.js:54`](../../../../apps/web/src/features/stock/services/refillPredictionService.js#L54)
   `predictRefill` converte intake→ml (liquid-aware) mas **não aplica `frequencyDailyFactor`** → trata
   dose semanal como diária. Mounjaro mostra "0 dias" no card de tratamento vs "28 dias" no card de
   estoque (este já frequency-aware). Correção: `predictRefill` aplica `frequencyDailyFactor` no consumo
   teórico → ambas as superfícies convergem no `runwayDias` do modelo B4.

## Consequências

- (+) Elimina alerta de estoque falso (push/Telegram) para líquidos/injetáveis — risco clínico real.
- (+) Card de tratamento e card de estoque passam a concordar (fonte única = modelo dose-primário).
- (+) Display alinhado ao modelo mental do paciente (doses/aplicações) para freq ≠ diário.
- (+) Custo legível e correto (custo/dose), fim da dízima ilegível.
- (+) Recompra continua cronológica (runway) — semântica de alerta de estoque intacta.
- (+) Diário sem regressão (`doses == dias`).
- (−) `resolveStockStatus` muda a semântica do input (consumo/dia → par doses+runway); todos os
  callers precisam migrar para o novo cálculo na mesma fase (R-267 read-path; mapear em T038).
- (−) Camada de apresentação tocada em múltiplas superfícies (web badges, mobile badges, PDF,
  Telegram, cron serverless, card de tratamento) — cobertura por testes de cada (R-270 failure modes:
  estoque 0, dosePorTomada 0/NULL, time_schedule vazio, frequencyDailyFactor de freq não mapeada).
- (Δ escopo) **FR-013c sai da Fase D** (cron de alerta de estoque) e entra em B4 — Fase D fica só com
  validade biológica + smoke de insulina + FR-013b (prefill densidade) + FR-015b (frase de push).
  Serverless não roda em dev → teste jest obrigatório (cron não tem smoke manual).
