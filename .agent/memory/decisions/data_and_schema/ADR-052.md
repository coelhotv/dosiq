# ADR-052 — Semântica de unidade como fundação compartilhada (líquidos ∩ diabetes)

## Status
**ACCEPTED** (2026-05-29)

## Contexto

Dois drafts de épico pendentes — [diabetes](../../../../plans/dose_instances_refactor/draft_plan_diabetic_support.md) (insulina basal/bolus + glicemia) e [líquidos](../../../../plans/dose_instances_refactor/LIQUID_MEDICATIONS_EPIC_DRAFT.md) (xaropes/gotas/volume fracionado). ADR-050 já tratou diabetes. Avaliados em conjunto contra o refactor `dose_instances` em curso, com **verificação direta no schema de produção**.

### Achado factual que muda os dois drafts
Verificação no Postgres de prod (`information_schema`):

| Coluna | Tipo real |
|--------|-----------|
| `dose_instances.expected_dose` | **`numeric`** (escala livre) |
| `medicine_logs.quantity_taken` | **`numeric`** (escala livre) |
| `protocols.dosage_per_intake` | **`numeric`** (escala livre) |

→ O modelo de dados **já suporta fração** (2,5 ml, 12 UI, 0,75 ml). **Não há migration de coluna** para nenhum dos dois épicos. O draft de líquidos supunha precisar de `ALTER ... numeric(10,2)` nas colunas de dose — **falso**; a fração já cabe. (Os `ALTER` de líquidos que sobram são de **estoque** — `current_volume_ml`, `drops_per_ml` — não de dose.)

### A convergência: uma parede, não duas
Diabetes e líquidos colidem na **mesma** parede — a **unidade de administração**:

| | Diabetes | Líquidos |
|---|----------|----------|
| Dose em | UI | ml / gotas |
| Estoque | volume da caneta (U-100) | volume do frasco |
| Decremento | UI → volume | ml fracionado FIFO |
| Display | "12 UI" | "2,5 ml (50 mg)" |

Ambos precisam do **mesmo trio**: (1) dose+estoque na unidade de administração; (2) decremento *unit-aware* (volume/fração, em paralelo ao pill-cêntrico); (3) `formatDoseUnit` respeitando a unidade real (hoje retorna genérico — ADR-046). FP-4 do ADR-050 já nomeou isso para diabetes; é **o mesmo trabalho** para líquidos.

### O que o refactor já entrega de graça (confirmado)
- Adesão por razão (`Σaplicado / Σesperado`) é **unit-agnóstica** desde que os dois lados usem a mesma unidade do medicamento (e usam). Fração já funciona no dado.
- Elo planejado↔aplicado (`dose_instance_id`, R-246), tolerância por instância (FP-2), timeline event-agnóstica (FP-3, Fase 4) → ambos os épicos plugam sem reescrever.

## Decisão

### 1. A parede de unidade é UMA fundação compartilhada
Não modelar "líquidos" e "diabetes" como dois caminhos de unidade independentes. O trio unit-aware (dose+estoque+display na `dosage_unit`) é **uma** camada que ambos consomem.

### 2. Líquidos ANTES de diabetes
Líquidos exercita a parede de unidade **sem** biomarcadores, validade biológica nem linha SaMD. É o caminho mais limpo para destravar o motor unit-aware. Diabetes **reusa** essa fundação e adiciona seu net-new (`biomarkers_log`, TTL `opened_at`, meal-scheduling). Atacar diabetes primeiro carregaria a parede de unidade junto com 4 complexidades clínicas de uma vez.

```
Refactor: F2.4 backfill → F3 (leitura, com seams abaixo) → F4 (timeline event-agnóstica)
   → Épico Líquidos (parede de unidade + FIFO fracionado de estoque)   ← destrava a unidade
      → Épico Diabetes (reusa unidade + biomarkers + TTL + meal-scheduling)
```

### 3. Três seams baratos na Fase 3 (camada de leitura) — para herdar agora
A Fase 3 (adesão/dashboard consomem `dose_instances`) DEVE nascer com:

- **Seam A — semântica de unidade explícita (contrato):** `expected_dose`/`quantity_taken` são "quantidade na `medicines.dosage_unit`", **nunca** comprimidos. Documentar como contrato; a matemática de leitura não pode cravar a suposição pill-cêntrica. (Reforça FP-4.)
- **Seam B — modo de adesão por protocolo:** não cravar `Σaplicado/Σesperado` (R-112 atual) como único modo. Bolus variável (e refeição pulada) quebra esse denominador. Prever **modo binário-de-evento** (tomou/não tomou) vs **exatidão-de-dose**, selecionável por protocolo. FP-1 já garante a base (não assume aplicado==esperado); falta o seletor. Seam barato agora, refactor-da-refactor se ignorado.
- **Seam C — cap Zod 100 é pill-specific:** o limite `quantity_taken ≤ 100` (R-022) tem semântica "100 comprimidos", inválida para UI/ml. Marcar para revisão por unidade quando a parede de unidade for atacada (não mexer na Fase 3; só não assumir que 100 é universal).

### 4. Sem migration de coluna no refactor
O DB já é `numeric`. Nenhum dos dois épicos exige `ALTER` nas colunas de dose. Os `ALTER` reais são de **estoque** (`stock.current_volume_ml`, `drops_per_ml`, `opened_at`, `shelf_life_days`) e **definição** (`is_liquid`/forma injetável) — todos no escopo dos épicos, não do refactor.

## Consequências

**Positivas:**
- Uma fundação de unidade serve dois universos de paciente (crônico cardíaco já atendido + líquidos + diabético).
- F3 nasce preparada sem custo relevante (3 seams = contrato + 1 seletor + 1 flag de revisão).
- Mata a suposição falsa de "migration de coluna" nos dois drafts.

**Negativas / aceitas:**
- F3 carrega disciplina extra (resistir a pill-centrismo, prever modo de adesão) — custo pequeno, pago na hora.
- Sequência impõe líquidos antes de diabetes; se houver pressão de produto por diabetes primeiro, reavaliar — mas o custo técnico de inverter é carregar a parede de unidade junto com a complexidade clínica.

## Fronteira conhecida (não resolver agora)
O gerador de `dose_instances` é **clock-based** (`time_schedule` cronológico). Bolus "antes do almoço" é **meal-anchored** — um modo de geração futuro do épico de diabetes, não coberto por nenhum FP. Documentado como limite do modelo atual.

## Alternativas consideradas
- **Diabetes antes de líquidos** — rejeitado: carrega a parede de unidade junto de biomarcadores/TTL/SaMD.
- **Migrar colunas de dose para `numeric(10,2)` no refactor** — desnecessário: já são `numeric`.
- **Deixar F3 cravar `Σaplicado/Σesperado`** — rejeitado: refactor-da-refactor garantido no bolus.
