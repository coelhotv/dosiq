# ADR-055 — Modelo de dado do "alarme crítico" por-tratamento

**Status:** accepted · **Date:** 2026-06-03 · **Spec:** 010-native-alarm-v2
**Pack:** data_and_schema · **Relaciona:** ADR-048 (dose_instances), ADR-050 FP-2 (config por protocolo), **ADR-057 (spec 011 — reminder passa a ler dose_instances; pré-req desta)**

## Contexto

O Alarme v2 (spec 010) precisa de uma flag opt-in "alerta crítico" **por-tratamento**
(não mais o toggle global por-device do v1). Dois consumidores distintos da flag:
1. **Mobile scheduler** (`useAlarmScheduler.syncAlarms`) — lê `dose_instances` (janela
   72h via `buildDoseItemsFromInstances`) p/ decidir **quais** ocorrências viram alarme.
2. **Server reminder** (`server/bot/_reminderHelpers.js`) — **pós-spec 011/ADR-057** lê
   `dose_instances` (ocorrências devidas), não mais `protocols`. Lê a coluna
   **materializada** `dose_instances.critical_alarm` para o gate per-dose (ADR-056).

> **Reconciliação (spec 011 é pré-req da 010):** quando o ADR-055 foi escrito, o reminder
> ainda lia `protocols` → cogitou-se ler a flag em `protocols`. A 011 move a fonte do reminder
> p/ `dose_instances`, então **ambos** os consumidores leem a coluna materializada
> `dose_instances.critical_alarm` (fonte única, congelada por ocorrência). `protocols.critical_alarm`
> permanece só como **intenção editável + origem da materialização**, nunca lida em runtime no gate.

Evidência (real repo):
- `protocols` recebe colunas via `ALTER TABLE ... ADD COLUMN` (ex.: `weekdays`,
  `start_date` — `docs/migrations/20260526_add_weekdays_to_protocols.sql`).
- `doseInstanceGenerator.js:183-186` materializa cada instância com
  `{protocol_id, scheduled_for, expected_dose, tolerance_minutes}`.
- `dose_instances` já tem `snoozed_until` ociosa (DOSE_INSTANCES.md:58).

## Decisão

Duas colunas booleanas, **mesma fonte de verdade** (a intenção do usuário no protocolo):

1. **`protocols.critical_alarm boolean NOT NULL DEFAULT false`** — a **intenção** editável
   pelo usuário e a **origem da materialização**. NÃO é lida em runtime no gate (pós-011).
2. **`dose_instances.critical_alarm boolean NOT NULL DEFAULT false`** — **materializada**
   da flag do protocolo na geração da ocorrência (como `expected_dose`/`tolerance_minutes`).
   Lida pelo mobile scheduler **e pelo server reminder** (pós-011). É o **eixo por-dose**,
   congelado por ocorrência — **fonte única do gate** crítico (server + mobile).

`critical_alarm` é **booleano puro** — canais/rota NUNCA moram aqui (são pref por-usuário,
computados live pelo dispatcher; ver ADR-056).

### Materialização e re-sync (FR-009)
- `doseInstanceGenerator` lê `protocol.critical_alarm` → grava em cada instância gerada.
- Editar a flag do protocolo → re-materializa as `dose_instances` **futuras** daquele
  protocolo (wipe+regenera o `pending` futuro, padrão `syncInstancesOnWrite`; nunca toca
  passado/`taken`/`missed` — invariante §11.3 DOSE_INSTANCES).

## Alternativas rejeitadas
- **Só em `protocols`** (sem materializar): o mobile scheduler leria a flag do protocolo
  junto com a instância — funciona, mas perde o congelamento por-ocorrência (filosofia
  ADR-048) e exige o protocolo carregado no scheduler. Rejeitado por consistência.
- **Enum de rota em `dose_instances`**: drift de prefs de canal em milhões de linhas.
  Rejeitado (operador confirmou: só o bit crítico).

## Consequências
- Migração de 2 colunas (default false → nenhuma dose vira crítica retroativa).
- `CON-024` (DoseItem de `buildDoseItemsFromInstances`) ganha `critical` (aditivo).
- Atenção AP-201 se alguma view consumir a coluna; AP-209 se materialização via RPC.
