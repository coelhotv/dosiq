# ADR-071 — Unified Dose Logging and Stock Orchestration in Core

## Contexto

Hoje, o registro de tomada de dose e o correspondente controle de estoque (FIFO) estão duplicados:
- No web, em `logService.js` (`create`, `update`, `delete`), orquestrando validações Zod, inserções em `medicine_logs`, débito via `stockService.decrease` (que usa o RPC no DB) e rollback compensatório em JS no caso de falha de estoque, além da âncora `anchorLogToInstance`.
- No mobile, em `doseService.js` (`registerDose`, `undoDose`, `updateOrphanLog`, `deleteOrphanLog`), orquestrando validações Zod, inserções no DB, chamadas diretas de RPC `consume_stock_fifo` e rollback compensatório também em JS.

Esta duplicação fere o princípio **"service-first, screen-second"** estabelecido no master plan e foi a causa raiz de descompassos de estoque e logs órfãos (classe de bugs **AP-231**). Como a Web e o Mobile agora utilizam o mesmo motor de estoque (RPC no Postgres), a orquestração de tomada/estorno de doses pode e deve ser centralizada.

## Decisão

Criar uma factory de serviço unificado no core: `createDoseLogService({ client, getUserId })` localizado em `@dosiq/core/services/doseLogService.js`.

Este serviço centralizará os seguintes métodos:
1. `registerDose(logData, { instanceId })`: valida inputs via `logSchema`, insere `medicine_log`, consome estoque atômico via `consume_stock_fifo`, e faz a âncora best-effort `anchorLogToInstance`. Faz rollback do log em caso de falha de estoque.
2. `undoDose(instanceId)`: localiza a instância, reverte estoque via `restore_stock_for_log`, remove o `medicine_log` e restaura a `dose_instance` para `pending` ou `missed` de acordo com a tolerância.
3. `updateOrphanLog(logId, updates)`: atualiza logs avulsos. Se o medicamento ou quantidade mudar, restaura o estoque antigo, aplica a atualização e consome o estoque novo, tratando falhas de reconsumo.
4. `deleteOrphanLog(logId)`: remove logs avulsos devolvendo estoque via `restore_stock_for_log`.

## Justificativa

- **DRY de Core Write-Path**: A lógica de escrita do fluxo principal é o caminho mais crítico do sistema. Centralizar a orquestração com 100% de cobertura de testes unitários no core garante estabilidade.
- **Acoplamento Limpo**: Platform adapters (`doseService` no mobile e `logService` no web) mantêm responsabilidades locais de plataforma (como detecção offline no React Native, triggers do Firebase Analytics, cancelamento de alarmes locais via Notifee, etc.) e apenas delegam as operações de dados ao core.
- **Redução do Blast Radius**: Evita que mudanças de regras de negócio (ex. novas formas farmacêuticas de titulação ou tolerância) precisem de portas manuais duplicadas.

## Consequências

- **Nova Factory Compartilhada**: Criação de `packages/core/src/services/doseLogService.js` (contrato **CON-026**).
- **Paridade de Testes**: Mover os cenários de teste de rollback e âncoras para a suíte do core.
- **Platform Refactor**: `logService` (web) e `doseService` (mobile) viram cascas finas sem lógica de escrita SQL/RPC de estoque direta.
