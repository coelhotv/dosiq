# ADR-086 — Política de uso de Critical Alerts (iOS)

**Status**: accepted
**Data**: 2026-07-21
**Spec**: 054-critical-alerts
**Categoria**: mobile_and_platform

## Contexto

A Apple aprovou a managed capability Critical Alerts para o dosiq. Critical alert fura silencioso/Focus/DND — poder auditável pela Apple: uso abusivo causa rejeição no review ou revogação do entitlement. A política de QUANDO uma notificação é crítica precisa ser uma decisão registrada, não um default de código.

## Decisão

1. **Escopo do critical**: SOMENTE o alarme LOCAL de dose com `dose_instances.critical_alarm = true` (fonte única — ADR-055/056), nos disparos **T0 e nag** (o nag herda a flag do alarme original via builder compartilhado). Nenhum outro emissor — digest, estoque, titulação, nudge, relatório, Live Activity, push remoto — emite a flag.
2. **Volume e som fixos**: `criticalVolume: 0.8`, som `alarm_dose.wav` (o custom sound de alarme já existente — mesma identidade sonora). Definidos em UM ponto (`alarmService`), nunca espalhados. Sem configuração de volume pelo usuário na v1.
3. **Flag derivada da autorização do SO**: `critical: true` NUNCA é incondicional — só é emitida quando a autorização criticalAlert está concedida (`getNotificationSettings().ios.criticalAlert`). Corolário: builds sem o entitlement no profile jamais emitem a flag (a autorização não é concedível sem entitlement) → imune à rejeição silenciosa do iOS.
4. **Autorização contextual** (R-239): prompt do SO pedido apenas em ponto de intenção (toggle `critical_alarm` no form de tratamento), precedido de sheet explicativo in-app. Negação → degradação para `timeSensitive` (comportamento atual), sem nag de re-prompt.
5. **Inventário fixado por teste**: teste de contrato (família R-297) varre os emissores da flag; caminho novo que emitir critical quebra o teste. É a materialização executável desta política.
6. **Push remoto crítico**: FORA. Slice 2 condicional da spec 054 (gate: v1 verde + prova R-296 do cenário em prod). Se aprovado, esta ADR se estende ao emissor server com a MESMA política.

## Alternativas rejeitadas

- **Critical em toda notificação de dose**: risco direto de revogação do entitlement; contradiz a semântica do `critical_alarm` (o usuário já expressa a criticidade por dose).
- **Toggle de usuário "usar critical alerts"**: superfície redundante — a intenção já é o `critical_alarm` + a autorização do SO (revogável em Ajustes).
- **Volume configurável**: superfície extra sem demanda comprovada; reavaliável pós-smoke.

## Consequências

- Compliance: política citável no review da Apple (escopo restrito, opt-in duplo: por-dose + autorização do SO).
- `interruptionLevel` permanece `timeSensitive` como piso; `critical` é promoção por-notificação condicionada à autorização.
- CON-031 ganha `detail.mode` aditivo no `alarm_scheduled` (crítico vs normal) para auditabilidade do modo efetivo.
- SQP deve descrever nos release notes texto explicativo da política para review da Apple em ingles (en-US).
