# ADR-090 — Drop `@react-native-firebase` → Sentry (crash) + PostHog (analytics de produto)

**Status:** accepted
**Data:** 2026-07-24
**Origem:** blocker T029 da spec 055 (PR 1.3) — `@react-native-firebase` não compila sob Xcode 26.3 / RN 0.81 com `useFrameworks: 'static'` ([[T029-debt-handoff]])
**Categoria:** mobile_and_platform
**Relaciona:** spec 055 (Expo SDK bump) · spec 051 (EAS Update) · [[ADR-088]] · [[R-083]] · [[R-295]]

## Contexto

O bump de SDK do 55 (RN 0.81+, Xcode 26.3) endureceu o toolchain iOS a ponto de
`@react-native-firebase/{app,analytics,crashlytics}` **não compilar** sob `useFrameworks: 'static'`
(default Expo): o clang recusa a declaração concorrente de `RCTBridgeModule`
(`must be imported from module 'RNFBApp.RNFBAppModule' before it is required`) + cascata
`-Wimplicit-int` fatal em `RCTExportMethod`. O flag `CLANG_ALLOW_NON_MODULAR_INCLUDES...`
(`withFirebasePodfileFix.js`, PR 1.1) mitiga o warning non-modular mas **não** o erro estrito de
resolução de módulo. Bug conhecido upstream sem fix nativo (invertase #8988/#8827, expo #39607);
`useFrameworks: 'dynamic'` resolve o firebase mas quebra o link de `react-native-netinfo` (pod da
comunidade não dynamic-safe) → troca de buraco.

**Fatos que destravam a decisão (medidos 2026-07-24):**
- Uso de firebase é **minúsculo e já abstraído**: `analytics` (eventos) + `crashlytics` (ErrorBoundary).
  Sem `messaging`/FCM (push é `expo-notifications` + notifee), sem `perf` (loading time é evento
  custom `cold_start`, não Firebase Performance), sem AdMob (ads descartados — sem escala).
- 4 pontos de uso: `firebaseAnalytics.ts` (wrapper), `AppRoot.tsx` (`analytics()` direto + `cold_start`),
  `ErrorBoundary.tsx` (crashlytics). Todos fail-silent por design.
- Firebase é native-frágil e **reexplode a cada bump de SDK** (voltaria na W2/SDK 55).
- `google-services.json`/`.plist` ficam necessários pro push Android (FCM transport via
  `expo-notifications`), **independente** do pacote RNFB — não se deletam.

## Decisão

**Remover `@react-native-firebase/{app,analytics,crashlytics}`** e substituir por dois provedores
native-leves (pods RN puros, sem `.xcframework` estático → compilam sob `static` sem o inferno de
header; não reexplodem no SDK 55):

1. **Crash reporting → `@sentry/react-native`.** Free tier (5k erros/mês; frota = 25 ativos → folga
   enorme). Crash nativo iOS+Android. `ErrorBoundary` passa a `Sentry.captureException`. Config plugin
   Sentry substitui os plugins firebase + `withFirebasePodfileFix.js`.
2. **Analytics de produto → `posthog-react-native`.** Free tier 1M eventos/mês, funil/retenção/A/B
   in-app/feature flags no mesmo tier. **Hosting: `us` (US-Virginia)** — decisão do PO 2026-07-24:
   apesar de a EU ser privacy-first (mais estrito que LGPD), o backbone Brasil↔US é bem maior que
   Brasil↔EU e o app é **brasil-only**; latência ganha do EU-Frankfurt neste momento (revisável se a
   base internacionalizar). Peer deps quase todas já
   presentes (async-storage, expo-application/device/file-system, react-navigation, safe-area-context);
   falta só `expo-localization`. **Session replay desligado** (come evento). O wrapper
   `firebaseAnalytics.ts` (renomeado `productAnalytics.ts`) mantém a **mesma API exportada**
   (`logEvent/setUserId/setUserProperty/logScreenView`) → blast mínimo; `cold_start` vira
   `posthog.capture('cold_start', { duration_ms })`.

Volta-se a `useFrameworks: 'static'` limpo (firebase fora → netinfo ok, sem dynamic, sem monkey-patch).

### Fronteira com a spec 051 (OTA) — NÃO negociável

PostHog toca a 051 em **um ponto só**: **métrica de adoção de frota** (`app_version` por evento →
alimenta o gate ADR-088 Era 1→2, hoje via `fleet-versions.sh`). **Proibido:**
- feature flag do PostHog como gating de conteúdo OTA — 051 [governance §125](../../../../plans/specs/051-expo-updates/spec.md)
  proíbe "feature-flag-para-ligar-depois" (app de saúde/Play: código OTA tem de estar ativo/revisável);
- PostHog no caminho do kill switch (`min_app_version`) — é boot-blocking + fail-open (AP-303); a 051
  já decidiu Supabase + padrão dos nudges (026). Não adicionar dependência remota nova a esse path.

## Opções consideradas

- **A — `patch-package` nos headers do firebase (static):** desbloqueia rápido, blast native mínimo.
  Rejeitada como permanente: re-patch a cada bump de firebase/SDK, não estrutural.
- **B — `useFrameworks: 'dynamic'` + drop netinfo:** provado resolver firebase, mas notifee/apple-targets
  sob dynamic são **desconhecidos** — troca um buraco native por outro maior. Rejeitada (risco).
- **C — drop firebase → Sentry + PostHog (ESCOLHIDA):** maior diff de código (3 arquivos, já isolados),
  mas mata o blocker **permanentemente** e dá analytics de produto melhor que o Firebase Analytics
  básico de hoje. Decisão do PO 2026-07-24, ads descartados removem o único valor único do ecossistema
  Google (atribuição paga).

## Consequências

- **iOS volta a buildar** (gate `npx expo run:ios` verde — o que o T029 não fechava). Executa como
  **PR 1.3b** dentro da W1 (caminho crítico: sem isto nenhum build iOS sai → v0.29.0 não fecha).
- Perde-se console Firebase (histórico de crash/analytics) — frota 25 ativos, perda baixa; A/B de loja
  (aquisição) fica em App Store Connect PPO + Play Console (nativo, provider-agnóstico); atribuição paga
  adiada (sem mídia hoje; MMP free quando precisar).
- Novos env (R-083): `SENTRY_DSN`, `POSTHOG_API_KEY`, host US `https://us.i.posthog.com`
  (US-Virginia — ver §Decisão; app brasil-only, backbone bra/us > bra/eu).
- SQP: minor/behavioral — `APP_VERSION` já 0.29.0 (bump do PR 1.1), **não** re-bumpar; CHANGELOG PT.
- Reduz superfície native frágil: um blocker a menos na W2 (SDK 55) e no futuro.
