# ADR-091 — Superfície de config remota do kill switch de versão mínima

**Status:** accepted
**Data:** 2026-07-25
**Spec:** 051 (fatia **051-A**, executa na Onda 1 da 055 · release v0.29.0)
**Relacionados:** ADR-088 (schema é API pública) · ADR-082/083 (OTA) · ADR-089 (frota) · ADR-090 (Sentry/PostHog)
**Anti-patterns em jogo:** AP-303 (indeterminado ≠ negação) · AP-314 (DDL destrutiva quebra binário instalado) · AP-278 (grant tolerado por acidente) · AP-216 (destructuring do Supabase Auth)
**Regras em jogo:** R-042 · R-090/R-091 · R-270 · R-271 · R-287 · R-289 · R-295

---

## Contexto

O ADR-088 consolidou o kill switch de versão mínima **nesta spec**, mas o FR-018 nunca foi projetado:
dizia apenas *"config remota"*, sem nomear tabela, coluna, grant, endpoint ou tela. Mandava reusar
*"o padrão `min_app_version` dos nudges (026)"* — que é uma **coluna de conteúdo** em `in_app_nudges`
(*este nudge aparece para quais versões?*), não uma config global de bloqueio.

Medido no banco de produção em 2026-07-25 (não assumido):

| Verificação | Resultado |
|---|---|
| Tabela de config/flags já existente | **nenhuma** — só `in_app_nudges` (por conteúdo) e `user_settings` (por usuário) |
| Grants em **toda** tabela do projeto | `SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER` p/ **`anon` E `authenticated`** (herança de `ALTER DEFAULT PRIVILEGES` no schema `public`) |
| O que impede escrita hoje | **apenas** a ausência de policy de escrita sob RLS — camada única |
| Policy de SELECT de `in_app_nudges` | restrita ao role `authenticated` |
| Leitura remota no boot do mobile | **nenhuma** existe hoje |

Ou seja: a superfície teria de ser inventada dentro de uma sessão de código — e é a parte perigosa,
porque **quem escreve `min_supported_version` pode inutilizar a base instalada inteira**. Escrever isso
sem decisão registrada é exatamente o cenário que o aviso RC-SEC da 051 marca como *"quem escreve
brica a base"*.

A RC-SEC-2 (2026-07-25) auditou o desenho proposto e emitiu **8 findings** (2 CRITICAL, 2 HIGH,
3 MEDIUM, 1 LOW fora de escopo). As decisões abaixo incorporam todos.

### O achado técnico que sozinho justifica o ADR

`satisfiesSemver` ([`packages/core/src/utils/semver.ts:45`](../../../../packages/core/src/utils/semver.ts))
é **fail-closed por design** — versão inválida ⇒ `false` — porque nasceu para *filtrar nudges*, onde
esconder é o comportamento seguro. No boot, o seguro é o **oposto**. Reusá-la "porque a spec manda
reusar o comparador existente" **inverte a semântica**: uma config corrompida bloquearia a base inteira.
`compareSemver` ([`semver.ts:26`](../../../../packages/core/src/utils/semver.ts)) devolve `null` para
entrada inválida — e esse `null` é exatamente o "indeterminado" que o AP-303 manda deixar passar.

## Decisão

### D1 — Tabela dedicada `public.app_version_gate` (uma linha por plataforma)

| Coluna | Tipo | Nota |
|---|---|---|
| `platform` | `text` PK | CHECK `('ios','android')` sincronizado com o enum do core (R-271) |
| `min_supported_version` | `text` nullable | formato `X.Y.Z` (regex reusada de `nudgeSchema.ts:72`) |
| `is_active` | `boolean NOT NULL DEFAULT false` | **nasce desligado** |
| `message` | `text` nullable | copy opcional; `null` ⇒ default compilado |
| `store_url` | `text` nullable | sob allowlist no cliente (D6) |
| `updated_at` | `timestamptz NOT NULL DEFAULT now()` | auditoria |
| `updated_by` | `uuid` | FK→`auth.users(id)` `ON DELETE SET NULL` (R-287 — trilha sobrevive ao titular) |

**Rejeitado:** estender `in_app_nudges`. Semânticas diferentes (conteúdo opcional por usuário × bloqueio
global de boot), políticas de acesso diferentes (nudges lê só `authenticated`; o gate precisa de `anon`)
e ciclos de vida diferentes. Misturar produziria o mesmo tipo de sobrecarga conceitual que o ADR-089
rejeitou ao não estender `notification_devices`.

### D2 — A decisão é **pura**, mora em `@dosiq/core`, e a UI **obedece**

Um resolver único e testável recebe *(versão instalada, linha do gate)* e devolve a decisão. A UI não
reintroduz lógica própria. É o antídoto direto do AP-303, cuja falha foi literalmente *"guard de UI que
contradiz a decisão pura que consome"*.

**Tabela-verdade — normativa, escrita como teste (uma asserção por linha), não como prosa:**

| Condição | Decisão |
|---|---|
| erro de rede / timeout / offline | **ABRE** |
| `error` não-nulo do PostgREST (`42703`, `42501`, RLS…) | **ABRE** |
| linha ausente para a plataforma | **ABRE** |
| `is_active = false` | **ABRE** |
| `compareSemver(instalada, min) === null` (qualquer lado inválido) | **ABRE** |
| `compareSemver(instalada, min) === -1` | **BLOQUEIA** |
| qualquer outro caso | **ABRE** |

### D3 — `compareSemver` obrigatório; **`satisfiesSemver` PROIBIDA neste caminho**

Comparador novo continua proibido (a spec já vedava). Mas o reuso correto é `compareSemver`, pelo
motivo do §Contexto. **Também proibido** o fallback hardcoded `'0.15.0'` de
[`useNudges.ts:11`](../../../../apps/mobile/src/features/profile/hooks/useNudges.ts): um default
desatualizado converte indeterminação em bloqueio falso. Versão instalada ilegível ⇒ **abre**.

### D4 — Fail-open explícito, sem cache do estado de bloqueio

O app renderiza normalmente e a checagem corre **em paralelo**; nada de splash bloqueante esperando
rede (isso regrediria o boot e recriaria o AP-303). **Cachear o estado de bloqueio é PROIBIDO** —
cachear um gate ativo bloquearia o usuário offline para sempre, sem meio de recuperação. Sem rede ⇒ abre.

`supabase-js` **não lança** em erro de query: retorna `{ data: null, error }`. O serviço de leitura
DEVE inspecionar `error` explicitamente — o `useNudges` atual não inspeciona e por isso sobrescreve o
cache bom com `[]` em silêncio ([`useNudges.ts:74-86`](../../../../apps/mobile/src/features/profile/hooks/useNudges.ts)).
Não repetir o padrão.

### D5 — Escrita: **duas camadas independentes** (AP-278)

Nenhuma pode ser a única:

1. `REVOKE INSERT, UPDATE, DELETE, TRUNCATE ON public.app_version_gate FROM anon, authenticated;`
   explícito na migração. ⚠️ Neste projeto `REVOKE ... FROM PUBLIC` sozinho **não** basta — os
   privilégios vêm de `ALTER DEFAULT PRIVILEGES` nomeando os roles.
2. RLS **ON**, **uma** policy de `SELECT` para **`anon` E `authenticated`** com `USING (true)`, e
   **zero** policies de escrita.

⚠️ **Não copiar a policy dos nudges** (restrita a `authenticated`): o bloqueio ocorre antes de haver
sessão, logo `anon` precisa ler — senão o gate fica mudo exatamente para quem abre o app pela primeira
vez após o servidor mudar.

Escrita exclusivamente pelo caminho admin (`service_role`, que ignora RLS), atrás de autenticação de
admin (R-042). Sem função serverless nova: handler no router `api/admin.ts` já existente (R-090),
helper em diretório `_`-prefixado (R-091).

**Column-level (S-10):** `REVOKE SELECT (updated_by, updated_at) FROM anon, authenticated` — o cliente
precisa de 5 colunas; entregar o uuid interno do admin a `anon` é exposição gratuita. Restringir no
`select()` do app é higiene, não controle; o revoke é a camada real.

### D6 — Todo conteúdo remoto do gate é **não-confiável**, mesmo vindo do nosso banco

- **`store_url` sob allowlist no cliente** (S-8): apenas `https://apps.apple.com/…` e
  `https://play.google.com/…`; qualquer outro valor é tratado como ausente e o botão cai para constante
  compilada. Validar também no Zod da escrita (defesa em profundidade). Razão: config remota →
  `Linking.openURL` é fronteira de confiança, numa tela full-screen onde o botão é a **única** ação e o
  usuário está condicionado a clicar para recuperar acesso ao próprio remédio.
- **`message` como `<Text>` puro** (S-9), com cap de tamanho, sem markdown/HTML/link tocável. Razão:
  texto arbitrário não-dismissível em app de saúde para toda a base é engenharia social com a
  credibilidade da marca.

### D7 — Saída honesta compilada para o dosiq web

O overlay SEMPRE exibe, abaixo do botão da loja, texto + link para **`https://dosiq.app`**.

🔴🔴 **A URL é CONSTANTE COMPILADA — nunca vem da linha do gate.** Duas razões, ambas de segurança:
(a) puxá-la da config remota criaria um **segundo** vetor do S-8; (b) a saída de emergência não pode
ser removível pela mesma configuração que aplica o bloqueio — mesmo princípio do D9.

Isto muda a **postura de compliance**: o bloqueio deixa de ser *"você perdeu acesso ao seu histórico de
medicação"* (tensão com LGPD art. 18 e Constituição §I/§IX — a mesma que o AP-303 nomeou) e passa a ser
*"este binário não fala com o servidor com segurança; a porta que sempre funciona é esta"*. Funciona
porque **a web não tem o problema que causa o bloqueio**: deploya por Vercel e está sempre corrente,
enquanto binário instalado fica parado (AP-314).

### D8 — Guarda de raio de impacto **server-side** (S-7)

O fail-open protege contra falha de **leitura**; não protege contra escrita **errada** — um typo em
`min_supported_version` bricka a base. A guarda roda **no handler**, não na UI: o endpoint computa a
frota afetada (mesma união `notification_devices ∪ device_activity` do
[`scripts/fleet-versions.sh`](../../../../scripts/fleet-versions.sh)) e **recusa** ativação sem
`acknowledge_affected_devices: <contagem exata>` batendo com a sua própria contagem. A UI apenas exibe.

**Desativar (`is_active = false`) NÃO exige acknowledge** — desbloquear tem de ser barato e imediato.

### D9 — Invariante: o kill switch nunca gateia a superfície usada para desativá-lo (S-11)

Hoje o gate é mobile-only e o painel é web ⇒ desligar não depende do que quebrou. Isso é **sorte de
desenho**; passa a ser invariante escrito. Se o web um dia entrar no escopo do gate (NC6), o painel
admin fica fora **por construção**.

### D10 — Identidade de admin deriva do **uid autenticado**, não do `telegram_chat_id` (S-6)

`ADMIN_CHAT_ID` é substituído por **`ADMIN_USER_ID`** (o `auth.users.id` do admin) e
[`verifyAdminAccess`](../../../../server/utils/auth.ts) compara direto com o `user.id` devolvido por
`supabase.auth.getUser()`, **eliminando a consulta a `user_settings`**.

**Por que era Critical agora e não antes:** admin era *"a linha de `user_settings` do usuário tem
`telegram_chat_id == ADMIN_CHAT_ID`"*. Medido: a policy de UPDATE de `user_settings` não restringe
coluna, `authenticated` tem o privilégio **na coluna**, e não há UNIQUE que torne a colisão visível ⇒
qualquer uma das 48 contas podia se auto-promover. O furo é pré-existente e protegia DLQ/feedbacks/
nudges — ruim, mas contido. O FR-021 põe **"bloquear o boot de toda a base de um app de medicação"**
atrás desse mesmo controle. RC-SEC não aprova um controle porque ele já existia; avalia se é adequado
**ao que passará a proteger**.

Verificado em 2026-07-25: `auth.users` tem **zero grants** para `anon`, `authenticated` e
`service_role` — a tabela não é alcançável por PostgREST nesses papéis, e o `id` é a PK atribuída pelo
GoTrue no signup. Não há superfície para o usuário alterar o próprio `uid`.

**Guards que fazem parte do controle (não são extras):**
- Continuar usando `getUser()`, que valida o token contra o servidor de auth. **Nunca** decode local
  de JWT sem verificação de assinatura — derrubaria o controle inteiro e é o tipo de "otimização" que
  passa despercebida num review futuro.
- **Env ausente ⇒ negar.** Nada de `if (adminUserId && ...)`. Fail-closed explícito, inclusive na
  checagem de configuração no topo de `api/admin.ts`.
- **AP-216 na mesma passagem:** o código atual faz `const { data: { user }, error } = await
  supabase.auth.getUser()` — destrutura `data` antes de checar null.
- 401/403 uniforme para fora (S-12); o detalhe fica no log.

**Blast radius contido:** `verifyAdminAccess` tem **um único call site**
([`api/admin.ts:157`](../../../../api/admin.ts)). O bot do Telegram não usa a função; `ADMIN_CHAT_ID`
segue existindo para o que sempre foi (mensageria).

## Alternativas rejeitadas

| Alternativa | Por que rejeitada |
|---|---|
| Reusar `in_app_nudges.min_app_version` | é filtro de conteúdo por usuário, não config global; policy restrita a `authenticated` deixaria o gate mudo sem sessão |
| `satisfiesSemver` como comparador | **fail-closed** — inverteria a semântica no boot; config corrompida viraria bloqueio universal |
| Feature flag do PostHog como gate | acrescenta dependência remota nova ao caminho boot-blocking (recria AP-303) e transfere autoridade a vendor externo; ADR-090 já traça a fronteira |
| Cachear a decisão de bloqueio | bricka o usuário offline permanentemente — oposto do fail-open |
| `REVOKE UPDATE (telegram_chat_id)` (recomendação original do S-6) | fecha o vetor mas **mantém** superfície escrita pelo usuário no caminho de autorização e a sobrecarga conceitual; entropia de ~10 dígitos chutáveis vs uuid de 122 bits; mantém round-trip ao banco. Ver tabela comparativa na RC-SEC-2 |
| Guarda de raio de impacto só na UI | a API é a fronteira, não a tela; `PATCH` direto pularia contagem e confirmação. Controle que só existe na UI é sugestão |
| `store_url` aberta sem allowlist | config remota → `Linking.openURL` numa tela onde clicar é a única saída = contexto ideal de phishing |
| Link do web vindo da linha do gate | 2º vetor do S-8 + saída de emergência removível pela config que aplica o bloqueio |
| Splash bloqueante esperando a leitura do gate | regride o boot e o offline-first (AP-303) |

## Consequências

**Positivas**
- O ADR-088 ganha o mecanismo que encerra a Era 1 (*"nenhum DROP, sem exceção"*): passa a existir
  política de versão mínima acionável.
- Fecha o vetor de auto-promoção a admin (S-6) — pré-existente, hoje protegendo DLQ/feedbacks/nudges.
- O bloqueio passa a **redirecionar** em vez de negar acesso a dado de saúde (D7).
- A decisão pura é testável sem device: a tabela-verdade vira suíte unitária.

**Negativas / custos aceitos**
- Uma tabela e uma migração a mais; `npm run supabase:types` no MESMO PR (R-289).
- O gate é **mais uma** leitura remota no boot — mitigada por ser paralela, sem cache e fail-open.
- Admin continua **um** por env var. Quando deixar de ser uma pessoa só, migrar para tabela
  `admin_users` gravável só por `service_role`. É questão de **escala**, não vetor aberto.
- O kill switch **não alcança** binário que não o embute — como OTA. Os 21 installs abaixo de 0.28
  medidos no ADR-088 seguem inalcançáveis; o relógio da adoção só começa quando o v0.29.0 sai.

**Dívidas registradas (não bloqueiam)**
- S-13: policies `Pilot_*` em `user_settings` dão a `PUBLIC`/`anon` escrita numa linha de `user_id`
  fixo. Não escala para admin (não há `auth.users` correspondente ⇒ não se obtém JWT), mas é escrita
  anônima em tabela de settings. Item próprio.
- NC6: cobertura **web** do gate assumida fora de escopo (051-A é mobile-only por construção). Se
  entrar, é um valor a mais no CHECK e um consumidor a mais — mas D9 passa a ser exigência ativa.
