# ADR-089 — Tabela dedicada `device_activity` para heartbeat independente de push

## Status
Accepted

## Contexto

`notification_devices` (ADR-027) foi desenhada pra tokens de push — `push_token`/`provider` são a razão de existir da tabela, e a UNIQUE de conflito (`upsert_notification_device`, `docs/migrations/20260427_upsert_notification_device_rpc.sql`) é `(provider, push_token)`. Push é pedido de forma contextual (R-239 — nunca no 1º load), então quem usa o app sem aceitar notificações nunca gera row ali.

Consequência medida (spec 057, 2026-07-22): segmentação de campanha e o gate de frota do ADR-088/051-FR-020 (`scripts/fleet-versions.sh`) tratam essa fonte como piso, não retrato — a frota real de app_version pode ser maior que a medida.

**Opção A (rejeitada) — estender `notification_devices`:** tornar `push_token`/`provider` opcionais, permitir insert sem eles. Reaproveita infraestrutura existente (RLS, índices), mas mistura duas semânticas na mesma tabela ("device com canal de push configurado" vs "device só visto rodando o app") e quebra a UNIQUE de conflito atual (que depende de `push_token` não-nulo) — exigiria chave de conflito alternativa convivendo com a antiga.

**Opção B (aprovada) — tabela nova dedicada `device_activity`:** heartbeat mínimo, sem nenhuma coluna de push. Zero risco de regressão em `notification_devices`/`upsert_notification_device` (código de push maduro, usado em produção). Custo: mais uma fonte pra `fleet-versions.sh` cruzar (já previsto como union, FR-005 da spec 057).

## Decisão

**Criar tabela `device_activity`:**

```sql
create table device_activity (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade, -- R-287
  device_fingerprint text not null,  -- mesma estratégia da 043 (os/osVersion/deviceModel, sem appVersion na chave — AP-208)
  platform text not null check (platform in ('ios', 'android')),
  app_version text not null,
  last_seen_at timestamptz not null default now(),
  created_at timestamptz not null default now(),
  unique (user_id, device_fingerprint)
);

create index idx_device_activity_user_id on device_activity (user_id);
create index idx_device_activity_last_seen on device_activity (last_seen_at);
```

RLS: `user_id = auth.uid()` para INSERT/UPDATE do próprio usuário, OU RPC `SECURITY DEFINER` (`upsert_device_activity`) espelhando `upsert_notification_device` — decisão de mecanismo (RLS direta vs RPC) fica para o plan.md, ambas cobertas pelo template `docs/standards/SUPABASE_MIGRATIONS.md`. Zero grant a `anon`.

**Relacionado:** `notification_devices` continua intocada — nenhuma migração nela, nenhuma mudança de contrato (CON-NNN existente, se houver, não muda).

## Consequências

**Positivas:**
- Zero risco de regressão em push (tabela/RPC/UNIQUE de `notification_devices` intactos)
- Semântica limpa: uma tabela = um conceito ("visto rodando", sem carga de push)
- `fleet-versions.sh` soma fonte por union, nunca duplica/substitui

**Negativas:**
- Mais uma tabela pra manter (migração, RLS, RPC, grants — mesmo template já usado 5x no projeto)
- Duas fontes de "device" (`notification_devices` + `device_activity`) exigem dedupe/union explícito em toda query de fleet — se esquecido, sub-conta a frota real (espelho do próprio problema que esta spec resolve)

**Fora de escopo:**
- Migrar/consolidar `notification_devices` e `device_activity` numa fonte única (poderia ser revisitado se o custo de manter duas tabelas separadas crescer)
- Analytics de produto completo (funis, eventos de UI) — heartbeat é só device+versão+timestamp

## Gatilho para Mudança

Se `notification_devices` algum dia parar de exigir push_token (ex.: virar canal opcional desde o início), revisitar se as duas tabelas deveriam consolidar.
