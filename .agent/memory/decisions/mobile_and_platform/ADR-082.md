# ADR-082 — Versionamento de releases OTA (EAS Update) sob política `runtimeVersion: appVersion`

**Status:** accepted (PO 2026-07-19)
**Spec:** 051-expo-updates (FR-012, NC3-versionamento)
**Tags:** mobile, eas-update, ota, versioning, release

## Contexto

A 051 adota EAS Update com `runtimeVersion: { policy: "appVersion" }` (ADR da NC1). Nessa política, o runtimeVersion É o `APP_VERSION` (`app.config.js`). Consequência mecânica: **qualquer bump de `APP_VERSION` cria um runtime novo** — updates OTA publicados só alcançam builds instalados do MESMO runtime. Um patch entregue por OTA que bumpasse a versão nunca chegaria a nenhum build instalado (todos ainda rodam a versão anterior): o update nasceria órfão.

Isso conflita com a convenção mobile vigente (`feedback_mobile_version_convention`: épico = minor, fase = patch), que assume que todo release incrementa `APP_VERSION`.

## Decisão

1. **Release OTA NÃO bumpa `APP_VERSION`.** O runtimeVersion do update deve ser o mesmo dos builds instalados que devem recebê-lo.
2. **Identidade do release OTA no CHANGELOG/SQP:** entrada `[X.Y.Z+ota.N]` onde `X.Y.Z` = `APP_VERSION` corrente (runtime alvo) e `N` = sequencial do OTA sobre esse runtime (1, 2, …). A entrada registra o `updateId` do EAS e o SHA da main publicado (FR-015).
3. **Bump de versão só em build de loja.** O próximo `eas build`+submit **absorve** os OTAs acumulados: o CHANGELOG da nova versão de loja incorpora as entradas `+ota.N` anteriores (referência, não duplicação), e o ciclo `ota.N` reinicia no runtime novo.
4. **Convenção mobile ajustada:** "fase = patch" continua valendo para releases DE LOJA. Correção/ajuste JS-only entregue por OTA usa `+ota.N` e não consome patch. Se a mesma correção depois justificar build de loja, aí sim entra no bump normal.

## Consequências

- Suporte identifica o código pelo par versão+updateId (tela de configurações — FR-016/PO-6), não só pela versão.
- SQP de um release OTA: plataforma mobile, impacto normalmente patch-like mas **sem bump de fonte de versão**; CHANGELOG obrigatório com `[X.Y.Z+ota.N]`.
- Frota fragmentada (FR-017): fix crítico pode exigir publicar `+ota.N` em mais de um runtime ativo; cada runtime tem seu próprio contador.
- Risco aceito: `APP_VERSION` deixa de identificar unicamente o bundle JS; mitigado por updateId visível + tag de observabilidade (FR-011/FR-016).

## Alternativas rejeitadas

- **Bumpar patch a cada OTA:** órfã o update (mecânica da política appVersion). Inviável.
- **Política `fingerprint`:** experimental, descartada na NC1.
- **runtimeVersion manual fixo desacoplado da versão:** perde a trava automática "tocou nativo ⇒ runtime novo via bump", aumenta risco de entregar JS incompatível.
