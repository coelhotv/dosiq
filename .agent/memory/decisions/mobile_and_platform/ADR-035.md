## Contexto

Wave N1 entregou agrupamento por treatment_plan e bulk register mobile. O sistema ainda usava um único campo `notification_preference` (enum legado) e não oferecia controle ao usuário sobre quando e onde ser notificado.

Problemas identificados:
- Sem quiet hours: usuários recebiam push às 23:00 ou durante reuniões
- Sem digest mode: usuários com 8+ protocolos recebiam N pushes simultâneos mesmo com planos agrupados
- Experiência nativa fragmentada: 3 cards separados no Perfil (Preferências, Central, Telegram) sem hierarquia clara
- `resolveChannelsForUser` dependia de enum legado, sem suporte a Web (PWA)

## Decisão

### 1. Campos novos em `user_settings` (migration 20260427)

```sql
quiet_hours_start TIME, quiet_hours_end TIME
notification_mode TEXT CHECK IN ('realtime', 'digest_morning', 'silent') DEFAULT 'realtime'
digest_time TIME DEFAULT '07:00'
channel_mobile_push_enabled BOOLEAN NOT NULL DEFAULT true
channel_web_push_enabled    BOOLEAN NOT NULL DEFAULT false
channel_telegram_enabled    BOOLEAN NOT NULL DEFAULT false
```

`notification_preference` mantido como campo legado de backcompat — não removido nesta wave.

### 2. `notificationGate.js` — supressão de notificações realtime

Função `shouldSendNow({ mode, quietHoursStart, quietHoursEnd, currentHHMM })`:
- `silent` → sempre false
- `digest_morning` → false (suprime realtime; digest cuida do resumo)
- `realtime` + within quiet hours → false
- `realtime` + outside quiet hours → true

`isInQuietHours` trata janela cross-midnight: se `start > end`, a janela passa pela meia-noite.

### 3. `resolveChannelsForUser` — flags explícitas com fallback legado

Quando `channel_*_enabled` estão presentes em `user_settings`, são a fonte de verdade:
- `channel_web_push_enabled === true` + device webpush ativo → retorna `'web_push'`
- `channel_mobile_push_enabled === true` + device expo ativo → retorna `'mobile_push'`
- `channel_telegram_enabled === true` + telegram_chat_id → retorna `'telegram'`

Quando flags ausentes → fallback para `notification_preference` legado.

### 4. Arquitetura nativa — hierarquia de 4 níveis

```
Perfil (hub de conta)
  └── Notificações (único ponto de entrada — badge de não lidas)
       ├── Avisos (Inbox) — filtros + zero state + gear → Preferências
       └── Preferências — canais + modo + quiet hours + digest time
            └── Conectar ao Telegram (subfluxo dedicado)
```

Eliminar os 3 cards paralelos no Perfil (Preferências, Central, Telegram) — consolidar em 1 entrada.

### 5. Digest matinal

`runDailyDigest` filtra por `notification_mode === 'digest_morning'` e `currentHHMM === user.digest_time`. Formato simples: title com contagem + body com lista de horários/nomes. Formatter enriquecido em N3.

## Consequências

- Usuários com `notification_preference = 'both'` continuam recebendo em ambos os canais (backfill automático na migration)
- Web (PWA) nunca é inferido — exige `channel_web_push_enabled = true` E device ativo com `provider = 'webpush'`
- App mobile não tenta criar subscription PWA — apenas exibe status informativo
- digest_morning suprime todos os lembretes realtime do dia; o digest é o único envio externo
