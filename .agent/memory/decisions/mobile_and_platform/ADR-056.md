# ADR-056 — Roteamento per-dose do alarme crítico vs push normal

**Status:** accepted · **Date:** 2026-06-03 · **Spec:** 010-native-alarm-v2
**Pack:** mobile_and_platform / notifications · **Relaciona:** ADR-055, **ADR-057 (spec 011 — PRÉ-REQUISITO: reminder lê dose_instances)**, R-200/R-220 (3-layer),
R-258 (gate v1 per-device), R-191/AP-112 (1 push/bloco)

> **⚠️ Re-escopo (2026-06-03):** este ADR foi reescrito após a spec 011 (ADR-057) virar
> pré-requisito. A versão original aplicava o split no reminder lendo `protocols.critical_alarm`
> (hack de duas fontes, porque o reminder lia `protocols`). Com a 011, o reminder lê
> `dose_instances` → o split lê `dose_instances.critical_alarm` **direto** (fonte única). C3 da
> 010 só inicia **após a 011 mergeada**.

## Contexto

v1: toggle global por-device (`native_alarm_enabled`) → alarme em TODA dose + gate suprime
push de TODA dose daquele device (R-258, em `expoPushChannel`, filtro por `kind` dose).

v2 (spec 010): crítico é **por-tratamento**. Precisa: dose crítica → alarme + **sem** push;
dose não-crítica → push normal. Sem dupla notificação (US2/SC-002).

Evidência (real repo):
- **Pós-011 (ADR-057):** o reminder lê `dose_instances` (ocorrências devidas) e **agrupa** via
  `partitionDoses` → kinds `dose_reminder` (individual), `dose_reminder_by_plan`,
  `dose_reminder_misc`. Cada dose do bloco carrega `instanceId` + `critical_alarm`. Um bloco
  pode **misturar** doses críticas e não-críticas (mesmo plano/minuto).
- O gate v1 vive no `expoPushChannel` (per-device, por `kind`).
- O mobile scheduler (`useAlarmScheduler.js:52-53`) lê `dose_instances`, filtra
  `status==='pending'` → agenda alarme.

## Decisão

Gate **em duas etapas**, granularidade **per-dose**:

1. **Partition-time (server reminder):** ao montar os blocos, **separar as doses críticas
   das não-críticas** usando `dose_instances.critical_alarm` (materializado, já lido pelo
   reminder pós-011). As doses críticas **não entram** nos blocos de push normal (o alarme do
   device as cobre). As não-críticas seguem o agrupamento atual (R-191 intacto). Isso resolve o
   bloco-misto: nunca se suprime um bloco inteiro nem se dobra uma crítica.

2. **Device-capability (expoPushChannel):** o `native_alarm_enabled` (v1) é **reaproveitado**
   como sinal de **capacidade de alarme do device** (device tem alarme armado + permissão).
   Para uma dose crítica, o canal só **suprime** o push de devices **com** a capacidade; um
   device sem capacidade (sem permissão/sem app) **recebe** o push crítico (fallback — não
   deixar o usuário sem nenhuma notificação). Toggle global de UX **aposentado** (FR-004);
   o flag persiste como capacidade, não como preferência.

3. **Mobile scheduler:** filtra `dose_instances.critical_alarm === true` (além de
   `status==='pending'`) — agenda alarme **só** das críticas (ADR-055).

### Fonte única `dose_instances.critical_alarm` (server + mobile)
Pós-011, **tanto** o server reminder **quanto** o mobile scheduler leem `dose_instances` →
ambos usam a coluna materializada `dose_instances.critical_alarm`. Fonte única, congelada por
ocorrência, derivada da intenção `protocols.critical_alarm` (ADR-055). Sem hack de duas fontes.

## Alternativas rejeitadas
- **Gate só no expoPushChannel por dose** (sem partition split): bloco misto força suprimir
  tudo ou nada → perde não-crítica ou dobra crítica. Rejeitado.
- **Split lendo `protocols.critical_alarm` no reminder** (versão original deste ADR, pré-011):
  hack de duas fontes (server lia protocols, mobile lia dose_instances). **Substituído** pela
  spec 011 (ADR-057) que move o reminder p/ `dose_instances` → fonte única. A 011 é o pré-req
  que tornou esta opção desnecessária.

## Consequências
- `partitionDoses` ganha consciência de criticidade (split). Possível novo kind ou flag no
  bloco → atualizar enum Zod do dispatcher se novo kind (R-193/AP-115).
- `expoPushChannel`: o filtro deixa de ser "todo dose-kind" e passa a per-dose-criticality +
  device-capability. Mudança de payload/rota → este ADR cobre (constitution V).
- Gate server-side só vale **pós-deploy** (AP-206). Validar por unit test.
- `native_alarm_enabled` ressemantizado (capacidade, não toggle) — documentar a transição.
- **Dependência de sequenciamento:** C3 da 010 só inicia após a **011 mergeada** (o reminder
  precisa já ler `dose_instances` p/ o split ter a coluna `critical_alarm` na fonte).
