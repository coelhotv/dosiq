# ADR-083 — Segurança do canal OTA: code signing habilitado + publish manual PO-only

**Status:** accepted (PO 2026-07-19)
**Spec:** 051-expo-updates (NC2, RC-SEC S1/S2)
**Tags:** mobile, eas-update, ota, security, code-signing

## Contexto

EAS Update cria um canal de distribuição de código executável para devices de um app de saúde. RC-SEC (2026-07-19) identificou: S1 (Critical) — conta Expo comprometida = bundle malicioso para 100% da base sem loja; S2 (High) — sem code signing, o cliente aceita qualquer bundle que a infra da Expo entregue.

Contexto operacional: builds locais no Mac Mini (`eas build --local`), submissão TestFlight local. `eas update` não usa build queue (só upload) — filas do plano gratuito são irrelevantes para OTA.

## Decisão

1. **Code signing do expo-updates habilitado NESTE slice (051).** `npx expo-updates codesigning:generate` no Mac Mini; certificado embutido no build via `app.config.js` (`updates.codeSigningCertificate`); todo `eas update` assina com a chave privada local; cliente rejeita bundle não assinado (PO-SEC-1).
2. **Chave privada fora do repo** (gitignore) + backup seguro documentado no runbook. Perda da chave ⇒ OTA bloqueado até novo build de loja com certificado novo — risco aceito e documentado.
3. **Publish de `production` manual, exclusivo do PO, do Mac Mini.** Conta Expo com 2FA. **Proibido criar `EXPO_TOKEN` persistente em CI** — não existe pipeline OTA e criar token robô é superfície gratuita (PO-SEC-3). Revisão desta proibição exige novo ADR.
4. **Trilha de auditoria:** SHA da main + autor na mensagem de todo update (FR-015; evidência no dashboard EAS).

## Consequências

- Defense in depth: comprometimento da conta Expo ou da infra EAS não basta para entregar código à base — precisa também da chave privada local.
- Custo recorrente ~zero: assinatura automática no `eas update`; setup único; TestFlight/builds inalterados.
- Novo ativo crítico a gerir: a chave privada (backup, acesso restrito ao Mac Mini/PO).

## Alternativas rejeitadas

- **Diferir code signing:** custo de habilitar é config única; janela sem integridade de bundle em app de saúde não se justifica.
- **Token de CI para publish automatizado:** sem pipeline OTA hoje; automação, se vier, será decidida em ADR próprio com escopo de token mínimo.
