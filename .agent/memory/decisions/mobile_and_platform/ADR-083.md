# ADR-083 — Segurança do canal OTA: code signing habilitado + publish manual PO-only

**Status:** accepted (PO 2026-07-19) · **emendado 2026-07-27** (D1 revertida — ver §Emenda)
**Spec:** 051-expo-updates (NC2, RC-SEC S1/S2)
**Tags:** mobile, eas-update, ota, security, code-signing

## Contexto

EAS Update cria um canal de distribuição de código executável para devices de um app de saúde. RC-SEC (2026-07-19) identificou: S1 (Critical) — conta Expo comprometida = bundle malicioso para 100% da base sem loja; S2 (High) — sem code signing, o cliente aceita qualquer bundle que a infra da Expo entregue.

Contexto operacional: builds locais no Mac Mini (`eas build --local`), submissão TestFlight local. `eas update` não usa build queue (só upload) — filas do plano gratuito são irrelevantes para OTA.

## Decisão

1. **Code signing do expo-updates habilitado NESTE slice (051).** `npx expo-updates codesigning:generate` no Mac Mini; certificado embutido no build via `app.config.js` (`updates.codeSigningCertificate`); todo `eas update` assina com a chave privada local; cliente rejeita bundle não assinado (PO-SEC-1).
2. **Chave privada fora do repo** (gitignore) + backup seguro documentado no runbook. Perda da chave ⇒ OTA bloqueado até novo build de loja com certificado novo — risco aceito e documentado.
3. **Publish de `production` manual, exclusivo do PO, do Mac Mini.** Conta Expo com 2FA. **Proibido criar `EXPO_TOKEN` persistente em CI** — não existe pipeline OTA e criar token robô é superfície gratuita (PO-SEC-3). Revisão desta proibição exige novo ADR.
4. **Trilha de auditoria:** SHA da main + autor na mensagem de todo update (FR-015; evidência no dashboard EAS).

## Consequências

- Defense in depth: comprometimento da conta Expo ou da infra EAS não basta para entregar código à base — precisa também da chave privada local.
- Custo recorrente ~zero: assinatura automática no `eas update`; setup único; TestFlight/builds inalterados.
- Novo ativo crítico a gerir: a chave privada (backup, acesso restrito ao Mac Mini/PO).

## Emenda 2026-07-27 — D1 revertida: code signing DESATIVADO (barreira de plano)

**Fato novo, descoberto na implementação (051-A PR 1.6):** code signing do EAS Update é **recurso pago**. O `eas update` recusa a publicação com:

```
EAS Update code signing requires a subscription to the EAS Enterprise plan.
This account (coelhotv) currently does not have a subscription plan.
```

A D1 original ("custo de habilitar é config única") era **factualmente errada** — não por análise ruim, mas porque a informação não estava disponível: a documentação do `expo-updates` descreve o recurso sem mencionar o gate de plano, e o `codesigning:generate` gera as chaves normalmente numa conta sem plano. O erro só aparece no primeiro `eas update`. Enterprise é preço corporativo, fora do orçamento do projeto.

**Decisão do PO (2026-07-27): seguir com OTA sem code signing, risco aceito e nomeado.**

1. `updates.codeSigningCertificate`/`codeSigningMetadata` ficam **comentados** no `app.config.js`, com o motivo anexado.
2. ⚠️ **Armadilha de reativação:** binário COM certificado rejeita bundle NÃO assinado. Reativar sem ter o plano trava o canal OTA nos dois sentidos (não dá pra assinar, e o cliente não aceita sem assinatura) e só um **novo build de loja** destrava. Não reative sem o plano ativo.
3. O par de chaves gerado fica guardado (`certs/certificate.pem` versionado; privada fora do repo em `DOSIQ_OTA_PRIVATE_KEY_PATH`). Se houver plano no futuro, reativar é descomentar + rebuildar.
4. **Os controles de D3 sobem de defesa secundária a defesa PRINCIPAL:** 2FA obrigatório na conta Expo, publish manual exclusivo do PO no Mac Mini, proibição de `EXPO_TOKEN` persistente em CI. Não eram redundância — agora são tudo o que existe.

**Risco residual, nomeado sem eufemismo:** comprometer a conta Expo passa a bastar para entregar código arbitrário a 100% da base instalada, sem passar por loja, num app de saúde com alarmes de dose. A única barreira é o 2FA. Mitigação parcial pós-fato: `update:rollback` continua disponível e não exige assinatura.

**PO-SEC-1 fica sem objeto** (não há como demonstrar rejeição de bundle não assinado sem o recurso). Substituída pela obrigação de demonstrar PO-SEC-3 (2FA ativo + zero token em CI), que era `[051-B]` e passa a ser o controle de fato.

**Revisão:** se o projeto assinar um plano do EAS que inclua o recurso, esta emenda é revertida (reativar D1) sem necessidade de ADR novo — a decisão original permanece a preferida.

## Alternativas rejeitadas

- **Diferir code signing:** custo de habilitar é config única; janela sem integridade de bundle em app de saúde não se justifica. — ⚠️ **Premissa falsa**, ver §Emenda: o custo não era config única, era assinatura Enterprise.
- **Pagar EAS Enterprise (avaliado em 2026-07-27):** preço corporativo, desproporcional ao estágio do projeto.
- **Servir updates de infra própria com assinatura:** trocaria a infra gerenciada do EAS por servidor próprio no caminho de entrega de código a um app de saúde — mais superfície para manter e para errar. Não investigado a fundo; reabrir só se o risco residual se mostrar inaceitável na prática.
- **Token de CI para publish automatizado:** sem pipeline OTA hoje; automação, se vier, será decidida em ADR próprio com escopo de token mínimo.
